# Задержка хуков: аудит, замеры, результат

Дата замеров: 2026-10-13. Машина: Windows 11, 24 логических процессора, Python 3.11.13 (окружение `ape311`), ревизия репо `278bc52`.

## Что измерялось

Сколько времени пользователь ждёт из-за хуков. Хук это отдельный процесс Python, который запускается на событие. По документации Claude Code все подходящие хуки одного события выполняются параллельно, поэтому ожидание определяется самым медленным хуком и затратами на одновременный запуск процессов. Сумма времён по очереди показывает нагрузку на процессор.

Две метрики в таблицах:

- «сумма по очереди»: сумма медиан всех хуков хода;
- «самая медленная группа фазы»: группы (событие и маска инструмента) измеряются по одной, внутри группы хуки запускаются одновременно, затем берётся максимум по группам каждой фазы (до и после инструмента) и складывается по фазам. Одновременный запуск нескольких групп одной фазы не учитывается, поэтому цифра занижает реальное ожидание. Для сравнения двух вариантов, измеренных одинаково (`--ab`), она годится, как абсолютная задержка нет.

Три типичных «хода»:

| Ход | Процессов Python |
|---|---|
| сообщение пользователя | 13 |
| вызов `Bash` | 18 |
| вызов `Edit` или `Write` | 30 |

## Как повторить

```bash
# базовый замер всех хуков из манифеста репозитория
python scripts/bench_hooks.py --python <путь к python 3.11> --runs 7 --out docs/perf/hook_bench_baseline.json

# честное сравнение двух вариантов запуска (чередование внутри одного прогона)
python scripts/bench_hooks.py --python <путь> --ab=-S --runs 9 --out docs/perf/hook_ab_S.json

# проверка, что флаг не меняет поведение хуков
python scripts/bench_hooks.py --python <путь> --verify-flags=-S
```

Хуки запускаются в временном каталоге HOME и временном git-репозитории, настоящие `~/.claude` и репозиторий не затрагиваются. Из-за этого хуки, которым нужны реальные данные (граф знаний, база задач), в замере делают меньше работы, чем в живой сессии. Цифры по таким хукам нижняя оценка.

## Где уходит время

- Пустой запуск интерпретатора: 51–54 мс. Это 52–55% времени каждого хода.
- Из 54 мс около 24 мс приходится на `site` и файлы `.pth` окружения: это разница между обычным и `-S` запуском (`baseline` в JSON, 51–54 против 24–30 мс). Какие именно `.pth` виноваты (`google_generativeai`, `pywin32`, `distutils-precedence`), показал разовый `python -X importtime`, скрипта для него в репо нет. Это свойство окружения, не репозитория.
- Запуск процессов одновременно стоит дорого. Пустые запуски: 1 процесс 53 мс, 13 процессов 96 мс, 30 процессов 192 мс. С `-S`: 25, 50 и 96 мс. Каждый лишний одновременный процесс добавляет около 4,8 мс (с `-S` около 2,4 мс). Источник: `docs/perf/adhoc/process_start_contention.py`.
- Свой код хуков (общая библиотека `hooks/lib`, чтение stdin, логирование) добавляет около 40 мс к полу (медиана хука 94 мс минус 54 мс пустого запуска, `hook_bench_baseline.json`).
- Версия «хуки импортируют фасад `utils`» не подтвердилась: ни один из 87 хуков не импортирует его (поиск по `hooks/*.py`).
- В 87 хуках из манифеста и в `hooks/lib` сторонних импортов нет (разбор AST). Сторонние пакеты есть только в хуках, которых нет в манифесте: `artifact_schema_validator.py` (`jsonschema`) и `doc_bridge.py` (`pandas`), оба загружают их лениво. Поэтому запуск без `site-packages` возможен для подключённых хуков. Скрипта разбора в репо нет, проверка повторяется поиском `import` по этим файлам.

## Результат опции `-S` (честное сравнение)

Варианты чередовались внутри одного прогона, 9 повторов, порядок менялся на каждом шаге. Первое сравнение двумя отдельными прогонами показывало −30%, но на той же группе повторные замеры давали около −17%: нагрузка машины дрейфовала между прогонами. В отчёт идут только данные с чередованием.

Цифры пересчитываются из `docs/perf/hook_ab_S.plain.json` и `docs/perf/hook_ab_S.flags.json` командой `python scripts/bench_hooks.py --compare docs/perf/hook_ab_S.plain.json docs/perf/hook_ab_S.flags.json`.

| Ход | Метрика | без `-S`, мс | с `-S`, мс | Изменение |
|---|---|---|---|---|
| сообщение | сумма по очереди | 1368,5 | 1082,3 | −20,9% |
| сообщение | самая медленная группа фазы | 187,5 | 154,0 | −17,9% |
| Bash | сумма по очереди | 1731,4 | 1354,8 | −21,8% |
| Bash | самая медленная группа фазы | 257,9 | 226,4 | −12,2% |
| Edit/Write | сумма по очереди | 3564,0 | 2846,1 | −20,1% |
| Edit/Write | самая медленная группа фазы | 414,6 | 385,7 | −7,0% |

Прогон `docs/perf/hook_bench_baseline.json` (один вариант, без чередования) дал для тех же ходов 1274,7 / 1702,4 / 3101,9 мс по очереди. Он нужен как справка, в сравнении не участвует: нагрузка машины в нём отличалась.

Проверка равенства поведения: 134 команды хуков, каждая запущена дважды без флага (контроль детерминизма) и один раз с `-S`, в чистом HOME. Расхождений из-за флага 0. Один хук (`plan_mode_guard.py`) недетерминирован сам по себе и исключён из сравнения. Ограничение: проверен один типовой payload на хук, остальные ветки кода не проверялись.

## Достигнута ли цель в 30%

Нет. Нагрузка на процессор снижена на 20–22%, ощущаемое ожидание (по метрике «самая медленная группа фазы») на 7–18%. Причина: ожидание зависит от числа одновременно запускаемых процессов, а `-S` уменьшает цену каждого, но не их число.

## Как включить `-S`

Опция выключена по умолчанию. Установщики подставляют флаги в каждую команду хука, если задана переменная окружения:

```bash
CLAUDE_HOOKS_PYTHON_FLAGS="-S" bash install.sh --profile=standard
```

В PowerShell: `$env:CLAUDE_HOOKS_PYTHON_FLAGS = "-S"`. Принимаются только точные токены `-S`, `-s`, `-B`, разделённые одним пробелом. Любое другое значение отбрасывается с предупреждением. Причина: флаги `-c`, `-m`, `-I`, `-x` меняют, какой код запускается (`-cpass` превратил бы каждый хук в пустую операцию, включая защитные), а проверка по набору символов их пропускает. Проверка значения без полной установки: `CLAUDE_HOOKS_PYTHON_FLAGS="-S" bash install.sh --check-hook-python-flags`.

## Что дало бы больше (не сделано)

1. Условие `if` у хуков (документация: процесс запускается только если вызов инструмента подходит под правило, например `Edit(**/decision.md)`). Девять хуков группы `Edit|Write` реагируют только на конкретные файлы (`decision.md`, `claim.md`, `mutation_suite.yaml` и подобные), но запускаются на каждую правку. Модель: без них самая медленная группа Pre `Edit|Write` 128 → 118 мс (−7,8%), группы Post 234 → 197 мс (−15,9%). Повторный запуск того же скрипта (параллельно шёл полный pytest, то есть нагрузка была выше) дал Pre −6,2%, Post −23,1%; разброс между прогонами реальный, поэтому честная оценка это диапазон: Pre −6…−8%, Post −16…−23%. Источник: `docs/perf/adhoc/if_gating_model.py`. Это модельная оценка по реальным хукам (хуки просто убраны из группы), а не измерение с `if` в живом клиенте. Нужно проверить семантику сопоставления путей в клиенте и для каждого хука доказать, что его собственное условие входит в правило.
2. Один процесс на группу вместо 13–30 (диспетчер). Оценка только по таблице запусков (`process_start_contention.py`): каждый отсутствующий одновременный процесс экономит порядка 5 мс, то есть единицы-десятки миллисекунд на ход, это не измерение диспетчера. Меняет изоляцию хуков, режимы отказа и таймауты, поэтому требует отдельного решения.
3. Обрезка импортов в `hooks/lib` (ленивые `shlex`, `datetime`, компиляция регулярных выражений). Верхняя оценка около 10 мс на хук по стоимости импортов, на параллельное время почти не влияет. Не делалось из-за риска для публичных констант, которые подменяют тесты.

## Ограничения

- Одна машина, одно окружение с несколькими `.pth`-файлами; на чистом окружении выигрыш от `-S` меньше.
- Харнесс Claude Code в замере не участвует: учтены только процессы хуков.
- Хуки при замере не видят реальное состояние `~/.claude`.
