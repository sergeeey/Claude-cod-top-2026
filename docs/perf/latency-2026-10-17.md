## Почему цель не достигнута

- Цель −15% по p95 и p99 достигнута для `post_commit` без нагрузки и для p95 под нагрузкой.
- Для `pre_edit`, `pre_bash` и `post_edit` (код) цель не достигнута. Структура времени хука: старт процесса (около 33 мс с пустым процессом) плюс импорт модулей (медиана около 40 мс по `importtime`) плюс тело (мало). Правки кода затрагивают только импорт; их эффект 2–10%.
- Что дало бы больший эффект: отсечение холостых хуков. Манифест с отсечением 13 хуков даёт −30% p95 без нагрузки и −33% под нагрузкой относительно базы того же кода. Другой путь — объединить хуки в один процесс. Это меняет изоляцию и режимы отказа, поэтому не делалось.
- Кандидаты в коде, не сделаны: ленивая компиляция регулярных выражений в `lib/security.py`; разбор разрыва wall − CPU.

## Ограничения

- Синтетическая нагрузка: 4 сессии, фиксированные входы, пустое состояние. В живой сессии с большим state цифры будут другими.
- p99 по 100–120 образцам опирается на один–два наибольших значения. Интервалы широкие: у what-if без нагрузки от 0,36 до 1,40. Контроль показал выброс ×2,3 у одинакового кода под нагрузкой. Выводов по p99 под нагрузкой не делаем.
- Разброс между сериями одного варианта около 7–9%. Одиночные серии не парные, поэтому их разница не доказательство. Сравниваются только отношения внутри одной серии.
- `before` отличается от текущего кода правками по ревью. В стенде без конкуренции за блокировки это не влияет на задержку, но `before` не является чистым снимком «до задержек».
- Отсечение проверено на пяти входах одного хука `post_edit`: `.py`, `.md`, `decision.md`, тесты. Пути вне репозитория, другие типы правок (`Write`) и другие ходы не проверялись.
- CPU с шагом 15,6 мс. RSS — сумма пиков процессов.
- Асинхронные хуки не входят в стенд, их CPU не учтён.
- Стенд пишет состояние `plan_mode_guard` в системный temp, общий для прогонов. Состояние мало (сотни байт), поэтому на сравнение это не влияет; вывод хука при этом может отличаться от изолированной проверки.
