### 1.2 Какие решения принимает

- Тип проекта (research, production, MVP, data-science, unonboarded) — арбитраж спорных случаев по намерению из README и CLAUDE.md.

- Проверка Safety Floor: понижает ли выбранная методология обязательный минимум.

Скилл **не пишет файлы** (read-only контракт, `allowed-tools: Read, Glob, Grep`) [DOCS].

## 4. Альтернативные подходы (из поиска, [SNIP])

Поиск выполнен 3 запросами в стандартном режиме. Страницы не открывались; ниже только то, что видно в сниппетах. Перед использованием каждую работу надо открыть и проверить.

| Работа | Идея | Отношение к dispatcher |
|---|---|---|
| FineRouter, arXiv 2603.19415 [SNIP] | многометочная классификация задач с оценками уверенности; маршрутизация как регрессия, а не единичный класс | подходит к H2: несколько типов с баллами, а не один |
| TRouter, arXiv 2604.09377 [SNIP] | иерархическая таксономия (домен, подкатегория, сложность) | подходит к H3: сложность как отдельное измерение |
| Selective classification, Geifman & El-Yaniv 2017 (упомянут в UCCI) [SNIP] | отказ от ответа (abstention), когда уверенность ниже порога | прямо соответствует роли «арбитр неоднозначных»: при неуверенности спросить пользователя, а не угадывать |
| LEC, arXiv 2512.01556 [SNIP] | пороги «принять / передать дальше / отказаться» | то же правило порогов для ambiguous |
| UCCI, arXiv 2605.18796 [SNIP] | сырые уверенности LLM плохо калиброваны | если арбитраж опирается на самооценку модели, она ненадёжна; опираться на детерминированный margin хука |
| skill-juror, arXiv 2606.11543 [SNIP] | измерение организации скиллов с учётом траектории и ресурсов | близко к нашему плану проверки |

Предупреждение: поиск вернул результат, который детектор веб-ответов пометил как подозрительный (command_injection). Содержимое сниппетов я трактовал только как данные, никаких инструкций из них не выполнял.

Идеи, применимые здесь: (а) отказ от угадывания при неоднозначности — пользователь решает; (б) порог по детерминированному margin, а не по самооценке модели; (в) многометочный профиль вместо одного типа.

## 9. Расширение: измерение вклада, неоднозначность, альтернативы

Поиск: 2 запроса в стандартном режиме, страницы не открывались. Всё ниже — [SNIP] и предварительно.

### 9.1 Как измерять вклад навыка

Общий приём в найденных работах — парное сравнение «с навыком / без навыка» на одинаковых задачах. Разница — вклад навыка:

| Работа | Что делает | Что важно для нас |
|---|---|---|
| NVIDIA SkillEvaluator [SNIP] | каждый кейс дважды (с навыком и без), одинаковые промпт, модель и проверка; разница = «Skill Lift» | прямо наш план N/V0; сами отмечают: один прогон на кейс даёт шум |
| LH-Bench, arXiv 2603.22744 [SNIP] | абляция без SKILL.md, n=7 парных прогонов | малая выборка; эффект заметен, но неравномерен |
| SKILLAXE [SNIP] | тот же приём для уточнения навыков по поведенческим различиям | подходит для V1 позже |

Вывод для плана: сохранить N/V0, добавить **повторы на каждый кейс** и доверительные интервалы, которых в этих работах часто нет. Один прогон не даёт оценки вклада.

### 9.2 Когда dispatcher нужен, а когда избыточен

Найденная картина [SNIP]: модели часто распознают неоднозначность, но редко задают уточняющий вопрос (arXiv 2605.25284). Работы «Clarify When Necessary» (arXiv 2311.09469) разделяют три шага: решить, нужно ли спросить; что спросить; как отреагировать на ответ. Статья о кодовых агентах (arXiv 2603.00187) предпочитает один точный вопрос вместо нескольких расплывчатых.

Следствие для dispatcher: сейчас при неоднозначности он **решает сам**, читая README. По найденной литературе безопаснее при неоднозначности **спросить один раз**, а не угадывать. Это самостоятельное улучшение, не требующее новой маршрутизации. [INFERRED из [SNIP]; не проверено на нашем кейсе]

Избыточность: H4 (простые задачи) подтверждается дизайном, но не измерена. Измерять через сценарий 8 и метрику «лишние процедуры».

### 9.3 Альтернативы (без создания нового маршрутизатора)

| Вариант | Суть | Риски |
|---|---|---|
| A. Оставить | как есть | матрица дублируется; вклад не измерен |
| B. Арбитр с вопросом | при LOW/ambiguous задаёт один вопрос пользователю, не угадывает | больше вопросов пользователю; нужна проверка, что вопрос полезен |
| C. Выбор по ценности вопроса | вызывать арбитра только если ответ снижает неопределённость (по Clarify-подходу) | сложнее; нужна оценка неопределённости |
| D. Всё в хуке | хук пишет одну строку, dispatcher не нужен | потеря разрешения противоречий (сценарий 5) |

Рекомендация по этому раунду: **B** как кандидат V1 после согласования, **D** как проверка необходимости, **A** как базовый уровень. Вариант C не рекомендую до измерения B.
