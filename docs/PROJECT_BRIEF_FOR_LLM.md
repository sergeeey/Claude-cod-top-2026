# Claude-cod-top-2026: обзор проекта для внешнего ревью

Репозиторий: https://github.com/sergeeey/Claude-cod-top-2026 (публичный, лицензия MIT).
Срез: ветка `main`, коммит `6bb6860`, 2026-11-24. Все числа ниже посчитаны по этому коммиту, если не сказано иное. Там, где число взято из README, это помечено: README — заявление автора, а не независимая проверка.

## Для чего проект

Это не приложение, а устанавливаемая конфигурация для Claude Code (CLI-агента Anthropic): хуки, навыки (skills), агенты, правила и шаблон `CLAUDE.md`. Установщик копирует их в `~/.claude/` пользователя.

Автор называет проект «Evidence-aware Goal Operating Layer»: агент получает цель, строит объяснимый план, подбирает навыки и агентов, работает в заданных рамках автономии, проверяет результат и запоминает, что сработало.

Главная проблема, против которой проект строился, в README названа Validation Theater. Пример: агент сам пишет тест, сам генерирует синтетические данные, получает F1=1.000 и объявляет успех, а на реальных данных всё ломается. Поэтому каждое утверждение помечается маркером доказательности, а синтетическая проверка не считается проверкой на реальных данных.

## Архитектура

### Реестры и гейты вместо ручного ревью

Три декларативных реестра описывают, что установлено, а скрипты сверяют их с реальными файлами. CI падает при любом расхождении.

| Реестр | Что описывает | Чем проверяется |
|---|---|---|
| `hooks/registry.yaml` | класс, `fail_mode`, событие и уровень эскалации каждого хука | `scripts/gen_hook_matrix.py --check`, генерирует `docs/hook-control-matrix.md` |
| `skills/registry.yaml` | `kind`, `maturity`, `depends_on`, контракт capability каждого навыка | `scripts/check_architecture.py --check` (11 пронумерованных гейтов) |
| frontmatter `agents/*.md` | имя и инструменты агента | гейт 9 в `check_architecture.py` |

Правило проекта: новый хук, навык или агент добавляется вместе с записью в реестре в том же PR.

### Хуки

Хуки — это Python-скрипты, которые Claude Code запускает детерминированно на своих событиях. В отличие от правил в тексте, хук не зависит от того, послушается ли модель.

Важное ограничение, которое README называет прямо: заблокировать действие до выполнения может только хук `PreToolUse`. Остальные события (`PostToolUse`, `SessionStart`, `Stop` и другие) могут лишь добавить предупреждение или контекст после факта. Например, детектор Validation Theater работает в `PostToolUse`, поэтому он предупреждает, а не блокирует.

Основные защитные хуки `PreToolUse` по README:
- `input_guard` проверяет вызовы MCP-инструментов на prompt injection по 8 категориям;
- `pre_commit_guard` не пускает коммит в `main`, `rm -rf`, `DROP TABLE`;
- `permission_policy` решает до запроса пользователя, разрешить, запретить или спросить про Bash-команду;
- `read_before_edit` не даёт править файл без предварительного чтения;
- `plan_mode_guard` требует план при правке трёх и более файлов;
- `mcp_circuit_breaker` восстанавливает сессию при падении MCP-сервера.

Кроме того, хук редактирования персональных данных вырезает 12 типов шаблонов (номера карт, IBAN, ключи API, JWT, e-mail, телефоны и другие) из вызовов `mcp__*` до отправки наружу. README отмечает, что это не средство соответствия требованиям: имена и часть идентификаторов он не ловит, а Bash и веб-инструменты не проверяет.

Различие двух настроек отказа: `fail_mode` в реестре описывает поведение при ошибке в логике хука, а `hook_main(fn, fail_closed=...)` описывает поведение при падении или таймауте самого скрипта. Хуки, которые блокируют, обязаны задавать `fail_closed` явно.

### Навыки и оркестрация

Навык — это папка с `SKILL.md`: инструкция с триггерами, которую Claude Code подгружает по запросу. В реестре каждый навык помечен типом (`kind`) и зрелостью (`maturity`).

| `kind` | Число | | `maturity` | Число |
|---|---|---|---|---|
| methodology | 79 | | wired (подключён) | 114 |
| verifier | 19 | | described (только описан) | 29 |
| generator | 15 | | dogfooded (опробован на реальной работе) | 19 |
| integration | 14 | | | |
| utility | 13 | | | |
| domain | 12 | | | |
| orchestrator | 10 | | | |

Маршрут задачи:
1. Хук `project_classifier` на старте сессии определяет тип проекта: research, production, MVP или data-science.
2. Навык `dispatcher` по типу проекта и типу задачи загружает одну методологию, а не все тяжёлые правила сразу. Например: production — обязательные ревьюер и тесты не ниже 80% покрытия; research — полный Falsification Ladder и EstimandOps; MVP — облегчённая проверка. Классификация не может снять минимальные требования к безопасности и тестам.
3. Навык `routing-policy` выбирает путь: задача → навык → агент → инструменты.
4. Исполняют агенты, проверяют `reviewer` и `tester`.

Навыки `core`: `routing-policy`, `dispatcher`, `agent-teams`, `brainstorming`, `claim-decomposer`, `context-engineering`, `git-worktrees`, `hd-mavp-router`, `mentor-mode`, `reference-registry`, `skill-self-update`, `tdd-workflow`.

Среди `extensions` большая часть — методологии проверки утверждений и исследований: `skeptic` (поиск способа опровергнуть идею), `estimand-l0-gate` (классификация вопроса: описательный, предсказательный или причинный), `sci-code-audit` (аудит научного кода), `hypothesis-arbiter` (выбор между конкурирующими гипотезами), `consilience` и другие. Есть и рабочие инструменты: аудит архитектуры, CI, Obsidian, литература.

### Агенты

13 агентов: `architect`, `builder`, `explorer`, `fe-mentor`, `navigator`, `reviewer`, `scope-guard`, `sec-auditor`, `security-guard`, `skill-suggester`, `teacher`, `tester`, `verifier`. Три команды запускают агентов параллельно: `review-squad` (ревьюер и аудитор безопасности), `build-squad` (сборщик и тестировщик в изолированных git worktree), `research-squad` (поиск и проверка найденного).

По README рабочие агенты идут на Sonnet, стратегические — на Opus. У 7 агентов есть память между сессиями, у 2 — изоляция в worktree.

### Как агенты используют навыки

- Набор инструментов агента задан в его frontmatter. Например, у `dispatcher` только `Read`, `Glob`, `Grep`: он не может ничего записать или выполнить.
- Субагент не видит разговор, он получает только бриф. Правило `rules/delegation-contract.md` требует в брифе цель, границы, критерий готовности и условие остановки.
- Агенты не пишут в файлы памяти. Они возвращают результат, а решение о записи принимает оркестратор (`rules/context-loading.md`). Так параллельные агенты не портят общее состояние.
- Отчёт агента с пометкой `[VERIFIED]` для оркестратора считается только `[INFERRED]`, пока он не перепроверен инструментом (`rules/audit-verification-gate.md`).

### Правила

Правила (`rules/`) — текстовые инструкции, которые загружаются в контекст модели. Ключевые:
- `integrity.md` и `evidence-markers.md` — маркеры `[VERIFIED]`, `[DOCS]`, `[CODE]`, `[INFERRED]`, `[WEAK]`, `[CONFLICTING]`, `[UNKNOWN]` и оценка уверенности по числу источников;
- `falsification-ladder.md` — проверка утверждения по ступеням сложности;
- `estimand-ops.md` — что именно измеряется, для кого и что результат НЕ доказывает;
- `skeptic-triggers.md` — когда вызывать скептика: идеальные метрики, ноль провалов, синтетические данные;
- `rationalizations.md` — таблица типичных оправданий агента и ответов на них;
- `security.md`, `permissions.md` — данные, секреты, права.

Уровни автономии (Green / Yellow / Red / Black) описаны в `rules/autonomy-budget.md`: чтение и локальные правки агент делает сам, а push, merge, удаление данных, деньги и отправку сообщений — только с явного согласия человека.

### Память

У проекта есть файлы состояния: `.claude/memory/activeContext.md` (что делаем сейчас), `decisions.md` (решения и причины), `patterns.md` с повторяющимися ошибками. Повторившаяся ошибка получает счётчик `[×N]`, а после трёх повторов становится жёстким правилом.

## Сильные стороны

- Описание сверяется с кодом автоматически: реестры и гейты в CI ловят ситуацию, когда документация обещает хук или навык, которого нет.
- Защита по умолчанию: блокирующие хуки работают fail-closed, а классификация проекта не может отключить минимум по безопасности и тестам.
- Явная дисциплина доказательств: маркеры, проверка утверждений агентов, отдельный учёт синтетических и реальных проверок.
- Методология для исследовательской работы, которой обычно нет в конфигурациях: Falsification Ladder, EstimandOps, журнал отрицательных результатов.
- Честный README: в нём прямо сказано, что проект не готов к production, что подтверждающих реальных прогонов пока 2 и что большинство событий только предупреждает.
- Всё на Python, без JS-зависимостей; около 10 МБ (по README).

## Слабые стороны и известные проблемы

| Проблема | Подробности | Источник |
|---|---|---|
| Мало подтверждений на практике | README: «dogfood evidence still growing (2 real runs so far)». Из 158 навыков только 19 помечены как опробованные на реальной работе, 29 только описаны | README, `skills/registry.yaml` |
| Большая часть контроля только предупреждает | Блокировать может лишь `PreToolUse`; детектор Validation Theater и многие проверки качества работают после факта | README, раздел о хуках |
| Цена контекста | По оценке README, профиль `standard` загружает около 28 500 токенов постоянных правил плюс около 2 100 на `CLAUDE.md` | README, таблица «Why This Config?» |
| Пересечение методологий | 79 навыков типа methodology; часть из них близка по назначению, поэтому нужен отдельный документ разграничения `docs/skill-disambiguation.md` | `skills/registry.yaml` |
| Агент из README отсутствует в репозитории | На схеме агентов в README есть `boyko-agent`, но файла `agents/boyko-agent.md` в `main` нет: это личный агент автора | README, `agents/` |

| Узкая применимость | Только Claude Code, в основном Python, рассчитан на одного разработчика; личные навыки `boyko-*` и навыки под Obsidian без доработки не переносятся | README |
| Расхождение живой установки и репозитория | Исправление, слитое в репозиторий, не действует, пока не переустановлено в `~/.claude`; для этого есть хук `live_drift_guard` и скрипт `scripts/redeploy_drift.py` | `CLAUDE.md` в корне репозитория |

1. `README.md` — назначение, состав, ограничения.

3. `PRODUCT_CONSTITUTION.md` и `docs/positioning.md` — миссия и позиционирование.
4. `hooks/registry.yaml` и `docs/hook-control-matrix.md` — все хуки и что из них реально блокирует.

## Что было бы полезно оценить внешнему ревьюеру

- Оправдана ли цена контекста профиля `standard` относительно пользы.
- Какие из 79 методологических навыков дублируют друг друга и что можно объединить.
- Можно ли перенести часть проверок из `PostToolUse` (предупреждение) в `PreToolUse` (блокировка) без большого числа ложных срабатываний.
- Как получить больше реальных подтверждений работы, чем 2 прогона.
