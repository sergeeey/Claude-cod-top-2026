# methodology-outcomes.md — Журнал полезности элементов собственной методологии

_Это НЕ реестр гипотез и НЕ список кандидатов на проверку. Сюда попадает только
компонент методологии (правило, gate, шаг протокола, скилл), который **уже был
реально применён и оценён**. Кандидаты «надо бы проверить» живут в
`pearl_registry/INDEX.md`, а не здесь — иначе журнал исходов превращается в
список пожеланий и перестаёт отвечать на свой единственный вопрос:
«что из нашей методологии реально работает?»._

**Статус: РУЧНАЯ ФАЗА (заведён 2026-07-29).** Ни хука, ни автоматической записи,
ни флага `research-audit --methodology` сознательно нет. Обоснование — в разделе
«Решение об автоматизации» ниже.

## Словарь вердиктов (ровно три значения)

| Вердикт | Когда |
|---|---|
| `ПОМОГЛО` | Есть сравнение (baseline / control / rerun) и наблюдаемая разница в пользу компонента |
| `НЕ ПОМОГЛО` | Есть сравнение, разницы нет ИЛИ разница против компонента |
| `НЕОПРЕДЕЛЁННО` | Применялось, но сравнить не с чем / результат не разделяет варианты |

`НЕ ТЕСТИРОВАЛОСЬ` в этот файл не попадает — это не исход.

**Правило области действия (обязательно, добавлено 2026-07-29 после внешней рецензии).**
Вердикт всегда читается ВМЕСТЕ с endpoint'ом, записанным в колонке «Компонент».
`НЕ ПОМОГЛО` в строке про конкретный endpoint не означает «компонент бесполезен» —
только «на этом endpoint'е, в этом кейсе разницы не обнаружено». Компонент обязан
называть свой endpoint явно; строка без endpoint'а неинтерпретируема и подлежит
переписыванию, а не толкованию. Причина жёсткости: широко записанный вердикт
превращается в зомби-вывод, который потом блокирует повторную проверку живой идеи —
ровно то, от чего защищает `Rescue Review` в `rules/falsification-ladder.md`.

## Формат колонок

- **Доказательство** — обязательно `путь@SHA` + наблюдаемая дельта. Голый путь
  не годится: файл может быть переписан позже, и строка станет непроверяемой.
- **Уверенность** — отдельно от `n`. `n` это размер наблюдения, уверенность
  учитывает ещё: есть ли baseline/control, повторяемость, переносимость на
  другие домены, известные конфаунды, шум измерения.

## Решение об автоматизации (пересмотреть после 4 записей)

Сейчас записей 2. Порог пересмотра — 4 **eligible** исхода (то есть строки в
таблице выше, а не кандидаты). На пересмотре проверить четыре вещи:

**Первые две строки — seed (внесены задним числом при заведении файла) и в
метриках времени/своевременности НЕ участвуют.** Считать эти две метрики
только по перспективно внесённым строкам №3–4. Иначе стартовая стоимость
заведения файла навсегда исказит оценку его текущей стоимости.

| Метрика | Ориентир | Статус на 2026-07-29 |
|---|---|---|
| Доля строк с `путь@SHA` | 100% | ✅ **PASS**, 2/2 |
| Записи вносились по факту решения, не задним числом | ≥3 из 4 | ⏳ **не применимо к seed-строкам** — измерять на строках №3–4 |
| Стоимость одной записи | ~2 минуты | ⏳ **bootstrap-наблюдение, не показатель.** Обе seed-строки потребовали `git log --follow` + перечитывания артефакта, но это разовая стоимость восстановления истории задним числом; при записи по горячим следам SHA и числа уже в руках. Измерять на строках №3–4 |
| Журнал реально использован последующим аудитом или решением | ≥1 раза | ⏳ **ЕЩЁ НЕ НАБЛЮДАЕМО** — файл создан сегодня, ни один аудит с тех пор не проводился |

> **Почему `⏳`, а не `❌` (правка 2026-07-29, внешняя рецензия).** Первая версия
> этой таблицы помечала три метрики как проваленные. Это была ошибка того же
> класса, против которого у нас есть отдельное правило: Substrate Gate в
> `rules/falsification-ladder.md` прямо запрещает записывать «тест не смог
> выполниться» как «claim провален». «Ещё не наблюдалось» — это третий исход, а
> не провал. Метрика, у которой физически не было возможности сработать, не
> может быть красной; красной она станет, если возможность была и не сработала.

> **Ориентиры выше — эвристики, а не откалиброванные пороги.** Ни «2 минуты», ни
> «≥3 из 4» ни на чём не основаны, кроме здравого смысла; их назначение — дать
> будущему пересмотру хоть какую-то опору, а не изобразить измеримость. Если на
> пересмотре они окажутся неудобными — менять их, а не подгонять под них журнал.

Решение по результату пересмотра:
- журналом никто не воспользовался → **не автоматизировать**, рассмотреть закрытие;
- полезен, но записи забываются → добавить мягкий хук, реагирующий **только** на
  явный маркер `<!-- methodology-outcome: <ID> -->` в `decision.md` (не на
  упоминание путей `rules/`/`agents/`/`skills/` — такой триггер даёт ошибки обоих
  родов, ровно как регексп `skeptic_auto_trigger`, ловивший `[100%]` из
  прогресс-бара pytest вместо авторских утверждений, см. `d1d0368`);
- полезен и записи не забываются → хук не нужен, добавить только срез
  `research-audit --methodology`.

## Находка первого дня (n=1, но настоящая)

Заведение этих двух строк само по себе кое-что поймало. Требование писать
`путь@SHA` + отдельную уверенность заставило перечитать первичный артефакт, и
перечитывание вскрыло, что ходовой пересказ «DDD-S2 дал 7→11/12» ронял два
факта: (а) сравнение с Arm A мутное, потому что Arm A в разных прогонах получил
9/12 и 7/12 на **байт-идентичном** тексте; (б) шум грейдера ±2 балла — это
половина заявленного улучшения. Ни один из этих фактов не был потерян злонамеренно,
они просто не пережили сжатие в одну фразу.

Это не доказывает, что журнал полезен — n=1, и «формат заставил перечитать
источник» может оказаться разовым эффектом новизны. Но зафиксировать стоит:
это первый наблюдаемый случай, когда сам формат что-то поймал.

## Внешние ориентиры (проверены, 2026-07-29)

Готового лёгкого решения именно под эту задачу не нашлось. Ближайшие аналоги,
существование и содержимое подтверждены через `gh api`:

- [`prime-radiant-inc/superpowers-evals`](https://github.com/prime-radiant-inc/superpowers-evals)
  (87★) — behavioral eval методологии; взято отсюда: трёхзначный вердикт
  (`pass`/`fail`/`indeterminate` — строка реально встречается 9 раз в их
  campaign-доке), frozen control, равный вес отрицательным результатам.
  Не взято: Quorum, контейнеры, отдельный eval-движок.
- [`obra/superpowers`](https://github.com/obra/superpowers) (263k★),
  `skills/writing-skills/SKILL.md` — TDD для методологии: baseline без skill →
  прогон со skill. Взято: для сильного `ПОМОГЛО` нужен baseline.
- [MADR](https://github.com/adr/madr) — взято: evidence + критерий пересмотра.
- MLflow ↔ Claude Code (трассировка реальных tool-call'ов + blind-comparator) —
  рабочее решение для оценки **скиллов**, отдельный трек, здесь не применяется.
