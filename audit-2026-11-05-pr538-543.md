## Findings and concrete fixes

### F1 — Reconcile axis status with evidence and accepted risk

**LOW; [CODE].** In `skills/extensions/boyko-knowledge-architecture/SKILL.md`, lines 66 and 181 restrict axis statuses to `PASS / PARTIAL / FAIL / UNKNOWN`. Line 90 explicitly calls useful-but-replaceable objects `PARTIAL` as an accepted risk. New line 191 instead says an owner-accepted shortcoming whose status is `PARTIAL` is reported as `OBSERVED` with the risk disposition. `OBSERVED` is also an evidence label at line 132.

This leaves two plausible outputs for the same accepted Recovery gap and no explicit rule for separating the axis verdict from the finding's evidence label. The ambiguity is present in the instructions; no downstream parser failure or new live report failure was demonstrated.

**Fix:** Define separate fields for axis status, evidence label and risk disposition. Retain the four-value axis vocabulary and state how an accepted gap affects it, or deliberately extend that vocabulary everywhere. Update the Recovery example and add one expected report row for an owner-accepted gap. This is a targeted documentation fix, not a proposal for another subsystem.

### F3 — Cover every newly exempted field and its strict neighbors

**LOW; [CODE], [VERIFIED-SYNTHETIC].** `tests/test_input_guard_harness_prose.py:43-64` adds four tests: recap prose, recap attack, remaining-plan prose, and unrelated-tool rejection. The `ask` value in the recap test contains no backticks, so that test cannot detect loss of its exemption. There is no dedicated handoff attack or strict `cwd/session_id/extra` control for the newly added tools. Existing spawn/send tests cover many shared scanner properties and reduce the risk, but do not exercise the full new routing map.

The audit ran 36 additional cases: six cases for each of the four explicitly documented new-tool fields, plus three strict-field controls for each field context. **Fix:** Parameterize these boundary cases in the new test file, including exact-name and non-dictionary controls for the new tools. Consider one explicit tool-to-fields map: the current expression at `hooks/input_guard.py:384` unions the shared legacy fields with the per-tool extras. That is broader than a pure per-tool schema map, but no harmful accepted server parameter was established, so it is not reported as a security vulnerability.
