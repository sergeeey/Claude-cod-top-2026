## Findings and concrete fixes

### F1 — Do not write after failing to acquire the state lock

**HIGH; incomplete repair of an existing race, not a claim that the old version was safe.**

[CODE] In [hook_state.py:194](https://github.com/sergeeey/Claude-cod-top-2026/blob/8fcdfba9820fc5c706d381c3a32270d9581d6560/hooks/hook_state.py#L194), `file_lock(...)` yields whether it acquired ownership. On False, the code only prints a warning and still reaches `_merge_and_write()`. Another owner can therefore replace the file after this unlocked writer reads or saves it. The statement at line 184 that this “never erases other keys” is false. The pre-existing [file_lock contract](https://github.com/sergeeey/Claude-cod-top-2026/blob/8fcdfba9820fc5c706d381c3a32270d9581d6560/hooks/lib/state.py#L158) already warns about precisely this failure mode.

[VERIFIED-SYNTHETIC] A bounded instrumented interleaving on Windows used the real filesystem, real lock sentinel, and unchanged 1.5-second lock timeout. A synchronization barrier paused writer A just before replacement, modeling a stalled write:

1. A stages `{"last_test": 150.0}` while holding the lock.
2. B saves `last_edit=200.0`; it times out, takes the unlocked branch, and successfully persists `{"last_edit": 200.0}`.
3. A resumes and replaces the file with `{"last_test": 150.0}`.
4. Reload has no `last_edit`; the actual `commit_test_gate._should_warn()` returns **False**.

This is controlled failure injection, not a production incident or a measured occurrence rate. The established tests pass, but this additional interleaving directly demonstrates the defect.

[CODE] The real consumer [commit_test_gate.py:167](https://github.com/sergeeey/Claude-cod-top-2026/blob/8fcdfba9820fc5c706d381c3a32270d9581d6560/hooks/commit_test_gate.py#L167) defaults missing timestamps to zero. The edit stamp writer at line 312 and test stamp writer at line 279 share this state. [INFERRED] Lost freshness evidence can suppress its advisory commit warning and affect the Stop freshness check. No live harness exploitation was attempted.

**Fix:** Require ownership for the complete read/merge/replace operation. On timeout, retain pending writes and return an explicit unavailable/deferred result, or retry through a bounded serialized path. Consumers using freshness state should distinguish failed persistence from known-fresh evidence. Simply skipping a failed edit stamp prevents clobbering but does not by itself guarantee that the edit is recorded. Add a deterministic two-writer timeout test checking both final state and consumer verdict. Narrow the concurrency guarantee to what is actually enforced.

### F2 — Preserve or explicitly constrain mutable-value persistence

**MEDIUM API compatibility regression; no current in-repository consumer failure established.**

[CODE] At [hook_state.py:215](https://github.com/sergeeey/Claude-cod-top-2026/blob/8fcdfba9820fc5c706d381c3a32270d9581d6560/hooks/hook_state.py#L215), only keys in `_dirty` are copied into the re-read disk state. The set is populated by top-level `__setitem__`, then cleared after a successful write. However, `get()` and `__getitem__()` still return the underlying mutable dictionaries/lists.

[VERIFIED-SYNTHETIC] The same public-API sequence was executed against both base and target source:

```python
state["session"] = {"count": 1}
state.save()
state["session"]["count"] = 2
state.save()
# Reload: base -> 2; target -> 1.
```

The second save replaces the edited local value with the disk value because the key was never marked dirty. No concurrency is required.

[CODE] Inspected current writers in `commit_test_gate`, `iteration_guard`, `ace_reflector`, `locality_escalation_guard` and `validation_theater_guard`; their write paths explicitly assign top-level keys. This limits the demonstrated impact to backward compatibility of the shared API.

**Fix:** Preserve compatibility by comparing values against a deep baseline and merging only genuinely changed keys, or expose and enforce an explicit mutation API with a documented migration. Do not silently expose live mutable values whose changes will be discarded. Add dictionary/list mutation and subsequent-save cases.

## 🔥 Trend Gap

As of 2026-11-01, the important gap is transaction correctness, not novelty. Python documents atomic successful replacement; it does not make the surrounding read/modify/write sequence a transaction. The PR has the right primitives but bypasses its own exclusion on timeout. [Official Python os.replace documentation](https://docs.python.org/3/library/os.html#os.replace).

SQLite documents serialized writes and transaction isolation, illustrating the stronger semantic contract a state store could provide. This is a comparison, not a recommendation to migrate this small store: repairing its existing lock protocol is the scoped fix. No claim that the industry “moved” to a particular framework in 2026 is supported or needed. [Official SQLite isolation documentation](https://www.sqlite.org/isolation.html).
