## Findings and concrete fixes

### F1 — Do not let heredoc-looking data conceal a second repository

**HIGH; [CODE], [VERIFIED-SYNTHETIC]; known and disclosed regression.** The changed target selection at [hooks/pre_commit_guard.py:450](https://github.com/sergeeey/Claude-cod-top-2026/blob/6bb6860d9f9de370c0a29c5da5d3565b56019406/hooks/pre_commit_guard.py#L450) relies on `_command_statements`, which consumes the existing `split_shell_statements`. That shared helper recognizes a heredoc opener by regex without excluding quoted data, then omits later lines. Once the first feature-repository commit selects the checked cwd, an omitted second commit is no longer checked against the session repository.

Fixture: session repository is on `main`; `FEATURE` is an absolute path to a clean repository on `feature/audit`.

```bash
git -C "FEATURE" commit --allow-empty -m x
printf "%s\n" "<<EOF"
git commit --allow-empty -m y
```

Actual hook subprocess results against real fixture repositories: base emits `permissionDecision=deny` for `main`; target exits 0 with empty stdout and stderr. Removing the `printf` line restores target denial for multiple repository directories. A single feature-repository commit is correctly allowed by target and incorrectly denied by base, proving the intended improvement too.

**Impact:** The guard can miss branch protection and staged-file checks for the second repository. This is a regression in this hook's decision, not proof of a complete harness bypass, production incident, credential disclosure or arbitrary code execution. No proposed commit chain was actually executed. Git Bash could not start in the sandbox (Win32 error 5); the shell interpretation is supported by quoted-data semantics, while the before/after hook decisions are directly reproduced. The PR's own Limits section explicitly describes this case; it is not presented as a newly discovered hidden limitation.

**Fix:** Do not accept an ambiguous chain on the basis of a single resolved target. Preserve quote context when identifying heredocs and use conservative rejection for unsupported neighboring executable statements until there is stronger enforcement. Persist this base/target regression and its plain-chain control. If moving enforcement to Git, specify supported invocation paths and resistance to bypass; merely adding `pre-commit` is insufficient for an adversarial policy.

### F2 — Respect quoting and the end of command substitutions

**MEDIUM; [CODE], [VERIFIED-SYNTHETIC]; new false denials.** [hooks/pre_commit_guard.py:517](https://github.com/sergeeey/Claude-cod-top-2026/blob/6bb6860d9f9de370c0a29c5da5d3565b56019406/hooks/pre_commit_guard.py#L517) searches for the first `$(` or backtick anywhere in a statement and then searches the entire remaining suffix for `git` and `commit`. It neither excludes single-quoted/escaped text nor bounds the search to the substitution body.

With session and target both on a feature branch, base allows and target denies both:

```bash
git -C 'FEATURE' commit --allow-empty -m 'docs: $(git commit)'
git -C "FEATURE" commit --allow-empty -m "$(date +%F) docs: git commit"
```

The first message is literal text. The second executes `date`, with `git commit` only in the subsequent prose. The plain-message control `-m "docs: git commit"` passes both versions. The emitted reason incorrectly says another unparseable commit shares the command. Single-quoted characters are literal under the [Bash quoting rules](https://www.gnu.org/software/bash/manual/bash.html).

**Fix:** Recognize only executable substitutions, retain quote/escape context, and bound inspection to their bodies. Add literal single-quote, escaped opener, harmless-substitution-plus-prose and real nested-commit controls. The current test for substitutions without Git words does not cover words outside the substitution.

### F3 — Do not expand a quoted tilde after tokenization

**MEDIUM; [CODE], [VERIFIED-SYNTHETIC]; new target mismatch.** [hooks/pre_commit_guard.py:403](https://github.com/sergeeey/Claude-cod-top-2026/blob/6bb6860d9f9de370c0a29c5da5d3565b56019406/hooks/pre_commit_guard.py#L403) receives dequoted tokens and unconditionally calls `os.path.expanduser(d)`. Shell quoting prevents tilde expansion; that information has already been erased. The [Bash manual](https://www.gnu.org/software/bash/manual/bash.html) describes expansion of unquoted tilde prefixes.

Fixture: a real repository exists at `feature/~/child`. For `git -C '~/child' commit --allow-empty -m x`, base emits no denial; target denies because it looks for `child` beneath the user's home. A direct Git argument-list oracle, `git -C ~/child rev-parse --show-toplevel` with the literal string `~/child` passed as one argv element, returns the fixture's literal `feature/~/child` path. This oracle executes real Git, not shell expansion. The attempted Bash oracle failed to start and is not counted as verification.

**Impact:** A valid commit is blocked; in a different filesystem layout the hook could inspect another existing repository. Only the false-denial layout was reproduced; the latter impact remains **[HYPOTHESIS]**.

**Fix:** Preserve whether tilde was quoted/escaped before expansion, or explicitly reject unresolved shell forms without pretending to have resolved their target. Test unquoted `~/child`, quoted `'~/child'`, `"~/child"`, and a literal tilde directory against Git argv behavior. Do not expand by executing arbitrary shell input.

### F4 — Preserve the differential cases as integration tests

**LOW; [CODE].** The additions to `tests/test_pre_commit_guard.py` are substantial and protect real review findings. However, Git responses in main-path tests are mocked; the file contains no real Git repository setup/execution oracle. The quotation helpers are frequently checked against hand-written expectations from the same parsing model.

**Fix:** Add a small, persistent matrix using isolated feature/main repositories, actual Git queries and separate shell-semantic controls. Include F1–F3 plus positive cases. This is a test coverage recommendation grounded in the reproduced defects, not a claim that every mocked test is weak.

## Security and robustness review

- **Trust boundary:** Assistant-supplied command text is translated into a repository identity used for permission decisions. F1–F3 occur at that translation boundary. The PR explicitly calls this an accident guard, which limits its security claim but does not erase a behavioral regression.
- **Injection:** Changed code analyzes text and invokes existing Git queries with argv lists; it does not execute the proposed shell text. No new SQL, template, deserialization or network sink was introduced. No prompt-injection-specific path was added. This is not an exhaustive vulnerability certification.
- **Secrets:** Manual diff inspection and an added-line scan for private-key headers, GitHub-token shapes and AWS access-key IDs found zero matches. Counts only were printed. This limited scan does not prove absence of all credential formats or secrets elsewhere in history.
- **Races / mutable state:** Filesystem/repository existence, branch, index and diff are read separately before the eventual command runs. A concurrent change or a branch-changing statement earlier in a chain can invalidate the snapshot. No new asynchronous writer is introduced. Race/stress testing was not performed; this pre-existing architectural limitation is not scored as a newly demonstrated exploit.
- **Paths:** Reusing drive normalization is sound for the supported syntax. F3 demonstrates that normalization must follow a correct account of shell quoting. Existing standalone `--git-dir`, aliases, scripts and multiple-`cd` limits remain disclosed rather than silently declared solved.
- **Rate limiting:** No external calls added by the diff. Existing subprocess timeouts remain. The audit did not benchmark adversarial input size or certify complexity bounds.

## 🔥 Trend Gap

As checked on **2026-11-17**, the relevant gap is conformance to documented interfaces, not tool fashion. Python describes `shlex` as a Unix-shell-oriented lexer and recommends argument-list subprocess calls where practical. That supports retaining argv-based Git calls; it does not make this bespoke text parser a complete Bash evaluator. [Python shlex documentation](https://docs.python.org/3/library/shlex.html).

Git documents cumulative `-C` behavior and path interpretation relative to the changed working directory. Ordinary absolute/relative/repeated `-C` cases are covered by this PR; F3 concerns expansion before Git receives argv. [Git command documentation](https://git-scm.com/docs/git).

Git-native controls run at a more appropriate point for repository/index checks, but official documentation explicitly permits bypassing `pre-commit` with `--no-verify`. A `reference-transaction` hook can inspect and reject prepared ref updates, with its own deployment/configuration assumptions. Neither should be advertised as an unbypassable policy in a user-controlled repository. [Git hook documentation](https://git-scm.com/docs/githooks).
