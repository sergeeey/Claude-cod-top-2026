# bank_spec.md — спецификация банка задач (фаза 0, шаг 4)

_Одобрено владельцем вместе с планом 2026-10-15 (вариант Б). Пилотный банк: 8 задач. Основной банк строится по этой спецификации после пилота._

## 1. Категории и типы агентов

| Категория | Задача | Узкий тип | Инструменты узкого типа (файл / среда) |
|---|---|---|---|
| C1 | ревью документа с посеянными дефектами | `reviewer` | файл: Read, Grep, Bash, Glob; среда (смоук A5): + Write, Edit |
| C3 | проверка утверждений по двум источникам | `verifier` | файл: Read, Bash, WebFetch, WebSearch, Glob, context7 ×2; среда не проверена |

Сравнение всегда с явным `subagent_type: general-purpose` на той же задаче.

## 2. Структура задачи

- `bank/<ID>.md` — вход, который видит агент. Содержит текст промпта и материалы. Ничего больше.
- `keys/key_<C>.json` — ключ: точные значения, фрагменты источников, полные формулировки дефектов. **Не передаётся ни агенту, ни оценщику.**
- `rubric.md` — рубрика для оценщика с нейтральными описаниями дефектов и ожидаемыми вердиктами (без численных эталонов и без фрагментов источников).

## 3. Промпт

Промпт одинаков для обоих плеч и записан в начале каждого входа:
- C1: «Задача. Ниже аналитическая записка. Проверь её и перечисли все проблемы… Отвечай только по тексту записки.»
- C3: «Задача. Ниже список утверждений и два источника… Для каждого утверждения дай вердикт, опираясь только на источники… Не добавляй знаний извне.»

Агент не получает информации о плече. Промпт не сообщает число дефектов или утверждений и не содержит слов, которые подсказывают, где ошибка.

## 4. Правила посева (C1)

- 6 дефектов на задачу, каждый — отдельного типа в пределах задачи.
- Типы: статистика, каузальный вывод, селективная отчётность, определение исхода, согласованность чисел, обобщение, единицы, экстраполяция, отсутствие контроля, несоответствие метода, преувеличение, выбор данных, ссылки, оформление графика, утечка данных, дисбаланс классов, арифметика.
- Серьёзность: от низкой до высокой; в каждой задаче есть хотя бы один дефект высокой серьёзности.
- Дефект обнаруживается по тексту без внешних знаний. Нельзя ставить дефект, который видим только при знании сторонней работы.

## 5. Правила для C3

- 8 утверждений: 4–6 проблемных (опровергнуто или не подтверждено по источникам), 2–4 верных.
- Два источника. Источники внутренне согласованы, кроме посеянных противоречий, которые видимы в тексте.
- Вердикт определяется только источниками. Если ответ можно получить только из внешних знаний, утверждение не включается.

## 6. Анти-утечка

- Вход не содержит ключа, номеров дефектов, сумм «всего дефектов», формулировок «найди N ошибок».
- Перед включением задачи в банк проверяется поиском по тексту входа: идентификаторы D1–D6, фразы из ключа, слова «эталон», «ключ», «правильный ответ».

## 7. Калибровка оценщиков (до запусков)

Каждый из двух оценщиков оценивает:
- пустой отчёт («проблем не нашёл») — ожидается 0 по всем пунктам;
- полный отчёт (все дефекты найдены с верными формулировками) — ожидается 1 по всем пунктам.

Оценщик, не прошедший калибровку, не допускается к основному этапу.

## 8. Сложность и потолок

Цель пилота: контрольный агент (явный `general-purpose`) набирает не больше 0,70 доли найденных дефектов (C1) или верных вердиктов по проблемным утверждениям (C3), чтобы оставался запас 0,30 для сравнения.

- Если контроль выше 0,70 — задача усложняется (тоньше дефекты, меньше явных опор), а не выбрасывается без записи. Изменение фиксируется в журнале.
- Потолок проверяется отдельно для каждой категории.

## 10. Основной банк

- Строится по этой спецификации: n задач на категорию плюс резерв 20% на исключения (см. plan.md, раздел 4).
- Каждая задача получает идентификатор, дату создания и хэш входа и ключа (FREEZE_MANIFEST.md).
- Задачи для основного этапа не используются в пилоте и не подглядываются при калибровке оценщиков.
