# claim.md — 20261014-contract-practical-value

Written 2026-10-14 BEFORE any task material existed, before any executor ran and before any outcome was graded. Follows `20261014-contract-router-precision` (keyword router: 8 % precision, about 3 % recall) and `20261014-contract-router-architectures` (model-based routers not shown better; REPEAT). Those experiments measured whether the router **picks the right card**. This one asks the question the owner actually has: does showing the card change the **result** of the work?

## Zero-Signal Gate

| Field | Value |
|-------|-------|
| **Entity** | the text a contract router puts in front of the model: the one-line hint the hook emits (`H`) and the full draft contract that `/contract` shows (`F`), compared with nothing (`C`) and with a plausible but wrong contract (`W`) |
| **Falsifiable predicate** | on identical tasks with planted, known defects, an executor given `F` finds a larger share of the planted defects than the same executor given `C`, by at least 0.15, without more false findings and at a bounded extra cost |
| **Measurable outcome** | share of planted defects found (blind graded against a rubric written before execution), false findings per task, tokens and wall-clock time of the executor |

## L0: Question Type

- [ ] Descriptive
- [ ] Predictive
- [x] Causal — "what would change in the result if the model were shown this contract?" Randomised assignment of the contract text to otherwise identical executions identifies it.

## Natural Language Statement

> We estimate the mean difference in the share of planted defects found, and in false findings, tokens and time per task, for ten synthetic engineering and research-audit tasks executed by a Sonnet-class subagent, comparing a task prompt with the full contract (`F`), with the hint line only (`H`) and with a wrong contract (`W`) against the same prompt without any contract (`C`), handling executions that produce no usable report as zero found and counting them (treatment-policy strategy).

## Causal layer (identification)

- **DAG:** contract text → what the executor attends to and which checks it runs → defects found / false findings / cost. Task difficulty and defect set are fixed per task and cancel in the paired comparison. Executor sampling noise is not a confounder under randomisation but inflates variance, which is why `C` and `F` are run twice.
- **Consistency:** the treatment is a fixed text, generated by the shipped code (`contracts_lib.hint` / `draft`) from the card; `W` uses the card named in the table below. No hand editing.
- **Positivity / exchangeability:** every task appears in every arm; arm order and slot assignment are randomised with a fixed seed written to this folder before execution.
- **SUTVA:** each execution is a fresh subagent context; executors share no memory.
- **Unmeasured threats:** (1) the executor may read files outside its directory, including the rubric (mitigation: rubrics are stored in a different directory with a neutral name and the executor is told to stay in its task directory; breaches cannot be excluded and are disclosed); (2) graders may infer the arm from wording (mitigation: arm labels removed, outputs shuffled and anonymised; wording leaks are counted in the limits); (3) the tasks and rubrics are written by agents, not by the owner.
- **Intercurrent event:** an execution that ends without a report is scored 0 found, 0 false (treatment-policy). The number of such executions is reported per arm.

## Tasks and arms (frozen)

Ten tasks, one per card type, authored by independent agents who were given only the task type and not the card text, so the planted defects do not mirror the contracts' "Done when" lists. Each task has 5 to 6 planted defects and 2 to 3 decoys (correct things that a careful reviewer should NOT flag). Card for `F`, and the near-miss card for `W`:

| task type (card for F) | wrong card for W |
|---|---|
| statistical-audit | experiment-protocol |
| dataset-leakage-audit | statistical-audit |
| performance-audit | algorithmic-complexity |
| hard-bug-localization | concurrency-audit |
| concurrency-audit | hard-bug-localization |
| reproducible-experiment | reproducible-build |
| causal-claim-audit | statistical-audit |
| api-compat-contract | dependency-modernization |
| test-coverage-synthesis | invariants-verification |
| paper-falsification-audit | systematic-review |

Runs: `C` twice, `F` twice, `H` once, `W` once per task: 60 executions. Executor: `sonnet`, general-purpose subagent, same instruction text in every arm apart from the inserted contract text. Graders: `opus`, one per task, receive the rubric and the five or six anonymised reports of that task in shuffled order.

## Endpoints (frozen)

Primary: `found` = planted defects correctly identified / planted defects. Secondary: false findings per task (decoys flagged as defects plus clearly wrong claims, counted by the grader); executor tokens and wall-clock; whether a report exists.

## Detectability, stated before any outcome

`n` = 10 tasks (paired), 2 runs per task in `C` and `F` and 1 in `H` and `W`. `baseline_or_sigma`: the standard deviation of the paired task-level difference is unknown; 0.20 is assumed, to be replaced by the observed value after the run. `alpha` 0.05 one-sided for the benefit claim (the predicate is directional), `power` 0.8. `MDE` = 2.8 × 0.20 / √10 ≈ **0.18** in `found`. `MCID` = **0.15** (set by the owner's wish to see a clear gain; below it the added text is not worth its complexity). Because MDE is slightly above MCID, a true effect of exactly 0.15 will often not be detected; an observed interval that straddles 0.15 is reported as such.

## Decision rules (frozen)

Let Δ_X = mean over the 10 tasks of (found in arm X − found in `C`), with `C` and `F` averaged over their two runs; interval by paired bootstrap over tasks (10 000 resamples), 95 %.

**Contract content (`F`):**
- **KEEP** if Δ_F ≥ 0.15 and the lower bound of its interval > 0, false findings per task not more than 0.5 higher than in `C`, and mean executor tokens not more than 40 % higher than in `C`.
- **REMOVE** if the upper bound of Δ_F < 0.15 and the point estimate < 0.05 (or negative): the benefit that would justify the added text is excluded.
- **IMPROVE** in every other case (signal not established, or cost or false-finding limits exceeded).

**Harm of a wrong recommendation (`W`):** harmful if mean Δ_W ≤ −0.10; tolerable if the lower bound of Δ_W's interval ≥ −0.10; otherwise unresolved.

**Hint line only (`H`)**, the artefact the hook delivers without `/contract`: reported with the same rules as `F`, read separately.

**The hook as a system:** expected gain per 1 000 prompts = (true hints per 1 000 prompts) × Δ_(H or F) − (false hints per 1 000) × harm of a wrong hint, using the rates measured on the 10 147 real prompts (the shipped router: 15 hints, 2 true, 13 false; so 0.20 true and 1.28 false per 1 000 prompts). Stated even when the contract content is KEEP. If this expected gain is below what one extra line of context per 1 000 prompts costs, the hook verdict is **REMOVE or IMPROVE** whatever the content verdict is.

Nothing is changed in the shipped code or cards by this experiment; a change needs a separate decision and the owner's go.

## What this result does NOT mean

1. It does not measure the owner's real tasks. The tasks are synthetic, authored by agents, with defects planted by design.
2. It does not show that the router finds the right card in real use: that was measured separately and is poor.
3. It does not generalise to other executors, longer tasks or tasks without a checkable answer.
4. With 10 tasks an improvement smaller than about 0.18 can be missed.
5. A model grader is not a human reviewer; the rubric is the only reference.

## Privacy

No private prompts are used: the tasks are synthetic. The report contains aggregate numbers only.

## Amendments made before any execution (2026-10-14)

Two independent reviewers checked the ten task bundles (planted defects reproduce, decoys are correct, no answer hints in the material). All ten were usable; the following were changed before the task set was hashed (`frozen_tasks.sha256`) and before any executor ran:

1. One scoring scheme for every task: found = 1, partially found = 0.5, not found = 0.
2. Task `t06`: two planted items (version pinning, input hashing) are reproducibility hygiene, not causes of the divergence; they are graded and reported but excluded from the primary `found` share, because a longer contract could earn them by generic advice. Decoy `D1` narrowed.
3. Task statements `t04` and `t05` gained the symptom that the reviewers found missing (a test that also fails alone; double charges), so a strict executor can reach every planted item.
4. Clarifications to rubric items of `t02`, `t03`, `t04`, `t07`, `t08`, `t09`, `t10` (see `grading_notes` in each rubric, kept outside the executors' reach).

## Amendment after execution began (2026-10-14), before any grading

- **What happened.** Eleven executions (`x1327`, `xaf11`, `xc7cd`, `xaadd`, `xd9ed`, `x2448`, `x0eff`, `xc3dc`, `x36b8`, `x4640`, `xe0fe`) ended on an API session-limit error (HTTP 429) almost at once. Their only text was the error message (62 characters). The first extraction counted them as finished; that was a bug in the extraction, now fixed by an exclusion list (`excluded_runs.json`).
- **Why it matters.** Seven of the eleven were arm `F`. Scoring them as zero would penalise one arm for an infrastructure failure, not for anything the contract did.
- **Change.** Each of the eleven is re-executed once as a new run: same prompt, same material, new run id, recorded in `plan_SECRET.json` with a `replaces` field. The original directories stay on disk and are excluded from analysis. If a rerun fails again, it is scored by the frozen rule (no usable report = 0 found, 0 false).
- **Not changed.** Arms, tasks, rubrics, endpoints and decision rules.
- **Two executions kept as extracted.** `x63c3` (`t02`, arm `C`) and `x0803` (`t03`, arm `F`) finished, but their final message is a reply to a background-task notification; the report sits in an earlier message. The frozen extraction rule takes the final message, so they are graded as extracted. A sensitivity analysis excludes them.
- **Pending runs.** 20 executions (plan indices 40 to 59) were never launched. They are run under the same design, in waves of at most eight. An earlier draft of this amendment said 21; that was a counting error, corrected here.
- **Extraction fix (2026-10-14).** A finished run whose final assistant record carries `stop_reason: null` and no tool call is now counted as finished. `xd239` had been missed because of this. The rule changes collection only, not the answers, arms, tasks or rubrics.
