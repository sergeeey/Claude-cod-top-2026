# Почему тесты модуля заказов то зелёные, то красные

## Коротко

Нестабильность даёт не один дефект, а четыре, плюс один редкий флейк. Причина у всех в `shop.py`, а не в «капризах pytest». Две вещи случайны: порядок элементов в `set` и `random.randint` для id заказа. Одна вещь зависит от порядка выполнения тестов: глобальный кэш цен. Изменяемый аргумент по умолчанию пока молчит, но ждёт своего часа. Последняя находка: редкий сбой на границе секунды в `test_receipt`.

| # | Где | Что не так | Кого роняет | Как часто |
|---|-----|-----------|-------------|-----------|
| 1 | `shop.py:47-51` | `primary_category` берёт `[0]` из `list(set)`, а порядок строк в set зависит от случайной соли хеша процесса | `test_primary_category` | 18 из 40 прогонов (45%), теория 50% |
| 2 | `shop.py:27-28` | id заказа это `randint(1, 40)`, пять id из сорока совпадают с вероятностью 22,9% | `test_order_ids_unique` | 12 из 40 (30%), теория 22,9% |
| 3 | `shop.py:6`, `11-17` | кэш цен ключуется только по `sku` и игнорирует `catalog`. Тест промо-цены ждёт 15,5 (сумма по обычному каталогу) и проходит только потому, что кэш заполнен другими тестами | `test_promo_order_total` | `test_pricing.py` отдельно: 30 из 30 красный. В полном наборе зелёный |
| 4 | `shop.py:32-34` | `items=[]` как значение по умолчанию: один список на все заказы без `items` | пока никого, держится на порядке тестов | в текущем порядке 0%, при обратном порядке падает |
| 5 | `shop.py:59`, `test_orders.py:43` | `datetime.now()` вызывается дважды, сравнение с точностью до секунды | `test_receipt` | около 1 из 100 000 запусков |

## Условия измерений

Python 3.13.2, pytest 8.4.2. Плагинов, меняющих порядок или параллелящих запуск (random-order, xdist, rerun), в окружении нет (`pip list`). Серии по 30 и 40 прогонов я гнал с `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1`, чтобы исключить сторонние плагины. Один контрольный прогон с плагинами дал то же падение `test_primary_category`.

Сводка 40 прогонов полного набора подряд без изменений:

```
14 прогонов: 8 passed            (35%)
22 прогона:  1 failed, 7 passed
 4 прогона:  2 failed, 6 passed
FAILED test_orders.py::test_primary_category   18
FAILED test_orders.py::test_order_ids_unique   12
```

Ожидание по двум независимым случайным причинам: зелёный прогон 0,5 × 0,771 = 38,6% (наблюдали 35%). Прогон с двумя падениями 0,5 × 0,229 = 11,4% (наблюдали 4 из 40, то есть 10%). Данные согласуются с теорией, других случайных источников в обычном прогоне почти нет.

## Причина 1: порядок элементов в set (`primary_category`)

```python
def categories(self, category_of):
    return list({category_of[sku] for sku, _ in self.items})   # shop.py:47-48
def primary_category(self, category_of):
    return self.categories(category_of)[0]                      # shop.py:50-51
```

Порядок обхода set строк определяется хешами. Хеши строк в Python солятся случайным значением при старте процесса (`PYTHONHASHSEED`). Поэтому два запуска без правок дают разный `[0]`.

Подтверждение:
- Чистый Python, `list({'books','food'})[0]` в 200 процессах с `PYTHONHASHSEED` от 0 до 199: `books` 108 раз, `food` 92 раза.
- Сам тест с зафиксированной солью: seed 0, 3, 4, 5 красный. Seed 1, 2, 6, 7 зелёный. Повторы seed 0 (три раза) и seed 1 (три раза) дают тот же результат. Исход определяется солью и больше ничем.

Это дефект продукта: «основная категория» заказа определяется случайно. Тест `test_orders.py:26-30` проверяет разумное ожидание, которое код не гарантирует.

## Причина 2: id заказа выбирается из 40 значений

```python
def new_order_id():
    return f"ORD-{random.randint(1, 40):03d}"    # shop.py:27-28
```

`test_order_ids_unique` создаёт 5 заказов и требует 5 разных id. Вероятность этого равна 40·39·38·37·36 / 40⁵ = 0,7711, то есть отказ в 22,9% запусков. Симуляция `new_order_id()` на 200 000 попыток дала 22,88%. В 40 прогонах набора упало 12 раз (30%), это в пределах разброса (одно стандартное отклонение при n=40 около 6,6 п.п.).

Тест здесь прав, ошибся код. В реальной работе коллизии начинаются сразу: при 8 заказах вероятность совпадения id 52,7%, при 10 она 70,7%, при 15 она 95,1%. Рядом лежит `next_sequence()`, которым id можно было бы делать уникальными.

## Причина 3: глобальный кэш цен связывает тесты

```python
_PRICE_CACHE = {}                         # shop.py:6
def load_price(sku, catalog):             # shop.py:11-17
    if sku in _PRICE_CACHE:
        return _PRICE_CACHE[sku]          # цена из ЛЮБОГО прошлого каталога
    ...
```

Кэш не знает, из какого каталога пришла цена. Прямая проверка в свежем процессе: `load_price('pen', CATALOG)` вернул 1.5, затем `load_price('pen', PROMO)` тоже вернул 1.5 вместо 1.2.

Теперь тест `test_pricing.py:11-15`:
- Честный итог по промо-каталогу: 2·1,2 + 10,0 = 12,4. Проверено в свежем процессе: `total` = 12.4.
- Тест ждёт 15,5. Это ровно сумма по обычному каталогу 2·1,5 + 12,5 (проверено: 15.5). Ожидаемое значение записано, когда кэш уже был заполнен обычными ценами. Тест закрепляет баг как норму.

В полном наборе он зелёный потому, что `test_orders.py` выполняется раньше и кладёт в кэш нужные цены. Перо (`pen` = 1,5) попадает туда из `test_add_items` (`test_orders.py:20-23`), книга (`book` = 12,5) из `test_receipt` (`test_orders.py:38-43`).

Какой тест что держит (каждый запуск отдельным процессом):

| Что запущено | Результат |
|--------------|-----------|
| `test_add_items` + `test_receipt` + `test_promo_order_total` | 3 passed |
| `test_receipt` + `test_promo_order_total` (пера нет в кэше) | `assert 14.9 == 15.5` |
| `test_add_items` + `test_promo_order_total` (книги нет в кэше) | `assert 13.0 == 15.5` |
| `pytest test_pricing.py`, 30 запусков подряд | 30 из 30 красных |
| `pytest -k promo` | красный |
| `pytest test_pricing.py test_orders.py` (pricing первым, seed=1, чтобы убрать причину 1) | красными стали три теста: `test_promo_order_total` (12.4 вместо 15.5), `test_add_items` (2.4 вместо 3.0), `test_receipt` (10.0 вместо 12.5) |

Связь симметрична: кто первым положил цену в кэш, тот и «победил». Если промо-тест идёт раньше, он ломает обычные тесты заказов: они получают промо-цены при обычном каталоге.

Про ваше «иногда краснеет, если запустить только `test_pricing.py`». У меня отдельный файл красный всегда (30 из 30), случайности в этом тесте нет. Единственный найденный механизм, при котором он зелёный, это кэш, заполненный другими тестами в том же процессе. Поэтому результат зависит от способа запуска: весь набор, один файл, `-k`, один тест из IDE, другой порядок аргументов. Если у вас отдельный файл бывает зелёным, воспроизвести это я не смог. Причину в вашем окружении назвать не берусь [UNKNOWN].

## Причина 4: `items=[]` по умолчанию (мина под порядок тестов)

```python
def __init__(self, customer, items=[]):    # shop.py:32-34
    self.items = items
```

Подтверждено: после `Order('alice').add('pen', 2)` объект `Order('bob').items` равен `[('pen', 2)]`, и это тот же список (`a.items is b.items` → True).

Сейчас тесты проходят по везению. `test_new_order_is_empty` (строка 9) стоит раньше `test_add_items` (строка 20), оба вызывают `Order(name)` без `items`. В обратном порядке (`test_add_items`, потом `test_new_order_is_empty`) второй падает: `assert [('pen', 2)] == []`. Между двумя одинаковыми запусками это ничего не меняет. Но случайный порядок, параллельный запуск или повторный прогон теста в том же процессе включат этот сбой. В работе дефект хуже: товары любого заказа, созданного без `items`, попадают во все остальные такие заказы.

## Причина 5: граница секунды в `test_receipt`

`receipt` берёт `datetime.now()` (`shop.py:59`). Тест через доли миллисекунды вызывает `datetime.now()` ещё раз и сравнивает строки с точностью до секунды (`test_orders.py:43`). Если секунда сменилась между двумя вызовами, тест красный.

- Детерминированное доказательство: с подменёнными часами 12:00:00.999999 → 12:00:01.000000 тест падает на `test_orders.py:43`. В пределах одной секунды проходит.
- Частота: 10 расхождений на 976 262 повторных проверки, то есть 1,0·10⁻⁵ на одно выполнение. Окно между вызовами (`receipt()` плюс второй `now()`): медиана 16,9 мкс, p99 38,4 мкс.

Ваши красные прогоны это не объясняет, но на CI с тысячами запусков этот тест когда-нибудь тоже упадёт.

## Что проверил и отбросил

- Плагины pytest: при выключенных те же падения в тех же долях.
- `test_sequence_increments`: счётчик под локом, в 40 прогонах не падал. Хрупкий только если другой код создаёт `Order` между двумя строками теста.
- Плавающая арифметика в `total`: порядок суммирования зависит от порядка вставки в dict и детерминирован. 3.0, 12.4, 15.5 стабильны.
- Гонка check-then-set в `load_price` и `time.sleep(0.001)`: потоков в тестах нет, на результат не влияют. Это латентный дефект на случай многопоточности.

## Что предлагаю сделать

Порядок важен: сначала кэш, потом правка ожидания. Иначе красный тест покажется новой поломкой.

1. Кэш цен (причина 3). Если кэш нужен только для имитации чтения, достаточно убрать его: `load_price` возвращает `catalog[sku]`. Если за ним настоящее дорогое чтение, кэш должен принадлежать объекту, владеющему каталогом (например, `PriceList` со своим словарём), а не модулю. Ключ `(id(catalog), sku)` не рекомендую: `id` переиспользуется после сборки мусора. Затем исправить ожидание в `test_pricing.py:15` с 15,5 на 12,4. Фикстура, очищающая `_PRICE_CACHE`, без исправления кэша только спрячет проблему. После неё тест станет стабильно красным (12,4 против 15,5), и это покажет, что он записал баг.
2. Id заказа (причина 2). `uuid.uuid4().hex[:12]` либо `f"ORD-{next_sequence():06d}"`, если достаточно уникальности внутри одного процесса. После перезапуска счётчик начнётся заново, для сквозной уникальности нужен uuid или последовательность в хранилище.
3. Основная категория (причина 1). Убрать set из пути, где важен порядок: `list(dict.fromkeys(category_of[sku] for sku, _ in self.items))` сохраняет порядок появления. Нужно решение владельца: «категория первого добавленного товара» или «категория с наибольшей суммой». Текущий тест (книга первой и дороже, яблоки вторыми и их больше по штукам) эти варианты не различает. Надо добавить тест, где яблоко добавлено первым, а книга вторым. Вариант «по числу штук» дал бы `food` и противоречит тесту.
4. Список по умолчанию (причина 4): `def __init__(self, customer, items=None): self.items = [] if items is None else list(items)`.
5. Часы в `receipt` (причина 5): передавать время параметром (`receipt(order, catalog, now=None)`), в тесте подать фиксированный `datetime`. Это самое дешёвое исправление и самое малозначимое по частоте.

Чтобы такое ловилось сразу, а не раз в неделю:
- В CI прогонять набор с несколькими значениями `PYTHONHASHSEED` (я показал, что оно меняет исход) и с перемешиванием порядка тестов. Например, плагин pytest-randomly: он у вас не установлен, я его не проверял.
- Прогонять каждый тестовый файл и каждый тест отдельным процессом. `test_pricing.py` один красный с первого запуска показал бы связь через кэш.
- Не добавлять повторы (rerun) и пометки «нестабильный»: во всех пяти случаях причина находится и исправляется в коде.

# Почему тесты модуля заказов то зелёные, то красные

Окружение: Windows 11, Python 3.13.2, pytest 8.4.2. Плагинов случайного порядка (`pytest-randomly`, `xdist`, `rerunfailures`) нет, так что случайность идёт из самого кода и тестов. Причин пять, они независимы, и все пять объясняются механизмом по коду. Четыре из пяти я подтвердил запусками, а по `test_receipt` у меня только разбор кода.

## Подтверждения

### Полный прогон, 6 раз подряд без правок
Команда: `python -m pytest -q -p no:cacheprovider`. Зелёных прогонов не было.

```
1: FAILED test_order_ids_unique (assert 4 == 5)                1 failed, 7 passed
2: FAILED test_order_ids_unique (assert 3 == 5)                1 failed, 7 passed
3: FAILED test_primary_category, test_order_ids_unique         2 failed, 6 passed
4: FAILED test_primary_category                                1 failed, 7 passed
5: FAILED test_primary_category, test_order_ids_unique         2 failed, 6 passed
6: FAILED test_primary_category                                1 failed, 7 passed
```

Два теста падают независимо друг от друга. Если обе причины в одном прогоне промахнутся, будет зелёное. Это примерно 0,77 × 0,5, около 38 %. Это расчёт из двух вероятностей, а не измерение на большой выборке. Серия из 30 прогонов у меня не успела закончиться, так что точных долей на большой выборке нет.

### Причина 1: ID из 40 значений (`shop.py:28`)
`random.randint(1, 40)`, а тест создаёт 5 заказов и требует 5 разных ID. Это задача о днях рождения.
- Точный расчёт `1 - 40·39·38·37·36 / 40^5` даёт 0,2289.
- Симуляция на 100000 повторов даёт 0,22856.

В проде коллизии между заказами неизбежны уже на нескольких десятках заказов.

### Причина 2: порядок в `set` (`shop.py:47-51`)
`categories()` возвращает `list({...})`, а `primary_category()` берёт `[0]`. Для `book` и `apple` это множество `{"books", "food"}`, и порядок в нём зависит от `PYTHONHASHSEED`. Этот seed по умолчанию случаен в каждом процессе.
- По 20 значениям seed первый элемент: `{'food': 10, 'books': 10}`, то есть 50 на 50.
- Отдельно: seed 0 даёт `['food', 'books']`, seeds 1 и 2 дают `['books', 'food']`.

Тест ждёт `"books"` (`test_orders.py:30`), но в коде нигде не сказано, что такое «основная» категория. Дефект и в коде, и в тесте.

### Причина 3: кэш цен и красный `test_pricing.py`
`load_price()` кэширует цену только по `sku`, каталог в ключ не входит. Кэш живёт весь процесс и между тестами не сбрасывается. `test_promo_order_total` (`test_pricing.py:11-15`) считает заказ по PROMO: 2 × 1.2 + 10.0 = 12.4. Ожидает он 15.5, то есть 2 × 1.5 + 12.5, цены обычного каталога. Тест проходит только если до него в процессе уже закэшировали `pen=1.5` и `book=12.5`.

```
pytest test_pricing.py                  (5 раз)  -> FAILED, assert 12.4 == 15.5   5 из 5
pytest test_pricing.py::test_promo_order_total   -> assert 12.4 == 15.5
pytest test_orders.py::test_add_items test_pricing.py::test_promo_order_total
                                                 -> assert 13.0 == 15.5  (pen из кэша 1.5, book по PROMO 10.0)
pytest (весь набор)                              -> promo проходит: test_orders.py шёл раньше и заполнил кэш
pytest test_pricing.py::test_promo_order_total test_orders.py::test_add_items
                                                 -> FAILED test_add_items: assert 2.4 == 3.0  (pen по PROMO 1.2)
```

- **Ложно зелёный тест.** В полном наборе тест зелёный не потому, что скидка считается верно, а потому, что кэш подкладывает цены обычного каталога. Реально скидка по PROMO не проверяется вообще.
- **Баг и в коде.** `Order.total()` вернёт неверные цены, если до этого в процессе считали по другому каталогу.
- **«Иногда» не воспроизвелось.** У меня `test_pricing.py` отдельно падал 5 из 5, а не «иногда». Результат зависит от того, что запускалось в том же процессе раньше.

### Причина 4: `items=[]` (`shop.py:32-34`)
Все заказы, созданные без явного списка, делят один и тот же список. `test_new_order_is_empty` и `test_add_items` оба вызывают `Order(...)` без списка. В файловом порядке пустота проверяется первой и проходит. Если поменять порядок, получается красное:

```
pytest test_orders.py::test_add_items test_orders.py::test_new_order_is_empty
  -> FAILED test_new_order_is_empty: assert [('pen', 2)] == []
```

В остальных тестах авторы везде вручную передают `[]`, то есть проблему обходили в тестах, а не чинили в коде. Любая смена порядка (`-k`, `--lf`, запуск одного теста, `pytest-randomly`) её выдаст. В проде это утечка товаров между покупателями.

### Причина 5: `test_receipt` и граница секунды
`receipt()` берёт `now()` с точностью до секунды (`shop.py:59`), тест берёт второй `now()` позже и сравнивает на равенство (`test_orders.py:43`). Между вызовами идёт `total()` с `time.sleep(0.001)` при пустом кэше (`shop.py:14`). Если между вызовами меняется секунда, тест падает. В 6 полных прогонах он не упал, так что падение я не видел, и частоту не измерял. Оценка по механизму: доли процента.

## Что подтверждено и как

Python 3.13.2, pytest 8.4.2. Плагинов случайного порядка или параллельного запуска нет (`pip list`). Конфигурации pytest в папке нет.

### 1. `primary_category` зависит от хеш-сида (`shop.py:47-51`)

`categories()` возвращает `list({...})`, то есть порядок множества строк. Для строк он определяется `PYTHONHASHSEED`, который Python выбирает случайно при каждом запуске. `primary_category()` берёт `[0]` этого списка.

Проверка: `diag_flaky.py`, раздел A, сиды 0-19. Для `book` + `apple` получилось 10 раз `books` и 10 раз `food`. Результат полностью определяется сидом: при `PYTHONHASHSEED=1` всегда `books`, при `0` всегда `food`.

В продакшене это тоже дефект: основная категория заказа меняется от перезапуска к перезапуску. Что считать основной категорией, код не определяет. Тест неявно предполагает «первая добавленная» (`book` добавлен раньше `apple`). Тот же ответ дают «по сумме» (12,5 против 1,2) и «по алфавиту». Выбор правила за вами, его нужно записать в код и в тест.

### 2. Коллизии ID заказов (`shop.py:27-28`)

В тесте создаётся 5 заказов, ID берутся из 40 значений. Вероятность совпадения: 1 − (40·39·38·37·36)/40⁵ = 0,2289. Монте-Карло на реальном `Order()`, 200 000 попыток: 45 749 коллизий, 0,2287. Прямой вызов самого теста 5000 раз в одном процессе: 1082 падения, 0,216. Это примерно на 2 стандартных отклонения ниже теории, а на 200 000 попытках расхождения нет.

Это проблема не только теста. В реальной системе два заказа с одним ID при тысячах заказов случаются почти наверняка.

### 3. Общий кэш цен (`shop.py:6, 11-17`)

`_PRICE_CACHE` живёт на уровне модуля, ключ только `sku`, каталог в ключ не входит. Первый вызов `load_price("pen", X)` навсегда задаёт цену `pen` для всех каталогов до конца процесса.

# Почему тесты модуля заказов то зелёные, то красные

## Коротко

Многопоточность тут ни при чём: тесты однопоточные. Причин пять, и все они в `shop.py` и в самих тестах. Две из них (порядок элементов в множестве и случайные номера заказов) дают разный результат от запуска к запуску. Остальные три (общий кэш цен, общий список по умолчанию, сравнение времени) зависят от порядка тестов или от случая.

Поправка к описанию: `test_pricing.py` в одиночку падает не «иногда», а каждый раз. `test_promo_order_total` проходит только после `test_orders.py`, потому что тот заполняет кэш обычными ценами.

Исправления сделаны в копии `fixed_copy/`. Исходные файлы проекта не менялись.

## Что нашёл

Номера строк относятся к исходному `shop.py`.

**1. Кэш цен привязан только к артикулу (строки 6, 11-17).** `_PRICE_CACHE[sku]` не учитывает, из какого каталога взята цена. Первый вызов определяет цену для всех следующих.
- Один `test_promo_order_total` в 5 отдельных процессах: 5 из 5 падений, `assert 12.4 == 15.5`.
- Ожидание 15.5 равно сумме по обычным ценам (1.5·2 + 12.5). По акционным ценам получается 1.2·2 + 10.0 = 12.4. Тест проходил только на отравлённом кэше, то есть закрепляет ошибку.
- Связь действует в обе стороны. Если `test_pricing.py` идёт раньше `test_orders.py`, то на 10 значениях `PYTHONHASHSEED` падают ещё `test_add_items` (2.4 вместо 3.0) и `test_receipt` (10.0 вместо 12.5), 10 из 10.

**2. Порядок элементов множества зависит от `PYTHONHASHSEED` (строка 48).** `categories()` возвращает `list(set)`, а `primary_category` берёт первый элемент.
- Перебор `PYTHONHASHSEED` 0-49: неверный результат («food») на 24 из 50 значений.
- Полный набор, 40 запусков: `test_primary_category` упал 23 раза (57%).

**3. Номера заказов случайные, от 1 до 40 (строки 27-28).** Для 5 заказов вероятность совпадения равна 1 − 40·39·38·37·36/40⁵ = 22,89%.
- 20000 попыток с `random.seed(12345)`: 4577 совпадений (22,88%).
- `test_order_ids_unique` в 40 запусках упал 7 раз (17,5%; ожидание около 9, расхождение в пределах шума).
- Это не только проблема теста. Среди 41 заказа совпадения неизбежны, в тесте их оказалось 15. Из 400 заказов, созданных 8 потоками, дублей 360.

**4. Изменяемое значение по умолчанию `items=[]` (строка 32).** Все заказы без явного списка делят один список.
- `test_add_items` перед `test_new_order_is_empty` роняет второй: `assert [('pen', 2)] == []`.
- В штатном порядке это скрыто: пустой тест в файле стоит раньше.
- В 8 потоках у каждого из 8 заказов по 800 позиций вместо 100. На практике это утечка позиций между покупателями.

**5. Сравнение времени с точностью до секунды (`test_orders.py`, строка 43).** `receipt` и тест вызывают `datetime.now()` по отдельности. Если между вызовами меняется секунда, равенство нарушается.

## Доказательства по причинам

**Причина 1, `new_order_id`.**
- Для пяти заказов из 40 номеров вероятность дубликата `1 − 40·39·38·37·36/40^5 = 0.2289`.
- Монте-Карло на `new_order_id()`: 45601 дубликатов из 200000 = 22.8%.
- Через `Order(...)`, как в тесте: 4534 из 20000 = 22.7%. В pytest: 67 из 300 = 22.3%.
- На 8 заказах вероятность дубликата 52.7%, на 20 заказах 99.7% (`evidence/probes_before.txt`).
- Это дефект и для продакшена, не только для теста.

**Причина 2, порядок категорий.**
- Взяты 100 значений `PYTHONHASHSEED` (0..99), каждое запущено дважды в отдельных процессах. Для каждого сида ответ повторился, то есть он детерминирован.
- `"food"` вместо `"books"` получено для 44 сидов из 100 (сиды 0, 3, 4, 5, 8, 15, …).
- Значит, причина именно хеш-сид: не время и не потоки.

**Причина 3, кэш.**
- `load_price('pen', CATALOG)` вернул 1.5, затем `load_price('pen', PROMO)` вернул 1.5 вместо 1.2.
- При кэше, оставленном `test_orders.py`, `total(PROMO)` даёт 15.5.
- После промо-расчёта обычная цена за 2 ручки даёт 2.4 вместо 3.0. В случайном порядке это ломает `receipt` (10.0 вместо 12.5) и `add_items`.
- Для продакшена это значит, что цены в процессе не обновляются никогда.

**Причина 4, изменяемый аргумент по умолчанию.**
- После `a = Order("a"); a.add("pen")` у `b = Order("b")` оказывается `b.items == [('pen', 1)]`, `a.items is b.items` равно `True`.
- В обычном порядке не видно: `test_new_order_is_empty` стоит первым, а `test_add_items` пачкает общий список позже.
- `ruff` на исходнике ловит сам (`B006`, `shop.py:32:40`).
- Для продакшена это утечка позиций между заказами разных клиентов.

# Почему тесты модуля заказов то зелёные, то красные

Версии: pytest 8.4.2, Python 3.13.2. Плагинов случайного порядка и xdist нет, порядок тестов фиксированный. Случайность даёт сам код: хеш-сид строк и модуль `random`.

## Итог

Полный прогон на исходном коде падал в 62% запусков (311 из 500). Причин в коде четыре, одна редкая в тесте и одна ошибка в ожидаемом значении.

| № | Причина | Место в исходнике | Проявление | Частота |
|---|---|---|---|---|
| 1 | `set` строк в `categories()`: порядок зависит от `PYTHONHASHSEED`, а он новый при каждом запуске | `shop.py:48` | `test_primary_category` | 46% (92/200), 54% (163/300), 55% (55/100) |
| 2 | id заказа из `random.randint(1, 40)`, всего 40 значений | `shop.py:28` | `test_order_ids_unique` | 23,5% (47/200), 20,3% (61/300); расчёт 22,9%, симуляция 23,0% |

Причины 1 и 2 независимы. Ожидаемая доля красных запусков: 1 − 0,5·0,771 = 61,5%. Измерено 62,2%.

## test_pricing.py отдельно

Вы пишете, что он краснеет «иногда». У меня он краснеет всегда: 100 из 100 запусков, ошибка `assert 12.4 == 15.5`. Как у вас он оказывался зелёным при отдельном запуске, я не воспроизвёл. Это [UNKNOWN].

В общем прогоне он зелёный потому, что `test_add_items` кладёт в кэш `pen=1.5`, а `test_receipt` кладёт `book=12.5`. Акционный заказ тогда получает обычные цены. Явные порядки на исходнике при `PYTHONHASHSEED=1` (`_orig_snapshot/ordering_demos.txt`):

- `test_add_items`, `test_receipt`, `test_promo_order_total`: 3 passed.
- `test_add_items`, `test_promo_order_total`: красный, `13.0 == 15.5`.
- `test_promo_order_total`, затем `test_add_items`: оба красные (`12.4 == 15.5` и `2.4 == 3.0`).
- `test_add_items`, затем `test_new_order_is_empty`: красный, `[('pen', 2)] == []` (причина 4).

Это не только проблема тестов. В рабочем коде заказ по акционному каталогу вернёт обычные цены, если артикул уже загружали из другого каталога.

## Альтернативные объяснения

1. **Гонки между потоками.** Отвергнуто. Во всех 8 тестах жив один поток (`threading.active_count()` = 1). Окно гонки в `load_price` в коде есть, но 16 потоков дали 1 чтение каталога и один результат. `next_sequence` под 16×1000 вызовов выдала 16000 уникальных значений.
2. **Плагины pytest.** Отвергнуто. С `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` (300 запусков) красных 64,7%, с плагинами (200 запусков) 58,5%. Разница в пределах шума, набор падающих тестов тот же.
3. **Округление float.** Отвергнуто. `2*1.5 == 3.0`, `1.2*2+10.0 == 12.4` и `2*1.5+12.5 == 15.5` истинны.
4. **Время в `test_receipt`.** Не отвергнуто, это реальная, но редкая причина. Окно между двумя `now()` в среднем 11,9 мкс, расчётная частота 1,2e-5. В цикле на 300 000 вызовов исходное сравнение разошлось 2 раза (ожидалось около 3,6). В 500 запусках набора `test_receipt` не падал ни разу. Объяснить 62% красных он не может. Подменой часов воспроизведено: исходное условие даёт False, новое с вилкой «до/после» даёт True.
