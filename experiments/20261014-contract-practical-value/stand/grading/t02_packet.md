# Можно ли верить ROC AUC 0.817

## Вывод

Цифре верить нельзя. Основную часть значения даёт утечка целевой переменной в признак `user_rate`. Ещё завышают результат повторы строк между обучающей и тестовой частями и случайное разбиение вместо разбиения по времени. После исправлений оценка падает до 0.62–0.66 для текущего kNN и до 0.69–0.70 для простой логистической регрессии. Для запуска ориентируйтесь на AUC около 0.65 (интервал примерно 0.60–0.69). Потолок на этих данных около 0.80.

Данные в папке синтетические (`data.py`), реального журнала магазина у меня нет. Цифры относятся к этому генератору, на реальных данных их нужно пересчитать тем же способом.

## Что найдено и чем подтверждено

`python train.py` воспроизводит `k=41 test ROC AUC=0.817 accuracy=0.756`, как в README.

### 1. Утечка цели в `user_rate` (главная причина)

В `train.py:14-19, 77` доля покупок пользователя считается по всей таблице до разбиения и включает метку самой строки. В бою метки текущей сессии ещё нет.

- Без `user_rate` в итоговой модели из 5 признаков AUC падает с 0.817 до 0.692 (-0.125, `audit2_output.txt`).
- Один `user_rate` даёт на тесте AUC 0.776. Если считать его без собственной строки, получается 0.686.
- Контроль на случайных метках: ответ заменён подбрасыванием монеты, не связанной ни с чем. Исходный пайплайн даёт AUC 0.647, 0.642, 0.664, 0.641 вместо 0.5. Исправленный даёт 0.525, 0.485, 0.471, 0.509.
- Одно это исправление (метки только из обучающей части, для обучающих строк без своей метки) даёт 0.740 вместо 0.820. Это среднее по 8 разбиениям.

### 2. Повторы строк

`data.py:57-58` добавляет 396 дублей (11 % таблицы, одинаковые `user_id` и `day`). `train.py:89` удаляет дубли только в обучающей части и только после разбиения. У 135 из 892 тестовых строк (15 %) в обучении есть точная копия. На них AUC 0.919, на остальных 0.798. Дедупликация до разбиения даёт -0.010.

### 3. Разбиение не соответствует использованию

В `train.py:83-86` строки разбиваются случайно. Все 300 пользователей есть и в обучении, и в тесте, и модель видит их будущие сессии. README описывает другое: переобучение раз в неделю и прогноз на следующие недели, поэтому оценивать надо по времени.

Акция действовала до дня 120 (`data.py:12, 45`). Конверсия со скидкой: 0.613 при акции и 0.430 после. Без скидки 0.388 в обоих периодах. На тестовых строках до дня 120 AUC 0.844, после – 0.768. Эффект скидки после акции почти исчезает, а модель считает её значимым признаком.

### 4. Дефекты, не повлиявшие на число

Это стандартизация и ранжирование признаков по всем данным (`train.py:80-81`) и выбор `n_feat` и `k` по тесту (`train.py:91-98`). Их исправление не меняет среднее по 8 разбиениям (0.820 до и после). Чинить нужно, но 0.817 они не объясняют.

### 5. Потолок

Реплика генератора с истинной вероятностью покупки (она знает скрытые вкус и настроение пользователя) даёт AUC 0.814 на тех же тестовых строках. Заявленные 0.817 равны уровню оракула, а реальная модель до него дотянуть не может. Это независимый признак завышения. Для периода после дня 120 потолок 0.796.

## Какое качество ждать

Оценка по времени: обучение на прошлом, прогноз на следующие дни. Предобработка и подбор параметров идут только по обучающей части, а доля покупок строится только по прошлым сессиям.

| Вариант | AUC |
|---|---|
| Исходный пайплайн, 8 разбиений | 0.820 (sd 0.021) |
| Все механические утечки исправлены, случайное разбиение | 0.710 |
| То же без `user_rate`, случайное разбиение | 0.665 |
| То же, разбиение по пользователям | 0.649 |
| kNN, одно разбиение по времени (обучение до дня 135) | 0.620, ДИ 95 % [0.578; 0.665] |
| kNN, недельное переобучение, 11 недель | 0.656 (после акции 0.635, ДИ [0.599; 0.677]) |
| Логистическая регрессия, недельное переобучение | 0.689 (после акции 0.680–0.690, ДИ [0.653; 0.728]) |
| Логистическая регрессия, одно разбиение по времени | 0.701, ДИ [0.662; 0.741] |
| Только прошлая доля покупок | 0.643 (после акции 0.651) |

Доверительные интервалы получены бутстрепом по пользователям. Шум оценки на таком объёме около ±0.04. Для самого значения 0.817 интервал [0.786; 0.845].

Проверка стенда:

## Что нашёл

### 1. Утечка таргета через `user_rate` (главная причина)
- `train.py:14-19` и `train.py:77`: `user_rate` считается как среднее `y` пользователя по всей таблице до разбиения. В него входят метки тестовых строк и метка самой строки.

- В боевом режиме метка текущей сессии неизвестна, а будущих сессий нет вообще. Для признака нужны только прошлые метки, либо метки обучающей части с исключением самой строки.

### 2. Гиперпараметры выбраны по тесту
- `train.py:91-98`: сетка из 4 значений числа признаков и 6 значений `k` даёт 24 конфигурации. Лучшая по AUC на тесте выбирается и тут же отчитывается как результат (`train.py:100-106`).

### 3. Предобработка и отбор признаков видят тест
- `train.py:80-81`: стандартизация (`standardize`) и ранжирование признаков по корреляции с `y` (`rank_features`) считаются по всей выборке, включая тест. Метки тестовых строк участвуют в выборе 5 признаков.

### 4. Дубликаты строк попадают в тест
- `data.py:57-58`: около 1/8 строк журнала продублировано, а `train.py:89` убирает дубли только в обучении.
- Проверка: у **15.1 %** тестовых строк есть точная копия в обучении, и kNN при `k=1` такие строки просто «вспоминает». На итоговой цифре эффект небольшой: 0.817 → 0.814 при дедупликации до разбиения.

### 5. Случайное разбиение не соответствует сценарию применения
