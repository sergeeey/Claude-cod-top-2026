# Отчёт: почему results.json не повторяется и что изменено

Исходный скрипт сохранён без изменений в `original/run_experiment.py`.

## Коротко

Зерно в скрипте зафиксировано, но управляет только одним из двух генераторов случайных чисел. Подвыборка 80% строк делается через стандартный `random.shuffle` без `seed`, поэтому при каждом запуске берётся другой набор строк. Это главная причина. Есть ещё две: порядок файлов зависит от файловой системы, порядок групп зависит от `PYTHONHASHSEED`. Этим объясняются и ваши расхождения между повторными запусками, и числа коллеги.

После исправления два независимых запуска (разные каталоги, разные venv, разные `PYTHONHASHSEED`) дали побайтово одинаковый `results.json`. На другом компьютере и другой ОС я не проверял, только на этой машине (см. «Что не проверено»).

## Базовая линия (измерена до правок)

Оригинальный скрипт, 6 запусков, данные те же. Файлы: `evidence/orig_*.txt|json`.

| запуск | PYTHONHASHSEED | effect | n (control / placebo / treatment) |
|---|---|---|---|
| A1 | 0 | 0.7599 | 20 / 30 / 22 |
| A2 | 0 | 1.0888 | 17 / 30 / 25 |
| A3 | 0 | 0.8412 | 19 / 27 / 26 |
| H1 | 1 | 0.4890 | 20 / 24 / 28 |
| H2 | 2 | 1.0756 | 21 / 29 / 22 |
| H3 | 3 | 0.5120 | 21 / 29 / 22 |

Эффект гуляет от 0.489 до 1.089. При одинаковом `PYTHONHASHSEED=0` три запуска дают 0.76, 1.09, 0.84, значит дело не только в хэшах. Размеры групп `n` тоже меняются: выборка каждый раз другая.

## Что нашёл

Каждую причину проверил отдельно: правил копию исходного скрипта по одному пункту (`original/v1.py`, `v2.py`, `v3.py`, вывод в `evidence/diag.txt`).

1. **Незасеянный `random.shuffle` (главная причина).** В `subsample` (строки 33-37 оригинала) стоит `random.shuffle(rows)`, а `SEED` передаётся только в `np.random.default_rng(SEED)` (строка 47). Стандартный `random` стартует от системной энтропии. Подтверждение: с `random.seed(SEED)` (v1) `effect = 0.9903` при всех четырёх `PYTHONHASHSEED`, `n` = 23 / 27 / 22 везде.
2. **Порядок групп из `set` (меняются CI, средние нет).** Строка 48: `groups = {g for g, _ in rows}`, затем `for g in groups` с одним общим `rng`. Порядок в `set` зависит от `PYTHONHASHSEED`, поэтому поток `rng` расходуется на группы в другом порядке. В v1: `control.ci_low` 9.6144 при `PYTHONHASHSEED` 0 и 3, но 9.6279 при 1 и 2; `treatment.ci_high` 11.9268 против 11.9703. Средние и `effect` одинаковы. С `sorted(groups)` (v2) CI совпадают при всех четырёх значениях.
3. **Порядок `glob.glob` не гарантирован.** Строка 24, сортировки нет. На другой ФС или ОС порядок строк до `shuffle` другой, и подвыборка другая. Это я проверил только имитацией: в v3 (v2 + файлы в обратном порядке) `effect = 0.5414` против `0.9903`, `n` = 21 / 28 / 23 против 23 / 27 / 22. Реальный порядок на машине коллеги я не видел.
4. **Шум в самом файле результата.** В `results.json` пишутся `run_at` и абсолютный `data_dir`, поэтому `diff` или хэш файлов не совпадут на любой машине даже при верных числах.
5. **numpy не закреплён.** В `requirements.txt` было просто `numpy`. Поток PCG64 на практике стабилен, но между версиями формально не гарантирован. Версию окружения коллеги я не знаю.

Исключено: в CSV нет BOM, окончания строк LF, группы записаны единообразно (control 26, placebo 35, treatment 29, всего 90 строк).

## Что изменено

- `run_experiment.py`: вся случайность идёт из одного `numpy.random.SeedSequence(20240501)` с независимыми дочерними потоками. Один поток для подвыборки (`rng.choice` без возвращения), по одному на группу в фиксированном порядке `control, placebo, treatment`. Файлы читаются отсортированными. Стандартный `random` не используется. Зерно прежнее, перебора зёрен не было.
- `results.json` без времени и путей, ключи отсортированы, LF, добавлены sha256 файлов данных. Среда, версии, время, хэш скрипта и хэш результата пишутся в отдельный `manifest.json`.
- `requirements.txt`: `numpy==2.3.4`.
- `run.sh`: одной командой чистый venv, зависимости, запуск.
- `compare.py`: сравнение двух `results.json` с допуском в аргументе; допуски записаны в докстринг до первого сравнения.
- `README.md`: добавлен раздел про воспроизводимый запуск.

Числа нового скрипта **не равны** числам старого. Оригинал каждый раз брал новую подвыборку, у него нет «правильного» значения для сравнения. Новый `effect` — результат одной фиксированной подвыборки.

С `PYTHONHASHSEED=0` три запуска дали 0.7994, 0.5200, 0.6762. Значит, хеш-рандомизация строк разброс не объясняет: числа разные и при фиксированном хеш-зерне. Разброс effect 0.52–0.83 — это выборка разных 80% строк.

## Что нашёл (по убыванию вклада)
1. **Не засеянный `random.shuffle`** (функция `subsample`, исходная строка `random.shuffle(rows)`). Модуль `random` и `numpy.random.default_rng` имеют независимые состояния, а `SEED` использовался только для второго. Из-за этого результат не повторяется даже на одной машине.
   Подтверждение: если в исходный скрипт добавить только `random.seed(20240501)` (через обёртку, файл не менял), effect при любом `PYTHONHASHSEED` одинаков, 0.9903 в 4 запусках из 4. Без этой строки он каждый раз другой.
2. **Порядок файлов из `glob.glob` не определён** (`load_rows`). Он зависит от файловой системы и ОС. Он задаёт порядок строк до перемешивания, а значит, и то, какие строки попадут в 80%, даже при одном зерне.
   Подтверждение: исходный скрипт с `random.seed(...)`, `PYTHONHASHSEED=0` и обратным порядком файлов даёт effect 0.5414 вместо 0.9903. Даже после исправления п. 1 у коллеги числа были бы другими, если его `glob` вернул файлы в другом порядке.
3. **Обход множества групп** (`groups = {g for g, _ in rows}`, затем `for g in groups`). Порядок элементов множества строк зависит от `PYTHONHASHSEED`, который по умолчанию случаен на каждый запуск. Один общий `rng` расходовался по группам по очереди, поэтому поток случайных чисел доставался группам в разном порядке.
   Подтверждение: при засеянном `random` и разных `PYTHONHASHSEED` effect и средние не меняются, а границы интервалов меняются. Для `treatment` ci_low: 10.6563 (seed 0), 10.6254 (seed 1), 10.6254 (seed 2), 10.6517 (seed 3). Effect не пострадал, потому что считается по средним.
4. **В `results.json` лежали поля, которые меняются всегда.** Это `run_at` (время) и `data_dir` (абсолютный путь, разный на разных машинах). Побайтно сравнить результаты двух машин было невозможно по построению.
5. **numpy не закреплён** (`requirements.txt` содержал просто `numpy`). Numpy не гарантирует тот же поток чисел от `integers` и `permutation` между версиями. Я проверял только numpy 2.3.4 и Python 3.13.2, так что остальное — риск, а не наблюдение.

## Что изменил
Исходный скрипт сохранён как `baseline/run_experiment.py.orig`.
- Выборка 80% теперь идёт через `rng.permutation`. Модуль `random` не используется.
- Все потоки выводятся из одного `SEED` через `np.random.SeedSequence(SEED).spawn(...)`: один поток на разбиение и по одному на каждую группу.

# Отчёт: почему results.json не повторяется и что изменено

## Коротко

1. **Главная причина.** `SEED` не управляет перемешиванием строк. Зерно получает только `np.random.default_rng` (строка 46 исходника), а подвыбор 80% строк делает `random.shuffle` (строка 33) из стандартного модуля без зерна. Каждый запуск берёт другие 72 строки из 90.
2. **Ещё три источника расхождений.** Они сработали бы даже при зерне на `random`:
   - порядок обхода `set` групп (строки 49 и 52);
   - порядок файлов из `glob.glob` (строка 24);
   - содержимое самого `results.json`: `run_at`, абсолютный `data_dir`, CRLF на Windows (строки 67, 68, 71).
3. **numpy не закреплён.** Документация numpy не гарантирует поток `Generator` между версиями.
4. **Всё исправлено.** Новый `results.json` побайтно одинаков при любом `PYTHONHASHSEED`, при другом порядке файлов и при повторе запуска.
5. **Побочная находка, нужно ваше решение.** Сам случайный подвыбор 80% двигает эффект сильнее, чем любая из найденных ошибок (см. последний раздел).

## Что найдено и чем подтверждено

Вспомогательные скрипты лежат в `_diag/`. `_diag/driver.py` запускает исходную `main()` (копия в `_diag/run_experiment_original.py`) при заданных возмущениях.

### 1. `random.shuffle` без зерна [VERIFIED]

Команда, три раза подряд при одинаковом `PYTHONHASHSEED`: `PYTHONHASHSEED=0 python _diag/driver.py 0 glob`

Меняются `n`, средние и эффект. Этого одного хватает, чтобы ваши повторные запуски не совпадали и чтобы у коллеги вышли другие числа.

### 2. Порядок групп из `set` зависит от `PYTHONHASHSEED` [VERIFIED]

Общий `rng` расходуется по группам по очереди, а порядок групп во множестве меняется от запуска к запуску. Проверка: `random.seed(SEED)` добавлен, порядок файлов фиксирован, меняется только хеш-зерно: `for h in 1 2 3 4 5 6; do PYTHONHASHSEED=$h python _diag/driver.py 1 sorted; done`

Средние, `n` и эффект одинаковы (effect 0.9903, 23 / 27 / 22). Интервал группы `control` зависит только от её места в обходе:

| PYTHONHASHSEED | порядок обхода | ci control |
|---|---|---|
| 3, 5 | control, placebo, treatment | [9.6144, 10.9006] |
| 1, 2 | treatment, control, placebo | [9.6279, 10.9351] |
| 4, 6 | treatment, placebo, control и placebo, treatment, control | [9.5795, 10.8936] |

### 3. Порядок файлов из `glob.glob` [VERIFIED эффект; причина у коллеги INFERRED]

Подвыбор зависит от порядка строк, а он от порядка файлов. Проверка с `random.seed(SEED)`: `python _diag/driver.py 1 sorted` и `... 1 reversed`.

| порядок файлов | effect | n |
|---|---|---|
| a, b, c | 0.9903 | 23 / 27 / 22 |
| c, b, a | 0.5414 | 21 / 28 / 23 |

На этой машине `glob` вернул `site_a, site_b, site_c`, здесь причина не проявляется. Строка документации `glob.glob` в Python 3.13.2 порядок не обещает [DOCS]. Какой порядок был у коллеги, я проверить не могу [UNKNOWN].

### 4. Содержимое `results.json` [VERIFIED по коду; CRLF проверен мутацией]

- Строка 68 исходника пишет `run_at`, строка 67 пишет абсолютный `data_dir`. Эти поля различаются при каждом запуске и на каждой машине.
- Строка 71 открывает файл без `newline="\n"`. На Windows получается CRLF, на Linux LF. В копии нового кода без `newline="\n"` в `results.json` оказалось 33 байта `\r`.

### 5. numpy не закреплён [DOCS]

Раньше в `requirements.txt` стояло просто `numpy`. В `numpy.random.Generator.__doc__` установленной версии написано: «No Compatibility Guarantee ... the bit stream may change». На второй версии numpy я это не проверял [UNKNOWN].

Данные: три CSV с LF, без BOM и пропусков, три группы по 26 / 35 / 29 строк. Платформенная независимость арифметики numpy и округления — вывод [INFERRED], на другой платформе не запускался.
