# Отчёт: куда уходит время в service.py и почему bench.py врёт

## Коротко

1. Время уходит в четыре места `service.py`, не связанные с бизнес-логикой:
   - **Файл алиасов читается заново на каждый запрос** (строка 61, `handle_request`).
   - **На каждый запрос компилируется регулярка из 400 альтернатив** (строка 62). Её `fullmatch` на строке 72 равносилен `token in aliases`.
   - **`STOP_WORDS` — список из 400 слов** (строка 8, `rng.sample`), поэтому `token in STOP_WORDS` на строке 68 перебирает до 400 элементов на каждый токен.
   - **`encode_batch` склеивает bytes через `+=`** (строки 101–104), а это квадратичное копирование.
2. После правки этих четырёх мест медиана упала с 1.48 с до 0.060 с, то есть в 24.6 раза (21 раунд с чередованием вариантов, шум A/A 4.6%). Вывод побайтово тот же: sha256-префикс `ec10449a12b1638b` до и после.
3. `bench.py` по конструкции нельзя использовать для сравнения вариантов.
   - Реальный `dedupe gain` в нём равен нулю: все 1200 текстов уникальны (`len({r['text'] for r in reqs}) == 1200`), поэтому `dedupe=True` ничего не пропускает.
   - Показанные +9.3%, −6.3%, −37.1% — это дрейф нагрузки и порядок запуска.

## Почему bench.py показывает странные цифры

Три прогона подряд на исходном коде:

| прогон | plain | dedupe | «gain» |
|---|---|---|---|
| 1 | 1.928 с | 1.750 с | +9.3% |
| 2 | 1.537 с | 1.635 с | −6.3% |
| 3 | 1.593 с | 2.183 с | −37.1% |

Причины:
- Два раздельных прогона подряд (`run(False)`, затем `run(True)`, строки 20–21): второй измеряется в другом состоянии системы.
- Генерация данных входит в таймер (`make_requests` внутри `run`, строка 9). Она занимает около 0.047 с.
- Используется `time.time()` вместо `perf_counter()`.
- Замер один, без повторов. Сама исходная версия шумит: в интерливленном замере 1.35–2.37 с при медиане 1.48 с.

## Где реально уходит время

Профиль `cProfile` исходного кода, первые 300 запросов (0.543 с):
- Сборка паттерна `"|".join(re.escape(...))` на строке 62: 0.220 с, около 40%.
- `load_aliases`, то есть перечитывание файла на каждый запрос: 0.169 с, около 31%.
- `fullmatch`: 0.037 с, около 7%.

Список `STOP_WORDS` и `bytes +=` профиль не показывает. Первый растворён в собственном времени `handle_request`, второй вынесен за профилируемые 300 запросов. Поэтому `encode_batch` я померил отдельно: на 1200 результатов 0.28–0.37 с у исходной версии против 0.03 с у `b"".join` (3 измерения).

Вклад каждой правки отдельно (`ablation.py`, 12 раундов, порядок вариантов вращается; каждая правка применяется к исходному коду сама по себе):

| вариант | медиана | ускорение |
|---|---|---|
| исходный код | 1.736 с | 1.00x |
| только `b"".join` | 1.529 с | 1.14x |
| только `STOP_WORDS` как frozenset | 1.338 с | 1.30x |
| только вынос `load_aliases()` из цикла (регулярка ещё компилируется) | 1.428 с | 1.22x |
| вынос aliases и замена регулярки на `in aliases` | 0.738 с | 2.35x |
| все правки вместе | 0.080 с | 21.8x |
| итоговый `service.py` | 0.069 с | 25.0x |

Правки складываются по абсолютному времени (1.74 − 1.0 − 0.4 − 0.2 ≈ 0.1 с остаётся). Поэтому по отдельности каждая даёт мало, а вместе они убирают почти всё время. Чинить нужно все четыре.

## Замер до и после

Команда: `python bench_ab.py 21`. Результат сохранён в `bench_ab_result.txt`, сырые данные в `bench_ab_raw.csv`. В каждом раунде варианты A и B идут подряд с чередованием порядка, данные строятся один раз вне таймера, таймер `perf_counter`, прогревочный запуск отбрасывается. Затем тем же способом гоняется A/A-контроль.

```
A baseline  median 1.483s  min 1.351  max 2.367
B optimized median 0.060s  min 0.054  max 0.109
speedup (median A / median B): 24.61x   time saved: 95.9%
paired per-round ratio A/B: median 25.43x, min 13.64x
A/A control: apparent effect +4.6% (noise floor)
```

Эффект на порядок больше шума, худший парный раунд даёт 13.6x. Ранний 15-раундовый замер показал 3.35x, но он был сделан до правки `STOP_WORDS`, то есть это промежуточное состояние.

**Про цель.** Числовую цель я до правок не фиксировал: сначала снял профиль и сразу применил правки. Поэтому 24.6x — это измеренный результат, а не выполненная цель. Для будущих замеров порог лучше записывать до правки, например «медиана на 1200 запросах ≤ 0.3 с при A/A-шуме ≤ 10%».

## Оговорки

- **Одно поведенческое отличие.** Раньше `aliases.tsv` читался на каждый запрос, и при изменении файла посреди пачки поздние запросы видели новые алиасы. Теперь файл читается один раз на пачку. Тестом это не покрыто. Если алиасы обновляются на лету, нужен кэш с проверкой mtime.
- **Дефект, который был до моих правок.** `process_batch(dedupe=True)` падает с `KeyError: 'text'` на запросе без поля `text` (строка 90, обращение вне `try`). Без dedupe такой запрос попадает в `failures`. В обеих версиях это одинаково; я зафиксировал это в тестах, но не чинил.
- **Условия замера.** Одна машина и один Python 3.13.2: относительное ускорение должно переноситься, абсолютные секунды нет. На 3.11 и 3.12 из CI не гонял.
- **Профиль искажает абсолютные времена.** Доли в таблице профиля ориентировочные; итоговые числа взяты из `bench_ab.py` и `ablation.py` без профайлера.
- **Не оптимизировал** `describe_failure` и `validate_settings`. В бенчмарке сбоев 0, а `validate_settings` выполняется один раз при импорте на 5 ключах.
- **Проверяющие агенты не запускались.** `reviewer`, `tester`, `explorer` из контракта я не вызывал, потому что задание запрещало вложенных агентов. Независимой проверки третьей стороной нет; её стоит провести до внедрения.
