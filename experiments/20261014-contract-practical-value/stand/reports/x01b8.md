# Можно ли верить ROC AUC 0.817

## Вывод

Нет. Цифра воспроизводится (`python train.py` даёт `k=41 test ROC AUC=0.817 accuracy=0.756`), но она завышена. В пайплайне есть утечка целевой переменной в признак `user_rate`, и гиперпараметры выбраны по тестовой выборке. Кроме того, случайное разбиение по строкам не похоже на то, как модель будет использоваться.

Для заявленного сценария (раз в неделю переобучать на всей истории и прогнозировать следующие недели) стоит ждать **ROC AUC около 0.68**. Реалистичный коридор по 8 запускам на разных зёрнах данных: 0.64–0.73. Если много новых пользователей, которых модель не видела, будет около 0.64.

Все числа получены на синтетическом `data.py`. Они показывают масштаб завышения на этих данных. Для реальных данных нужно перезапустить честный пайплайн (`audit.py::honest`), а не переносить 0.68.

## Что нашёл

### 1. Утечка таргета через `user_rate` (главная причина)
- `train.py:14-19` и `train.py:77`: `user_rate` считается как среднее `y` пользователя по всей таблице до разбиения. В него входят метки тестовых строк и метка самой строки.
- Проверка: без этого признака на том же разбиении и том же коде AUC падает с 0.817 до **0.690**.
- В боевом режиме метка текущей сессии неизвестна, а будущих сессий нет вообще. Для признака нужны только прошлые метки, либо метки обучающей части с исключением самой строки.

### 2. Гиперпараметры выбраны по тесту
- `train.py:91-98`: сетка из 4 значений числа признаков и 6 значений `k` даёт 24 конфигурации. Лучшая по AUC на тесте выбирается и тут же отчитывается как результат (`train.py:100-106`).
- По сетке максимум 0.817, среднее 0.737. Часть разрыва реальна: в сетке есть заведомо плохие конфигурации. Поэтому нельзя сказать, сколько именно оптимизма даёт выбор по тесту. Сам метод некорректен.

### 3. Предобработка и отбор признаков видят тест
- `train.py:80-81`: стандартизация (`standardize`) и ранжирование признаков по корреляции с `y` (`rank_features`) считаются по всей выборке, включая тест. Метки тестовых строк участвуют в выборе 5 признаков.

### 4. Дубликаты строк попадают в тест
- `data.py:57-58`: около 1/8 строк журнала продублировано, а `train.py:89` убирает дубли только в обучении.
- Проверка: у **15.1 %** тестовых строк есть точная копия в обучении, и kNN при `k=1` такие строки просто «вспоминает». На итоговой цифре эффект небольшой: 0.817 → 0.814 при дедупликации до разбиения.
- Побочная находка: `np.unique(axis=0)` не склеивает строки с NaN, поэтому дубли с пропуском в `pages` (около 6 % строк) остаются. Лишних строк 19 из 3568 (3191 против 3172 при замене NaN на константу).

### 5. Случайное разбиение не соответствует сценарию применения
- `train.py:83-86`: строки перемешиваются случайно. Проверка: **100 %** пользователей из теста есть в обучении. Признаки `f1..f3` — это устройство пользователя (`data.py:50`), то есть фактически идентификатор. Модель узнаёт пользователя, а не учится предсказывать покупку.
- `data.py:40,45`: скидка влияет на покупку только до 120-го дня (акция). Измерено: до дня 120 P(покупка | скидка) = 0.613 против 0.388 без скидки, после — 0.430 против 0.388. Случайное разбиение смешивает периоды, и модель видит эффект скидки, которого в будущем не будет. Разбиение по времени этот сдвиг показывает.

## Как проверял

Скрипты `audit.py` и `audit2.py` лежат в папке проекта, запуск: `python audit.py`, `python audit2.py`. Исходный код я не менял.

Постепенное исправление на исходном разбиении (зерно данных 7):

| вариант | AUC |
|---|---|
| как в `train.py` | 0.817 |
| дедупликация до разбиения | 0.814 |
| без `user_rate` | 0.690 |
| дедупликация и без `user_rate` | 0.660 |

Честный пайплайн (`audit.py::honest`):
- дедупликация до разбиения;
- стандартизация, отбор признаков и `user_rate` считаются только по обучению (для строк обучения исключается своя метка);
- `k` и число признаков выбираются на внутренней валидации (последние 25 % дней обучения);
- тест открывается один раз.

Результаты по 8 зёрнам данных (7–14):

| схема оценки | AUC среднее | sd | min–max |
|---|---|---|---|
| по времени: обучение дни < 120, тест дни ≥ 120 | 0.678 | 0.015 | 0.660–0.708 |
| по пользователям: 75 новых пользователей в тесте | 0.643 | 0.026 | 0.601–0.691 |
| случайные строки, но без утечек (для сравнения) | 0.719 | 0.022 | 0.678–0.759 |

Сдвиг границы обучения по времени (`audit2.py`, 8 зёрен):

| обучение до дня | AUC среднее | sd | размер теста |
|---|---|---|---|
| 100 | 0.688 | 0.018 | ≈1413 |
| 125 | 0.684 | 0.017 | ≈970 |
| 140 | 0.680 | 0.030 | ≈700 |
| 155 | 0.700 | 0.025 | ≈437 |

Разбиение по времени воспроизводит боевую постановку, и оценка 0.68–0.70 устойчива к выбору границы. Единичный прогон даёт ±0.03 просто от случайности. Разница между 0.817 и 0.68 примерно в восемь раз больше этого разброса.

## Что предлагаю

1. Не запускать с ожиданием 0.82. Планировать на ≈0.68 и считать 0.64 нижней оценкой, если много новых пользователей.
2. Исправить пайплайн:
   - считать `user_rate` только по прошлым меткам пользователя (либо по меткам обучения с исключением своей строки);
   - стандартизацию, ранжирование признаков и импутацию делать только на обучении;
   - `k` и число признаков подбирать на валидации внутри обучения, тест открывать один раз.
3. Дедуплицировать до разбиения с учётом NaN (например, `np.nan_to_num` перед `np.unique`), а лучше устранить дубли в источнике журнала.
4. Оценивать по времени: обучение на прошлом, тест на следующих неделях. Для новых пользователей отдельно мерить качество с разбиением по пользователям.
5. Разобраться со скидкой: после окончания акции признак `discount` почти перестаёт работать. Если акции повторяются, нужен признак периода или переобучение на сопоставимых днях.
6. Перед запуском провести A/B-проверку персональных предложений: качество прогноза не равно эффекту от показа предложения.
7. Технические признаки `n0..n24` случайны, а модель использует только 5 лучших. Остальные можно отбросить.
