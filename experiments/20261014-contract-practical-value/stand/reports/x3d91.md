# client_lib 2.0.0: правда ли, что она полностью обратно совместима с 1.x

## Вывод

Нет, неправда. Фраза в `CHANGELOG.md` (строки 5-7: "fully backward compatible with 1.x. Existing client code keeps working without any changes") не выдерживает проверки. `client_app.py`, запущенный без единой правки против v1 и v2, даёт разные результаты в 6 из 7 шагов:

- 4 шага падают с исключением (`items`, `label`, `unit price Z-999`, `priority`).
- 2 шага молча возвращают другие числа (`subtotal` 20.0 -> 24.0, `shipping` 38.0 -> 455.2).
- 1 шаг не изменился (`unit price A-100`).

Самое опасное здесь не падения, а два тихих изменения: они портят деньги и не оставляют следа в логе.

Проверен один клиент, `client_app.py`, и весь публичный API (6 функций, 2 класса исключений). Другие клиенты я не видел. Для них вывод строится по диффу API: любой клиент, который вызывает эти функции так же, сломается так же.

## Чем подтверждено

Команды (из папки проекта; `-I -B` не пишет `__pycache__` и не подтягивает лишнее):

```

diff -u v1/client_lib.py v2/client_lib.py
```

Дополнительно я загрузил обе версии как модули через `importlib` и сравнил сигнатуры и поведение на отдельных входах. Результаты вошли в таблицу ниже.

## Что сломается или начнёт работать иначе

| # | Что | Где в клиенте | v1 | v2 | Как проявится |
|---|---|---|---|---|---|
| 1 | `invoice_total`: умолчание `tax_rate` | `client_app.py:44` | `0.0` (v1:36) | `0.2` (v2:44) | Тихо. Итог +20% (20.0 -> 24.0) |

Пояснения:

1. Нулевой налог в 1.x был явным умолчанием. Клиент вызывает `invoice_total(records)` без `tax_rate`, поэтому каждый счёт ночной задачи вырастет ровно на 20%. Явный `tax_rate=0.0` даёт прежний результат (10.0 и 10.0), ломаются только вызовы без аргумента.
2. Валидация в `shipping_cost` симметрична (`weight_kg <= 0 or distance_km <= 0`), поэтому перепутанные аргументы ошибку не вызывают. Вручную: v1 = 5.0 + 1.5*2.0 + 0.1*300 = 38.0; v2 = 5.0 + 1.5*300 + 0.1*2.0 = 455.2. Вызовы по ключевым словам не затронуты (38.0 и 38.0). Ломаются позиционные вызовы, а они самые частые.
3. Ключи словаря не входят в сигнатуру, поэтому проверка сигнатур этого не поймает.
4. Позиционный `format_price(19.9, "EUR")` работает одинаково (`19.90 EUR`). Ломаются только вызовы с `currency=`.
5. `lookup` имеет одинаковую сигнатуру и одинаково работает на успешном пути. Меняется только базовый класс исключения: `except NotFoundError` и `except LookupError` работают, `except KeyError` нет.
6. Сигнатура `normalize_priority` идентична, поведение нет. В changelog 2.0.0 об этом ничего нет. Пробелы по краям v2 срезает, регистр больше не понижает.

Что сказано в changelog (строки 14-19) и чего в нём нет: все пункты сформулированы нейтрально ("Parameter naming unified", "Record fields aligned with catalog terminology", "defaults aligned with accounting requirements", "Exception hierarchy clarified") и ни один не называет старое и новое значение. Значение 0.2 и смена порядка аргументов не упомянуты вообще. Пункта про `normalize_priority` в 2.0.0 нет.

## Что только выглядит опасным и безопасно

Проверено тем же сравнением.

- `_to_cents` -> `_as_cents`: имя приватное, клиент его не использует. В наборе публичных имён модуля единственное отличие: появилось `Decimal` (из-за `from decimal import Decimal`). Заденет только клиента с `from client_lib import *`.
- `format_price` принимает `Decimal` и строки. Все входы, работавшие в v1, дают тот же результат (`5` -> `5.00 USD`, `19.9, "EUR"` -> `19.90 EUR`). Меняется только область отказов: строка `"19.9"` в v1 давала `ValidationError`, в v2 возвращает `19.90 USD`. Для `"abc"` тип исключения прежний, текст другой. Ломается лишь код, который использовал отказ на строках как проверку.
- `parse_record(..., strict=False)`: новый параметр, по умолчанию выключен. `qty=0` проходит как в v1, позиционный `sep` работает, ошибка при неверном числе полей идентична. Ломает `parse_record` только переименование ключа (пункт 3).
- `lookup` идентичен, `ValidationError(ValueError)` не менялся.
- Словарь `CATALOG` в `client_app.py` (строки 6-9) тоже использует ключ `"name"`, но это собственные данные клиента, а не результат `parse_record`. Переименование на них не влияет.
- Новый номер версии и импорт `Decimal` на поведение не влияют.

## Что предлагаю

Выбор между двумя вариантами за вами. В любом случае формулировка про полную совместимость должна уйти из текущего changelog.

Вариант A: честно объявить поломку. 2.0.0 как мажорная версия для этого и предназначена. Убрать "fully backward compatible" и фразу "not a breaking change". Добавить раздел "Breaking changes" с шестью пунктами таблицы, с конкретными старыми и новыми значениями (`tax_rate` 0.0 -> 0.2, порядок аргументов `shipping_cost`), и приложить инструкцию по миграции.

Вариант B: вернуть совместимость и тогда оставить формулировку.

- `invoice_total`: вернуть `tax_rate=0.0`. Если нужен налог 20%, пусть клиент передаёт его явно или будет отдельная функция.
- `shipping_cost`: вернуть порядок `(weight_kg, distance_km)`. Если порядок всё же нужно менять, сделать параметры только именованными с циклом депрекации.
- `NotFoundError`: объявить `class NotFoundError(KeyError)`. `KeyError` уже подкласс `LookupError`, иерархия остаётся ясной, а `except KeyError` продолжает работать.
- `normalize_priority`: вернуть `.lower()`.
- `parse_record`: отдавать оба ключа, `name` и `title`, `name` пометить устаревшим.
- `format_price`: принимать `currency` как устаревший синоним `currency_code` с `DeprecationWarning`.

При любом варианте:

1. Первыми разобрать пункты 1 и 2: они не падают и не видны в логах. Если 2.0.0 уже где-то использовалась, проверить выпущенные суммы и стоимость доставки.
2. Добавить регрессионный тест совместимости: запускать `client_app.py v1` и `client_app.py v2` и сравнивать вывод построчно. Сейчас он расходится в 6 строках из 7. Сравнивать нужно вывод, а не exit code, он равен 0 в обеих версиях.
3. Сделать так, чтобы `step()` в клиенте возвращал ненулевой код при `FAILED`, иначе ночная задача будет "успешной" при любых сбоях.
