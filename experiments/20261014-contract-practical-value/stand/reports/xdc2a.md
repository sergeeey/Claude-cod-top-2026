# Почему results.json не повторяется, и что изменено

## Итог в двух строках
В `run_experiment.py` было четыре независимых источника расхождений, зерно `SEED` закрывало только один из них (бутстреп). Исправлено, результат теперь побайтно одинаков в трёх запусках (два чистых venv, другая папка, CSV с CRLF, три разных `PYTHONHASHSEED`).

## Что нашёл (каждый пункт проверен отдельным прогоном)

Базовая линия, исходный скрипт, 7 запусков подряд (4 обычных + `PYTHONHASHSEED`=1,2,3), numpy 2.3.4, Python 3.13.2:
`effect` = 0.357, 0.4505, 0.5913, 0.624, 0.6671, 0.6677, 0.9497. Размер группы `control` плавал от 19 до 24. Это числа для результата, до любых правок.

| # | Причина | Где в исходнике | Проверка |
|---|---|---|---|
| 1 | Подвыборка 80% делается через `random.shuffle` из стандартной библиотеки, которая зерном `SEED` не инициализируется (зерно получает только `np.random.default_rng`) | `subsample()`, `random.shuffle(rows)` | Меняются `n` по группам между запусками (control 24, 20, 22, 19). Это главный источник: у тебя повторные запуски не совпадают именно из-за него |
| 2 | Порядок файлов: `glob.glob` отдаёт список в порядке файловой системы, не отсортированный. Строки идут в другом порядке, и перемешивание даже с одним зерном выбирает другие строки | `load_rows()` | Абляция (`base_logs/ablate.py files`): shuffle-зерно и группы те же, порядок файлов прямой/обратный -> control n=23 / 24, treatment mean 11.0566 / 11.2103. Это объясняет, почему у коллеги (другая ОС/ФС) числа другие, даже при совпадении всего остального |
| 3 | `groups = {g for g, _ in rows}` - множество строк. Порядок обхода зависит от `PYTHONHASHSEED` (по умолчанию случайный на каждый процесс). Один общий `rng` расходуется по группам по очереди, поэтому группа, оказавшаяся второй, получает другой кусок потока | `main()`, цикл `for g in groups` | Абляция (`ablate.py hash`, подвыборка фиксирована): средние и `n` одинаковы, а `ci_low/ci_high` меняются от `PYTHONHASHSEED`: у control `ci_low` 9.5886 (seed 3) / 9.6374 (seed 1) / 9.5791 (seed 4) |
| 4 | `results.json` содержит `run_at` и абсолютный `data_dir`, поэтому файлы двух запусков никогда не совпадают побайтно, и у другой машины будет другой путь | конец `main()` | Видно по тексту файла |
| 5 (мелкие) | `effect` считался из уже округлённых до 4 знаков средних (ошибка до 1e-4); запись JSON в текстовом режиме на Windows даёт CRLF, на Linux LF - байты файла разные; numpy в `requirements.txt` не закреплён, а поток `Generator` numpy не гарантирован между версиями | `effect = ...`, `open(OUT_PATH, "w")`, `requirements.txt` | Чтение кода; по версиям numpy проверить на второй машине не мог |

Нерешённая сторона: `PYTHONHASHSEED` и порядок файлов влияют только на 2 и 3; пункт 1 сам по себе даёт разброс эффекта 0.36-0.95.

## Что изменено
- `run_experiment.py`: нет глобального `random`; подвыборка идёт из своего потока `np.random.default_rng` (SeedSequence(SEED).spawn), для каждой группы свой поток; группы берутся из явного кортежа `("control","placebo","treatment")`; файлы сортируются по имени; `effect` из неокруглённых средних; из `results.json` убраны время и путь, добавлены SHA-256 CSV (с нормализацией CRLF) и `sort_keys`; запись с `newline="\n"`; окружение вынесено в отдельный `manifest.json`. `SEED = 20240501` и все параметры не менялись, зерно из исходника, не подбиралось под результат.
- `requirements.txt`: `numpy==2.3.4`.
- `README.md` обновлён, `TOLERANCE.txt` записан до сравнения.
- Резервные материалы: `base_logs/` (исходник, 7 исходных результатов, абляция), `clean_runs/` (логи и результаты проверки).

## Допуски (записаны в `TOLERANCE.txt` до сравнения)
- T1, одно окружение: файл побайтно одинаков.
- T2, другое окружение: `n`, SHA-256 данных, параметры совпадают точно; средние, границы и эффект в пределах 1e-4.
- T3, сравнение с исходным: эталонного results.json от коллеги не было, исходный скрипт сам нестабилен, поэтому равенства нет, только проверка попадания в диапазон.

## Что важно знать о самом результате
- Диагностика (`clean_runs/spread.py`, не часть эксперимента): по всем 90 строкам эффект 0.6761; по 2000 случайным 80% подвыборкам эффект имеет среднее 0.6800, sd 0.2419, 95% диапазон [0.2150, 1.1342]. Значит значение 0.9166 - одна конкретная подвыборка, а не оценка эффекта. Бутстреп-интервалы в `results.json` этот разброс не учитывают. Если подвыборка 80% не нужна по смыслу (в README её назвали holdout, но на оставшихся 20% ничего не оценивается), лучше считать по всем данным: 0.6761. Это решение за тобой, я его не менял, так как оно меняет смысл анализа.
- Не проверено: другая версия numpy/Python и другая ОС (Linux/macOS) я не запускал; "другой компьютер" эмулировал папкой, CRLF и PYTHONHASHSEED. Поток `Generator` numpy гарантированно стабилен только внутри закреплённой версии, поэтому версия закреплена, а при смене действует допуск T2 (и его нужно подтвердить прогоном).
- Остаточная невоспроизводимость: сумма с плавающей точкой может отличаться в последнем бите на другом CPU/сборке numpy; округление до 4 знаков почти всегда это скрывает, но на границе округления возможен сдвиг 1e-4 (это T2). Внешних сервисов и сети в скрипте нет.

## Предложения
1. Решить, нужна ли подвыборка 80%. Без неё результат не зависит от выбора строк.
2. Прогнать `run_experiment.py` на машине коллеги в чистом venv и сравнить `results_sha256` из `manifest.json` с `2b04614e...baeb` (полный хэш: `2b04614e891c6a5f425fccd32a0cc1b84487e690c1a11f07ce37ca146442baeb`); при несовпадении сверить по допуску T2.
3. Добавить в CI проверку: два прогона, сравнение хэша.
