# Отчёт: почему результаты не совпадают и что исправлено

## Коротко

Зерно в скрипте было зафиксировано только наполовину. `SEED` попадал в генератор numpy (бутстреп), но 80% строк выбирались через глобальный `random.shuffle`, которому зерно никто не задавал. Поэтому каждый запуск брал другую подвыборку и считал эффект по другим данным. К этому добавились ещё три источника расхождений: порядок файлов, порядок групп в `set` и служебные поля в `results.json`. Все четыре исправлены. После правки `results.json` совпадает побайтно между запусками.

Новое воспроизводимое число: `effect = 0.9165`. Это результат одной конкретной подвыборки, а не «исправленная» оценка (см. «Что стоит решить»).

## Что найдено

Номера строк даны по исходному `run_experiment.py`. Его копия лежит в `_evidence/run_experiment_original.py`, там изменён только путь вывода.

### 1. Подвыборка не зависит от зерна (главная причина)

- Строка 34: `random.shuffle(rows)` использует глобальный генератор `random`. В файле нет ни `random.seed(...)`, ни `random.Random(SEED)`. Строка 46 `np.random.default_rng(SEED)` на `random` не влияет.
- Подтверждение. Три запуска исходного скрипта подряд дали `effect` = 0.9126, 0.6063, 0.9616. Три запуска с `PYTHONHASHSEED` = 0, 1, 2 дали 0.6154, 0.2389, 0.8962 (`_evidence/before_run*.json`, `before_hs*.json`). Два вызова `subsample` в одном процессе дали разные выборки при одинаковом `n = 72` (`_evidence/diag.py`, пункт 1).
- Следствие. Числа коллеги и ваши прошлые числа воспроизвести нельзя: какую выборку они получили, нигде не записано.

### 2. Порядок строк зависит от файловой системы

- Строка 24: `glob.glob(...)` возвращает файлы в произвольном порядке, который определяют ОС и файловая система. От порядка файлов зависит порядок строк, а `shuffle` с тем же зерном на другом порядке входа даёт другую выборку.
- Подтверждение моделированием. Зерно `random` зафиксировано, порядок файлов прямой или обратный. `effect` получается 0.9903 и 0.5414 (`diag.py`, пункт 2).
- Что у коллеги порядок реально другой, я не наблюдал, его машины у меня нет. Это [INFERRED].

### 3. Порядок групп берётся из `set`

- Строка 49: `groups = {g for g, _ in rows}`, затем строка 52: `for g in groups`. Все группы делят один общий `rng`. Порядок строк в `set` зависит от `PYTHONHASHSEED`, который по умолчанию случаен на каждый запуск.
- Подтверждение. Порядок групп при `PYTHONHASHSEED` = 0, 1, 2, 3:
  - `control, treatment, placebo`
  - `treatment, control, placebo`
  - `treatment, control, placebo`
  - `control, placebo, treatment`
- При одной и той же подвыборке интервал группы `control` меняется в зависимости от порядка: (9.6144, 10.9006), (9.6279, 10.9351), (9.5795, 10.8936) (`diag.py`, пункт 3).
- Средние при этом не меняются (control 10.2973, treatment 11.2876). Этот дефект портит интервалы, а не эффект.
- Порядок ключей в `results.json` тоже плавает (видно в `diff before_run1.json before_run2.json`).

### 4. В `results.json` лежат поля, которые не могут совпадать

- Строки 67-68: `"data_dir": DATA_DIR` (абсолютный путь на конкретной машине) и `"run_at": datetime.now()...`.
- Даже при одинаковых числах файлы у двух людей не совпадут побайтно, сравнивать приходится глазами.

### Проверено и не является причиной

- Кодировка и переводы строк: три CSV чистые ASCII, LF, без BOM (`file data/*.csv`, `grep -c $'\r'` даёт 0 для каждого).
- Метки групп: `control` 26, `placebo` 35, `treatment` 29 строк, плюс 3 заголовка, всего 90 строк данных. Опечаток и лишних пробелов нет.

### Не проверено

- **Другая версия numpy.** В исходном `requirements.txt` было просто `numpy`, у коллеги могла встать другая версия.
  - По политике numpy (NEP 19, помню по памяти, в документации заново не сверял) поток `Generator` между версиями не гарантируется.
  - Версию я закрепил, но совпадение на другой версии не проверял: ничего не скачивал и не ставил.
- **Другая ОС и процессор.** Все запуски на одной машине: Windows 11, Python 3.13.2, numpy 2.3.4. Суммирование float на другом процессоре теоретически может отличаться в последнем бите, но после округления до 4 знаков это почти наверняка не видно.
- **Файл коллеги.** Его `results.json` у меня нет. Что его числа расходились из-за пунктов 1-3, подтверждено механизмом, а не сверкой с его файлом.

- Результат: `effect = 0.9165`. control mean 10.2746 (n 23), placebo 10.1496 (n 28), treatment 11.1911 (n 21).

## Что стоит решить (я не менял)

Воспроизводимость теперь есть, но число 0.9165 зависит от того, какие 80% строк выпали. Данные из `_evidence/diag2.py`:

- Эффект на всех 90 строках: 0.6761 (control 10.3973, treatment 11.0734).
- Эффект на 2000 разных случайных 80%-подвыборках: от -0.111 до 1.368. Центральные 95% лежат в 0.190...1.161, медиана 0.687.

Выбор подвыборки двигает эффект сильнее, чем интервалы в таблице, а на некоторых подвыборках знак эффекта меняется. Зафиксированное зерно даёт 0.9165, это выше медианы. Это один розыгрыш, а не оценка эффекта.

В README эти 80% названы «holdout», но на оставшихся 20% ничего не обучается и не проверяется. Варианты:

1. Считать по всем 90 строкам (эффект 0.6761) и убрать подвыборку. Проще всего, случай не участвует.
2. Если подвыборка нужна по смыслу (например, для устойчивости), повторять её много раз и сообщать распределение эффекта, а не одно число.

Остальное по методу я не трогал:

- Интервалов для самого эффекта нет, только для средних по группам.
- `effect` считается из уже округлённых до 4 знаков средних (погрешность до 1e-4).

## Что делать коллеге

1. Взять тот же код, создать чистый venv на Python 3.11+, выполнить `pip install -r requirements.txt`.
2. Запустить `python run_experiment.py`, сравнить блок `input.files_sha256` и хеш `results.json`.
3. Если хеши CSV разные, расхождение в данных, а не в коде. Если данные те же, а числа другие, нужен его `run_meta.json` (версии Python и numpy).

Прежние числа (ваши и коллеги) воспроизвести нельзя. Использовать их можно только как иллюстрацию разброса.
