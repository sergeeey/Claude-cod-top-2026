# Почему тесты модуля заказов то зелёные, то красные

## Коротко

Многопоточность тут ни при чём: тесты однопоточные. Причин пять, и все они в `shop.py` и в самих тестах. Две из них (порядок элементов в множестве и случайные номера заказов) дают разный результат от запуска к запуску. Остальные три (общий кэш цен, общий список по умолчанию, сравнение времени) зависят от порядка тестов или от случая.

Поправка к описанию: `test_pricing.py` в одиночку падает не «иногда», а каждый раз. `test_promo_order_total` проходит только после `test_orders.py`, потому что тот заполняет кэш обычными ценами.

Исправления сделаны в копии `fixed_copy/`. Исходные файлы проекта не менялись.

## Что нашёл

Номера строк относятся к исходному `shop.py`.

**1. Кэш цен привязан только к артикулу (строки 6, 11-17).** `_PRICE_CACHE[sku]` не учитывает, из какого каталога взята цена. Первый вызов определяет цену для всех следующих.
- Один `test_promo_order_total` в 5 отдельных процессах: 5 из 5 падений, `assert 12.4 == 15.5`.
- Ожидание 15.5 равно сумме по обычным ценам (1.5·2 + 12.5). По акционным ценам получается 1.2·2 + 10.0 = 12.4. Тест проходил только на отравлённом кэше, то есть закрепляет ошибку.
- Связь действует в обе стороны. Если `test_pricing.py` идёт раньше `test_orders.py`, то на 10 значениях `PYTHONHASHSEED` падают ещё `test_add_items` (2.4 вместо 3.0) и `test_receipt` (10.0 вместо 12.5), 10 из 10.

**2. Порядок элементов множества зависит от `PYTHONHASHSEED` (строка 48).** `categories()` возвращает `list(set)`, а `primary_category` берёт первый элемент.
- Перебор `PYTHONHASHSEED` 0-49: неверный результат («food») на 24 из 50 значений.
- Полный набор, 40 запусков: `test_primary_category` упал 23 раза (57%).

**3. Номера заказов случайные, от 1 до 40 (строки 27-28).** Для 5 заказов вероятность совпадения равна 1 − 40·39·38·37·36/40⁵ = 22,89%.
- 20000 попыток с `random.seed(12345)`: 4577 совпадений (22,88%).
- `test_order_ids_unique` в 40 запусках упал 7 раз (17,5%; ожидание около 9, расхождение в пределах шума).
- Это не только проблема теста. Среди 41 заказа совпадения неизбежны, в тесте их оказалось 15. Из 400 заказов, созданных 8 потоками, дублей 360.

**4. Изменяемое значение по умолчанию `items=[]` (строка 32).** Все заказы без явного списка делят один список.
- `test_add_items` перед `test_new_order_is_empty` роняет второй: `assert [('pen', 2)] == []`.
- В штатном порядке это скрыто: пустой тест в файле стоит раньше.
- В 8 потоках у каждого из 8 заказов по 800 позиций вместо 100. На практике это утечка позиций между покупателями.

**5. Сравнение времени с точностью до секунды (`test_orders.py`, строка 43).** `receipt` и тест вызывают `datetime.now()` по отдельности. Если между вызовами меняется секунда, равенство нарушается.
- Тест с подменой часов воспроизводит расхождение при разрыве в 2 мкс на границе секунды.
- Реальный зазор: в среднем 4,4 мкс, максимум 156,7 мкс. Вероятность около 4,4·10⁻⁶ на запуск. В моих запусках не проявилось ни разу, к вашим наблюдениям это почти не относится.

**Вторично, на ваши симптомы не влияет.** В `load_price` проверка кэша и запись разделены `sleep(0.001)`. При принудительном пересечении 8 потоков загрузка идёт 8 раз вместо одного, 30 раундов из 30. В тестах потоков нет, это риск при реальной нагрузке.

Контроли. `next_sequence` с блокировкой при 16 потоках по 2000 вызовов выдала ровно числа 1..32000. Тот же стенд на счётчике без блокировки при принудительном пересечении теряет обновления (из 8 остаётся 1). Значит, стенд способен находить такие ошибки.

## Подтверждение

Вероятности совпадают с наблюдением. Полный набор зелёный, если категория угадана (50%) и номера не совпали (77,1%). Ожидание 38,6%, получено 14 зелёных из 40 (35%). Красных 26 из 40.

Исходные 40-кратные прогоны шли с плагинами pytest по умолчанию. Остальные шли с `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` ради скорости. На результат это не влияет.

Инварианты и тесты (`evidence/test_concurrency_findings.py`):
- I1: цена соответствует переданному каталогу при любом порядке вызовов.
- I2: холодная цена загружается один раз на ключ при одновременных запросах. Окно раскрывается барьером, 30 раундов по 8 потоков.
- I2b: загрузки разных ключей не блокируют друг друга. Это защита от взаимной блокировки и от единой общей блокировки. Тесты ограничены сторожевым таймаутом.
- I3: у каждого заказа свой список, включая 20 раундов по 8 потоков.
- I4: номера заказов уникальны, включая 400 заказов из 8 потоков.
- I5: категория не зависит от хеш-семени, перебор 50 значений.
- I6: проверка времени не ломается на границе секунды.
- I7: `next_sequence` атомарна (положительный контроль), стенд ловит потерю обновлений (отрицательный контроль).

## Что предлагаю сделать

Готовые правки лежат в `fixed_copy/shop.py`, `fixed_copy/test_orders.py`, `fixed_copy/test_pricing.py`.

1. Ключ кэша `(id(каталога), sku)`, в записи хранить ссылку на каталог, чтобы `id` не переиспользовался. Загрузка идёт под замком на ключ с повторной проверкой внутри. Общий замок на время загрузки не держится, замки не вложены, цикла нет. Ограничения: словарь замков растёт, записи не устаревают при изменении каталога. Для долгоживущего сервиса лучше вынести кэш в объект прайс-листа.
2. `items=None` и `self.items = [] if items is None else list(items)`. Копирование меняет семантику для тех, кто рассчитывал на общий список; в тестах таких нет.
3. Номер заказа выводить из `next_sequence()` (`ORD-000123`). Он уникален в рамках процесса. Если номера должны переживать перезапуск, нужен `uuid4` или последовательность в базе.
4. `categories()` через `dict.fromkeys(...)` даёт порядок первого появления. Что считать основной категорией, решает владелец продукта. Альтернативы: категория с наибольшей суммой или алфавитный порядок. Для текущего теста все варианты дают «books».
5. В `test_promo_order_total` ожидание 12.4 вместо 15.5. Подтвердите, что акционный итог должен быть именно 12.4.
6. В `test_receipt` заменить равенство двух вызовов `now()` проверкой окна `before <= printed_at <= after`, где `before` усечён до секунды.

## Ограничения

- Отсутствие находок в стрессе не доказывает отсутствия гонок. Зелёные прогоны исправленной копии подтверждают только проверенные чередования и названные числа прогонов. Для `next_sequence` и `load_price` вывод опирается ещё и на чтение кода.
- Независимая проверка агентом-ревьюером не проводилась: по условиям задания агентов запускать было нельзя. Перед переносом правок в основной код стоит показать их ревьюеру.
- Free-threaded сборка Python (без GIL) не проверялась: использовался Python 3.13.2 с GIL.
