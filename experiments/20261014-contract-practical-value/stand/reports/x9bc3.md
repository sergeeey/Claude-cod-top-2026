# Отчёт: проблемы параллелизма в сервисе склада

## Кратко

Все четыре симптома объясняются кодом.

| Симптом | Причина | Где |
|---|---|---|
| Остаток в минусе | проверка и списание в `reserve()` не атомарны | warehouse.py:36 и 39-40 |
| Цифры в отчётах не сходятся | потерянные обновления `_reserved`, утечка резервов при ретраях, `report()` без блокировки | warehouse.py:41, 55-56; orders.py:73-81 |
| Зависание | `transfer()` берёт две блокировки в разном порядке (ABBA) | warehouse.py:61, 65 |
| Двойное списание денег | ретрай платежа без ключа идемпотентности, резерв внутри цикла ретраев | orders.py:71-81 |

Ограничение: на стандартном `switchinterval` гонки в моих прогонах не проявились (0 из 300 и 0 из 400 запусков). Они воспроизводятся при расширенном окне гонки: `sys.setswitchinterval(1e-6)` или искусственная задержка. Это согласуется с жалобой «время от времени», но частоту в проде я измерить не могу.

## Как проверено

Скрипты лежат рядом с кодом:
- `repro_races.py`: `python repro_races.py` для исходного кода, `python repro_races.py fixed` для исправления.
- `repro_freeze.py`.

Логи: `repro_orig.log`, `repro_fixed.log`, `repro_freeze_orig.log`, `repro_freeze_fixed.log`. Числа ниже из последнего прогона. При повторе они немного плавают из-за планировщика потоков.

## Находки

### 1. Остаток уходит в минус: `reserve()` (высокая серьёзность)

`reserve()` проверяет остаток через `available()` (строка 36), и блокировка снимается при возврате. Списание идёт отдельно, под новой блокировкой (39-40). Между ними другой поток успевает забрать товар.

- Детерминированно: два потока резервируют последнюю единицу, окно зафиксировано барьером. Результат `[True, True]`, остаток -1, reserved 2.
- Нагрузка (8 потоков по 100 попыток на остатке 200, `switchinterval=1e-6`): минус в 300 из 300 запусков, продано больше 200 тоже в 300 из 300, минимум -7. При стандартном интервале 0 из 300.
- Второй путь к минусу: `transfer()` забирает товар между проверкой и списанием в `reserve()`. В сквозном прогоне сценария `main.py` (400 запусков, `1e-6`) минус встретился в 4 запусках, например `central pear=-1`.
- `_apply_delta` (16-18) не защищает от отрицательного остатка.
- Входные значения не проверяются. `reserve("a", -5)` возвращает True и увеличивает остаток, `transfer(a, b, "x", -5)` даёт `b = -5`.

### 2. Цифры в отчётах не сходятся (высокая)

а) Потерянные обновления `_reserved`. Строка 41 выполняется вне блокировки. В тесте с 8 потоками `reserved` не равен числу успешных резервов в 93 из 300 запусков (`1e-6`). В сквозном прогоне «free + reserved» не равно начальному запасу плюс пополнения в 14 запусках из 400.

б) Резервы не закрываются. `release()` определён (warehouse.py:44), но нигде не вызывается (grep по трём файлам). `_reserved` только растёт, оплаченные заказы остаются «в резерве».

в) Каждый ретрай резервирует заново (orders.py:73 внутри цикла на 71), а предыдущий резерв при сбое оплаты не снимается.
- Один заказ при недоступном шлюзе: free 7, reserved 3 вместо free 10.
- В штатном выводе `main.py` спрос на apple 39 единиц (посчитан по заказам), а `reserved=46`, то есть 7 лишних.
- На 200 запусках по 40 заказов потеряна 1681 единица свободного остатка.

г) `report()` без блокировки (warehouse.py:55-56).
- Параллельное добавление нового SKU даёт `RuntimeError: dictionary changed size during iteration`: 4077 ошибок на 4083 вызова.
- `snapshot()` тоже может вернуть несогласованную пару, потому что `reserve()` между списанием и увеличением `_reserved` блокировку отпускает. При одном пишущем потоке потерянных обновлений быть не может, но 248 из 20000 снимков не сошлись, то есть это рваное чтение.

### 3. Зависание: взаимная блокировка в `transfer()` (высокая)

`transfer(src, dst)` берёт `src._lock`, затем `dst._lock` (61, 65). Встречные `A->B` и `B->A` блокируются навсегда. `main.py:18-19` запускает именно такую пару.

- Детерминированно (пауза 50 мс между блокировками имитирует вытеснение): через 6 с оба потока стоят на `warehouse.py:65 with dst._lock`.
- Нагрузка (2 потока по 50 встречных переводов, `1e-6`): зависание в 5 из 5 первых итераций. При стандартном интервале 0 из 2000.
- В точном сценарии `main.py` (по одному переводу на поток) за 800 запусков зависаний не было: окно слишком узкое. При частых переводах в проде оно шире.
- Зависший перевод держит блокировку склада навсегда, и все воркеры встают на `available()` (warehouse.py:21). За 2 с выполнено 0 из 20 заказов, четыре воркера заблокированы, 16 заказов в очереди. Это объясняет «намертво завис».

### 4. Двойное списание денег (высокая)

Мок `PaymentGateway.charge` записывает списание (orders.py:29) до решения об ошибке (30-33), то есть моделирует «деньги ушли, ответ потерян». `_handle` при `TransientError` просто повторяет попытку (79-81) без ключа идемпотентности.

- Из 8000 заказов в профиле `main.py` (сбой 10%) 788 списаны больше одного раза, лишних списаний на 4180 денежных единиц.
- 3 заказа получили статус `failed`, но с тремя списаниями каждый, без возврата.
- При остатке ровно 1 ретрай не может заново зарезервировать собственную единицу: статус `rejected`, а деньги списаны.

Ограничения:
- Ведёт ли реальный шлюз себя как мок, я не знаю. Если у него есть ключи идемпотентности, исправление сводится к их передаче.
- `submit()` не отсекает повторную подачу того же `order_id`. Это вывод из чтения кода, запуском не проверялось.

### 5. Воркер умирает от любого исключения (средняя)

`_run` не ловит исключения (orders.py:62-68). Заказ с `qty=None` убил единственный воркер: результатов 0, `processed=0`, в очереди остались 3 элемента, а `stop()` вернулся без ошибки. Заказы теряются молча.

### 6. `processed += 1` без блокировки (низкая, не воспроизведено)

orders.py:68. В 12 прогонах по 20000 заказов потерь нет (3.13 с GIL, оба интервала). Код небезопасен по построению и сломается на free-threaded сборке, но на вашей конфигурации вклада в симптомы я не нашёл.

## Что не является ошибкой

- `restock_many` вызывает `restock` под той же блокировкой, `RLock` это допускает. Заменять `RLock` на обычный `Lock` нельзя: будет зависание.
- Блокировка в `PaymentGateway.charge` корректна, `sleep` вне блокировки.
- `_last_access` только пишется и нигде не читается. Запись вне блокировки (строка 38) безвредна.

## Что предлагаю сделать

Порядок по приоритету. Проверочная реализация лежит в `fixed/warehouse.py` и `fixed/orders.py`.

1. `reserve()`: проверка, списание и увеличение `_reserved` в одной критической секции. Проверка `qty > 0`, запрет отрицательного остатка в `_apply_delta`.
2. `transfer()`: брать блокировки в едином порядке (в проверочной версии по порядковому номеру склада), проверять `qty > 0`, обработать случай `src is dst`.
3. Заказ как последовательность:
   - резерв один раз, до цикла ретраев;
   - `charge(..., idempotency_key=order_id)`;
   - при успехе `commit` (резерв становится проданным), при исчерпании попыток `release`.
   - Нужно выяснить, поддерживает ли реальный шлюз ключи. Если нет, перед повтором проверять статус платежа по `order_id`, а не повторять вслепую.
4. `report()` строить из `snapshot()`.
5. `_run`: ловить исключения на уровне заказа, отдавать статус `error`, снимать резерв. Отсекать повторный `order_id` (в моей версии это множество в памяти, в проде нужно хранилище).
6. `processed` держать под блокировкой.
7. Тесты на инварианты под `sys.setswitchinterval(1e-6)`: остаток >= 0, free + reserved + sold постоянна, не больше одного списания на заказ.
