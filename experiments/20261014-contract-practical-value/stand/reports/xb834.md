# Почему тесты модуля заказов то зелёные, то красные

## Коротко

Нестабильность даёт не один дефект, а четыре, плюс один редкий флейк. Причина у всех в `shop.py`, а не в «капризах pytest». Две вещи случайны: порядок элементов в `set` и `random.randint` для id заказа. Одна вещь зависит от порядка выполнения тестов: глобальный кэш цен. Изменяемый аргумент по умолчанию пока молчит, но ждёт своего часа. Последняя находка: редкий сбой на границе секунды в `test_receipt`.

| # | Где | Что не так | Кого роняет | Как часто |
|---|-----|-----------|-------------|-----------|
| 1 | `shop.py:47-51` | `primary_category` берёт `[0]` из `list(set)`, а порядок строк в set зависит от случайной соли хеша процесса | `test_primary_category` | 18 из 40 прогонов (45%), теория 50% |
| 2 | `shop.py:27-28` | id заказа это `randint(1, 40)`, пять id из сорока совпадают с вероятностью 22,9% | `test_order_ids_unique` | 12 из 40 (30%), теория 22,9% |
| 3 | `shop.py:6`, `11-17` | кэш цен ключуется только по `sku` и игнорирует `catalog`. Тест промо-цены ждёт 15,5 (сумма по обычному каталогу) и проходит только потому, что кэш заполнен другими тестами | `test_promo_order_total` | `test_pricing.py` отдельно: 30 из 30 красный. В полном наборе зелёный |
| 4 | `shop.py:32-34` | `items=[]` как значение по умолчанию: один список на все заказы без `items` | пока никого, держится на порядке тестов | в текущем порядке 0%, при обратном порядке падает |
| 5 | `shop.py:59`, `test_orders.py:43` | `datetime.now()` вызывается дважды, сравнение с точностью до секунды | `test_receipt` | около 1 из 100 000 запусков |

## Условия измерений

Python 3.13.2, pytest 8.4.2. Плагинов, меняющих порядок или параллелящих запуск (random-order, xdist, rerun), в окружении нет (`pip list`). Серии по 30 и 40 прогонов я гнал с `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1`, чтобы исключить сторонние плагины. Один контрольный прогон с плагинами дал то же падение `test_primary_category`.

Сводка 40 прогонов полного набора подряд без изменений:

```
14 прогонов: 8 passed            (35%)
22 прогона:  1 failed, 7 passed
 4 прогона:  2 failed, 6 passed
FAILED test_orders.py::test_primary_category   18
FAILED test_orders.py::test_order_ids_unique   12
```

Ожидание по двум независимым случайным причинам: зелёный прогон 0,5 × 0,771 = 38,6% (наблюдали 35%). Прогон с двумя падениями 0,5 × 0,229 = 11,4% (наблюдали 4 из 40, то есть 10%). Данные согласуются с теорией, других случайных источников в обычном прогоне почти нет.

## Причина 1: порядок элементов в set (`primary_category`)

```python
def categories(self, category_of):
    return list({category_of[sku] for sku, _ in self.items})   # shop.py:47-48
def primary_category(self, category_of):
    return self.categories(category_of)[0]                      # shop.py:50-51
```

Порядок обхода set строк определяется хешами. Хеши строк в Python солятся случайным значением при старте процесса (`PYTHONHASHSEED`). Поэтому два запуска без правок дают разный `[0]`.

Подтверждение:
- Чистый Python, `list({'books','food'})[0]` в 200 процессах с `PYTHONHASHSEED` от 0 до 199: `books` 108 раз, `food` 92 раза.
- Сам тест с зафиксированной солью: seed 0, 3, 4, 5 красный. Seed 1, 2, 6, 7 зелёный. Повторы seed 0 (три раза) и seed 1 (три раза) дают тот же результат. Исход определяется солью и больше ничем.

Это дефект продукта: «основная категория» заказа определяется случайно. Тест `test_orders.py:26-30` проверяет разумное ожидание, которое код не гарантирует.

## Причина 2: id заказа выбирается из 40 значений

```python
def new_order_id():
    return f"ORD-{random.randint(1, 40):03d}"    # shop.py:27-28
```

`test_order_ids_unique` создаёт 5 заказов и требует 5 разных id. Вероятность этого равна 40·39·38·37·36 / 40⁵ = 0,7711, то есть отказ в 22,9% запусков. Симуляция `new_order_id()` на 200 000 попыток дала 22,88%. В 40 прогонах набора упало 12 раз (30%), это в пределах разброса (одно стандартное отклонение при n=40 около 6,6 п.п.).

Тест здесь прав, ошибся код. В реальной работе коллизии начинаются сразу: при 8 заказах вероятность совпадения id 52,7%, при 10 она 70,7%, при 15 она 95,1%. Рядом лежит `next_sequence()`, которым id можно было бы делать уникальными.

## Причина 3: глобальный кэш цен связывает тесты

```python
_PRICE_CACHE = {}                         # shop.py:6
def load_price(sku, catalog):             # shop.py:11-17
    if sku in _PRICE_CACHE:
        return _PRICE_CACHE[sku]          # цена из ЛЮБОГО прошлого каталога
    ...
```

Кэш не знает, из какого каталога пришла цена. Прямая проверка в свежем процессе: `load_price('pen', CATALOG)` вернул 1.5, затем `load_price('pen', PROMO)` тоже вернул 1.5 вместо 1.2.

Теперь тест `test_pricing.py:11-15`:
- Честный итог по промо-каталогу: 2·1,2 + 10,0 = 12,4. Проверено в свежем процессе: `total` = 12.4.
- Тест ждёт 15,5. Это ровно сумма по обычному каталогу 2·1,5 + 12,5 (проверено: 15.5). Ожидаемое значение записано, когда кэш уже был заполнен обычными ценами. Тест закрепляет баг как норму.

В полном наборе он зелёный потому, что `test_orders.py` выполняется раньше и кладёт в кэш нужные цены. Перо (`pen` = 1,5) попадает туда из `test_add_items` (`test_orders.py:20-23`), книга (`book` = 12,5) из `test_receipt` (`test_orders.py:38-43`).

Какой тест что держит (каждый запуск отдельным процессом):

| Что запущено | Результат |
|--------------|-----------|
| `test_add_items` + `test_receipt` + `test_promo_order_total` | 3 passed |
| `test_receipt` + `test_promo_order_total` (пера нет в кэше) | `assert 14.9 == 15.5` |
| `test_add_items` + `test_promo_order_total` (книги нет в кэше) | `assert 13.0 == 15.5` |
| `pytest test_pricing.py`, 30 запусков подряд | 30 из 30 красных |
| `pytest -k promo` | красный |
| `pytest test_pricing.py test_orders.py` (pricing первым, seed=1, чтобы убрать причину 1) | красными стали три теста: `test_promo_order_total` (12.4 вместо 15.5), `test_add_items` (2.4 вместо 3.0), `test_receipt` (10.0 вместо 12.5) |

Связь симметрична: кто первым положил цену в кэш, тот и «победил». Если промо-тест идёт раньше, он ломает обычные тесты заказов: они получают промо-цены при обычном каталоге.

Про ваше «иногда краснеет, если запустить только `test_pricing.py`». У меня отдельный файл красный всегда (30 из 30), случайности в этом тесте нет. Единственный найденный механизм, при котором он зелёный, это кэш, заполненный другими тестами в том же процессе. Поэтому результат зависит от способа запуска: весь набор, один файл, `-k`, один тест из IDE, другой порядок аргументов. Если у вас отдельный файл бывает зелёным, воспроизвести это я не смог. Причину в вашем окружении назвать не берусь [UNKNOWN].

## Причина 4: `items=[]` по умолчанию (мина под порядок тестов)

```python
def __init__(self, customer, items=[]):    # shop.py:32-34
    self.items = items
```

Подтверждено: после `Order('alice').add('pen', 2)` объект `Order('bob').items` равен `[('pen', 2)]`, и это тот же список (`a.items is b.items` → True).

Сейчас тесты проходят по везению. `test_new_order_is_empty` (строка 9) стоит раньше `test_add_items` (строка 20), оба вызывают `Order(name)` без `items`. В обратном порядке (`test_add_items`, потом `test_new_order_is_empty`) второй падает: `assert [('pen', 2)] == []`. Между двумя одинаковыми запусками это ничего не меняет. Но случайный порядок, параллельный запуск или повторный прогон теста в том же процессе включат этот сбой. В работе дефект хуже: товары любого заказа, созданного без `items`, попадают во все остальные такие заказы.

## Причина 5: граница секунды в `test_receipt`

`receipt` берёт `datetime.now()` (`shop.py:59`). Тест через доли миллисекунды вызывает `datetime.now()` ещё раз и сравнивает строки с точностью до секунды (`test_orders.py:43`). Если секунда сменилась между двумя вызовами, тест красный.

- Детерминированное доказательство: с подменёнными часами 12:00:00.999999 → 12:00:01.000000 тест падает на `test_orders.py:43`. В пределах одной секунды проходит.
- Частота: 10 расхождений на 976 262 повторных проверки, то есть 1,0·10⁻⁵ на одно выполнение. Окно между вызовами (`receipt()` плюс второй `now()`): медиана 16,9 мкс, p99 38,4 мкс.

Ваши красные прогоны это не объясняет, но на CI с тысячами запусков этот тест когда-нибудь тоже упадёт.

## Что проверил и отбросил

- Плагины pytest: при выключенных те же падения в тех же долях.
- `test_sequence_increments`: счётчик под локом, в 40 прогонах не падал. Хрупкий только если другой код создаёт `Order` между двумя строками теста.
- Плавающая арифметика в `total`: порядок суммирования зависит от порядка вставки в dict и детерминирован. 3.0, 12.4, 15.5 стабильны.
- Гонка check-then-set в `load_price` и `time.sleep(0.001)`: потоков в тестах нет, на результат не влияют. Это латентный дефект на случай многопоточности.

## Что предлагаю сделать

Порядок важен: сначала кэш, потом правка ожидания. Иначе красный тест покажется новой поломкой.

1. Кэш цен (причина 3). Если кэш нужен только для имитации чтения, достаточно убрать его: `load_price` возвращает `catalog[sku]`. Если за ним настоящее дорогое чтение, кэш должен принадлежать объекту, владеющему каталогом (например, `PriceList` со своим словарём), а не модулю. Ключ `(id(catalog), sku)` не рекомендую: `id` переиспользуется после сборки мусора. Затем исправить ожидание в `test_pricing.py:15` с 15,5 на 12,4. Фикстура, очищающая `_PRICE_CACHE`, без исправления кэша только спрячет проблему. После неё тест станет стабильно красным (12,4 против 15,5), и это покажет, что он записал баг.
2. Id заказа (причина 2). `uuid.uuid4().hex[:12]` либо `f"ORD-{next_sequence():06d}"`, если достаточно уникальности внутри одного процесса. После перезапуска счётчик начнётся заново, для сквозной уникальности нужен uuid или последовательность в хранилище.
3. Основная категория (причина 1). Убрать set из пути, где важен порядок: `list(dict.fromkeys(category_of[sku] for sku, _ in self.items))` сохраняет порядок появления. Нужно решение владельца: «категория первого добавленного товара» или «категория с наибольшей суммой». Текущий тест (книга первой и дороже, яблоки вторыми и их больше по штукам) эти варианты не различает. Надо добавить тест, где яблоко добавлено первым, а книга вторым. Вариант «по числу штук» дал бы `food` и противоречит тесту.
4. Список по умолчанию (причина 4): `def __init__(self, customer, items=None): self.items = [] if items is None else list(items)`.
5. Часы в `receipt` (причина 5): передавать время параметром (`receipt(order, catalog, now=None)`), в тесте подать фиксированный `datetime`. Это самое дешёвое исправление и самое малозначимое по частоте.

Чтобы такое ловилось сразу, а не раз в неделю:
- В CI прогонять набор с несколькими значениями `PYTHONHASHSEED` (я показал, что оно меняет исход) и с перемешиванием порядка тестов. Например, плагин pytest-randomly: он у вас не установлен, я его не проверял.
- Прогонять каждый тестовый файл и каждый тест отдельным процессом. `test_pricing.py` один красный с первого запуска показал бы связь через кэш.
- Не добавлять повторы (rerun) и пометки «нестабильный»: во всех пяти случаях причина находится и исправляется в коде.

## Ограничения

- Серии прогонов небольшие (40 и 30). Доли согласуются с теорией для причин 1 и 2, но это не точные оценки.
- Окружение одно (Windows, Python 3.13.2). На других версиях Python конкретные seed дадут другие значения, механизм тот же.
