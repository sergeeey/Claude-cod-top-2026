# client_lib 2.0.0: правда ли, что она полностью обратно совместима с 1.x

## Вывод

Нет, утверждение в CHANGELOG неверно ("fully backward compatible", "existing client code keeps working without any changes"). На v2 `client_app.py` даёт из 7 шагов 4 явных сбоя и 2 тихо неверных числа. Без изменений работает один шаг.

Номер 2.0.0 по semver допускает несовместимость. Неверна именно фраза о совместимости и формулировки раздела "Changed", которые прячут поломки.

## Что проверено и как

Python 3.13.2. Хеши sha256 (первые 8 символов): `client_app.py` ebc718ed, `CHANGELOG.md` c2ee1abf, `v1/client_lib.py` be063cd8, `v2/client_lib.py` 6da133d2.

- Запуск `python -B client_app.py v1` и `python -B client_app.py v2`, сравнение вывода через diff.
- `python -B compat_probe.py` (файл лежит в папке) сравнивает v1 и v2 на одинаковых входах. Всего 104 моих кейса: 77 совпали, 27 разошлись. Набор подобран мной и не является полным покрытием.
- Чтение исходников обеих версий и grep по `client_app.py`.

Базовой линии в виде тестов нет: в папке нет тестов, requirements, lockfile и pyproject. Единственная спецификация поведения — вывод `client_app` на v1: все 7 шагов отработали, код выхода 0.

Опаснее всего два тихих изменения, subtotal и shipping: исключения нет. Валидация симметрична, поэтому перепутанные аргументы `shipping_cost` её проходят. Кроме того, `step()` глотает исключения, и в обеих версиях код выхода 0, так что "задача завершилась успешно" поломку не показывает.

## Расхождения с CHANGELOG

- "Parameter naming unified" скрывает переименование `currency` (ломает вызов по ключу) и смену порядка аргументов в `shipping_cost`. Имена параметров там те же, менялся порядок.
- "Record fields aligned with catalog terminology": `name` стало `title`, чтение записей ломается. У самого `client_app` в CATALOG ключ как раз `name`.
- "invoice_total defaults aligned with accounting" означает +20 % к любой сумме у вызовов без `tax_rate`. С явным `tax_rate` результаты те же (9 из 9 кейсов).
- "Exception hierarchy clarified" ломает `except KeyError`. Заодно меняется текст ошибки: `str(NotFoundError('Z-999'))` был `'Z-999'` (в кавычках), стал `Z-999`.
- `normalize_priority` в разделе 2.0.0 не упомянут вообще. Регистронезависимость пропала молча (из 13 кейсов разошлись 5).

## Что только выглядит опасным и не ломает

- `_to_cents` стал `_as_cents`. Это приватный хелпер, в `client_app` он не используется (grep: 0 совпадений). Сломает только того, кто импортирует его напрямую.
- `format_price(19.9, "EUR")` с позиционной валютой работает так же. Все 22 кейса `format_price` совпали.
- У `parse_record` новый `strict=False` по умолчанию, поведение прежнее. `strict=True` отвергает qty 0 и -3, как заявлено.
- `format_price` теперь принимает `Decimal` и числовые строки (v1 их отвергал). Это расширение, как заявлено. Для nan тип ошибки сменился с `ValueError` на `ValidationError`, а это подкласс `ValueError`, так что `except ValueError` работает.
- `except LookupError` по-прежнему ловит `NotFoundError`. `ValidationError` остался подклассом `ValueError`.
- Вызовы `shipping_cost` по ключам (`weight_kg=`, `distance_km=`): 16 из 16 совпали.
- `lookup` при успехе и `invoice_total` с явным `tax_rate` не изменились.

Вне темы, есть в обеих версиях: `format_price(-0.5)` даёт `-1.50 USD`, потому что целочисленное деление округляет вниз. Это не регрессия.

## Что предлагаю

Если совместимость действительно обещана, исправить v2:
1. `format_price`: вернуть `currency`. Можно принимать `currency_code` как псевдоним.
2. `parse_record`: оставить `name`, а `title` добавить как дополнительный ключ.
3. `invoice_total`: вернуть дефолт 0.0. Если 0.2 нужен бизнесу, это отдельное явное решение для клиентов.
4. Вернуть `NotFoundError(KeyError)`.
5. `normalize_priority`: вернуть `.lower()`.
6. `shipping_cost`: вернуть порядок `(weight_kg, distance_km)`. Если порядок менять нужно, сделать аргументы только ключевыми и дать период предупреждений.

Если изменения намеренные, переписать CHANGELOG: убрать фразу о совместимости, добавить раздел "Breaking changes" по таблице выше и руководство по миграции. Клиентам при этом нужно:
- передавать `currency_code=`;
- читать `r['title']`;
- явно указывать `tax_rate=0.0`;
- ловить `lib.NotFoundError` (работает в обеих версиях);
- приводить приоритет к нижнему регистру;
- вызывать `shipping_cost` по ключам.

Дополнительно стоит завести контрактные тесты на обе версии (основой может быть `compat_probe.py`) и сделать так, чтобы `client_app` возвращал ненулевой код при FAILED.
