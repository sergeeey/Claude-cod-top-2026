## Что только выглядит опасным

- `_to_cents` → `_as_cents` (v1:17, v2:19) — приватный хелпер. `client_app.py` не обращается к атрибутам с подчёркиванием (проверено разбором AST в тесте). Результат `format_price` для int/float не изменился ни на одном из 3315 значений: сетка от -3.00 до 30.00 с шагом 0.01 плюс граничные 0.005, 1.005, 2.675, 1e6+0.01.
- `format_price` принимает `Decimal` и числовые строки. Это только расширение. Мелочь: `format_price("19.9")` раньше давал `ValidationError`, теперь `19.90 USD`. Заметит только клиент, который использовал отказ как проверку ввода. `client_app.py` строк не передаёт.
- Новый `parse_record(..., strict=False)`: по умолчанию поведение прежнее, `qty=0` принимается.
- `format_price(float('nan'))` раньше падал голым `ValueError`, теперь `ValidationError`. Он наследует `ValueError`, так что `except ValueError` ловит оба случая.
- Без изменений: `ValidationError(ValueError)`, `lookup` при попадании, ошибка числа полей в `parse_record`, проверки `shipping_cost` на `<= 0`.

Старая особенность, не регрессия: `format_price(-1.5)` даёт `-2.50 USD` в обеих версиях (`cents // 100` округляет вниз). Править это в 2.x без объявления не стоит, на вывод могут опираться клиенты.

## Что предлагаю

Решение по каждому пункту за вами: вернуть совместимость или оставить изменение и объявить его ломающим.

**Вариант A, вернуть совместимость в 2.0.x.** Патч `v2_proposed/client_lib.py`, все отличия от `v2` помечены `# COMPAT`:
- `NotFoundError(KeyError)`. `KeyError` сам является `LookupError`, так что оба варианта `except` работают.
- `format_price(amount, currency_code="USD", *, currency=None)`: старое имя как устаревший алиас с `DeprecationWarning`.
- `parse_record` возвращает оба ключа, `name` и `title`.
- `invoice_total(..., tax_rate=0.0)`.
- В `normalize_priority` вернуть `.lower()`.
- В `shipping_cost(weight_kg, distance_km)` вернуть прежний порядок.

**Вариант B, оставить как есть и честно объявить.** Если 20% по умолчанию и новый порядок аргументов нужны бизнесу, тогда:
1. Убрать из CHANGELOG фразу про полную совместимость. Добавить раздел «Breaking» со всеми шестью пунктами с конкретными значениями и памяткой по миграции.
2. Для двух молчаливых изменений одного changelog мало. `shipping_cost` лучше сделать с аргументами только по ключевому слову (`def shipping_cost(*, weight_kg, distance_km)`) с переходным периодом, а `invoice_total` — требовать явный `tax_rate`. Тогда ошибка станет громкой, а не неверной суммой в счёте.

Порядок работы: сначала пункты 1 и 2 (молчаливые, касаются денег), затем 3-6. Тесты стоит оставить в CI: они запускаются на любой версии через `LIB_DIR` и должны быть зелёными для каждого 2.x-релиза, который объявляет себя совместимым.
