# Почему тесты модуля заказов то зелёные, то красные

## Коротко

Нестабильность создают пять независимых дефектов в `shop.py` и в тестах. Три из них дают то, что вы видите. Остальные два проявляются редко или только при смене порядка тестов.

| # | Причина | Где | Что падает | Как проявляется |
|---|---------|-----|------------|-----------------|
| 1 | Порядок элементов `set` зависит от `PYTHONHASHSEED` | `shop.py:48` | `test_primary_category` | в каждом новом процессе случайно, около 50% |
| 2 | ID заказа: `random.randint(1, 40)` | `shop.py:28` | `test_order_ids_unique` | случайно, около 23% |
| 3 | Кэш цен `_PRICE_CACHE` общий для процесса, ключ только `sku` | `shop.py:6, 11-17` | `test_promo_order_total`; при другом порядке ещё `test_add_items` и `test_receipt` | зависит от порядка и состава запуска |
| 4 | Изменяемый аргумент по умолчанию `items=[]` | `shop.py:32` | `test_new_order_is_empty` | зависит от порядка |
| 5 | Сравнение времени на равенство с точностью до секунды | `test_orders.py:43` | `test_receipt` | очень редко, около 1e-5 на запуск |

Исходные файлы я не менял. Исправленная копия лежит в `fixed/`.

## Что подтверждено и как

Python 3.13.2, pytest 8.4.2. Плагинов случайного порядка или параллельного запуска нет (`pip list`). Конфигурации pytest в папке нет.

**Весь набор, 40 запусков подряд без изменений в коде** (`pytest -q`):
- зелёных 11 из 40 (8 passed);
- `test_primary_category` упал в 22 запусках из 40 (`assert 'food' ...`);
- `test_order_ids_unique` упал в 10 из 40 (`assert 4 == 5`, один раз `3 == 5`);
- оба упали вместе в 3 запусках.

Модель из пунктов 1 и 2 даёт долю зелёных 0,771 × 0,5 = 0,386. Наблюдаемые 0,275 отличаются примерно на 1,4 стандартного отклонения, это согласуется.

### 1. `primary_category` зависит от хеш-сида (`shop.py:47-51`)

`categories()` возвращает `list({...})`, то есть порядок множества строк. Для строк он определяется `PYTHONHASHSEED`, который Python выбирает случайно при каждом запуске. `primary_category()` берёт `[0]` этого списка.

Проверка: `diag_flaky.py`, раздел A, сиды 0-19. Для `book` + `apple` получилось 10 раз `books` и 10 раз `food`. Результат полностью определяется сидом: при `PYTHONHASHSEED=1` всегда `books`, при `0` всегда `food`.

В продакшене это тоже дефект: основная категория заказа меняется от перезапуска к перезапуску. Что считать основной категорией, код не определяет. Тест неявно предполагает «первая добавленная» (`book` добавлен раньше `apple`). Тот же ответ дают «по сумме» (12,5 против 1,2) и «по алфавиту». Выбор правила за вами, его нужно записать в код и в тест.

### 2. Коллизии ID заказов (`shop.py:27-28`)

В тесте создаётся 5 заказов, ID берутся из 40 значений. Вероятность совпадения: 1 − (40·39·38·37·36)/40⁵ = 0,2289. Монте-Карло на реальном `Order()`, 200 000 попыток: 45 749 коллизий, 0,2287. Прямой вызов самого теста 5000 раз в одном процессе: 1082 падения, 0,216. Это примерно на 2 стандартных отклонения ниже теории, а на 200 000 попытках расхождения нет.

Это проблема не только теста. В реальной системе два заказа с одним ID при тысячах заказов случаются почти наверняка.

### 3. Общий кэш цен (`shop.py:6, 11-17`)

`_PRICE_CACHE` живёт на уровне модуля, ключ только `sku`, каталог в ключ не входит. Первый вызов `load_price("pen", X)` навсегда задаёт цену `pen` для всех каталогов до конца процесса.

Матрица порядков (`diag_order.py`, `PYTHONHASHSEED=1`, чтобы убрать пункт 1):

| Запуск | Результат |
|--------|-----------|
| `test_orders.py test_pricing.py` (порядок по умолчанию) | 8 passed |
| `test_pricing.py` отдельно | fail: `assert 12.4 == 15.5` |
| `test_pricing.py::test_promo_order_total` отдельно | fail, то же |
| `test_pricing.py test_orders.py` | 3 failed: promo `12.4`, `test_add_items` `2.4 == 3.0`, `test_receipt` `10.0 == 12.5` |
| `test_add_items` → promo | fail: `13.0` (`pen` из кэша, `book` нет) |
| `test_add_items` + `test_primary_category` → promo | fail: `13.0` (`primary_category` не вызывает `total`, кэш не пополняет) |

`test_promo_order_total` ожидает 15.5, а правильная цена по акционному каталогу `PROMO` равна 2·1,2 + 10,0 = **12,4**. 15,5 получается только когда в кэше уже лежат обычные цены. Их кладут туда `test_add_items` (`pen`) и `test_receipt` (`book`). В обычном порядке файлов тест зелёный по неверной причине: неверный результат закреплён в самом тесте.

Расхождение с вашим описанием: вы пишете, что `test_pricing.py` в одиночку краснеет «иногда». У меня он упал 10 из 10 запусков, то есть стабильно. Случайной составляющей в нём я не нашёл. Вероятнее всего, «иногда» означает, что вы запускаете его то отдельно (красный), то в составе всего набора (зелёный).

В продакшене это денежная ошибка: после первого обращения к обычному каталогу акционные цены не применяются, и наоборот.

### 4. `items=[]` в `Order.__init__` (`shop.py:32`)

Список по умолчанию создаётся один раз и общий для всех заказов без явных `items`. `diag_flaky.py`, раздел E: `a.items is b.items` равно `True`, а свежий `Order("carol")` уже содержит `[('pen', 2)]`.

Порядок `test_add_items` → `test_new_order_is_empty` даёт fail (`assert [('pe...`). Обратный порядок, он же порядок в файле, проходит. Сейчас тест зелёный случайно и покраснеет, если порядок поменяется (плагин случайного порядка, `-k`, перенос теста). В коде это утечка позиций одного клиента в заказ другого.

### 5. Сравнение времени с точностью до секунды (`test_orders.py:43`)

`receipt()` берёт `datetime.now()`, потом тест берёт его ещё раз и требует равенства строк с секундами. Окно между двумя вызовами: медиана 11,5 мкс, максимум 1,3 мс (`diag_flaky.py`, раздел C). Вероятность падения порядка 1,2·10⁻⁵ на запуск. На ваши наблюдения это не влияет, но дефект настоящий. Это расчёт по измеренному окну, само падение я не воспроизводил.

## Что проверено и причиной не является

`test_sequence_increments` проверяет только разницу соседних значений счётчика, защищённого блокировкой. Однопоточно он падать не может. Абсолютное значение счётчика зависит от порядка, но тест его не проверяет.

## Что предлагаю сделать

1. `shop.py`: убрать глобальный `_PRICE_CACHE`. Если медленная загрузка цены настоящая (в коде есть `time.sleep(0.001)`), привязать кэш к объекту каталога или ключу `(catalog_id, sku)` с явной инвалидацией. Не прятать проблему фикстурой, которая чистит кэш: продуктовая ошибка останется.
2. `Order.__init__(self, customer, items=None)` и `self.items = [] if items is None else list(items)`.
3. ID заказа: `uuid4` либо номер из `next_sequence()`. Второй вариант уникален только внутри процесса.
4. `categories()`: детерминированный порядок, например `list(dict.fromkeys(...))` (первая добавленная). Выбрать правило «основной категории» и зафиксировать его в тесте.
5. `test_promo_order_total`: ожидаемое значение `12.4`.
6. `test_receipt`: проверять, что `printed_at` лежит между временем до вызова (с обнулёнными микросекундами) и после, а не равенство. Либо передавать часы в `receipt()`.
7. Добавить тесты, которые ловят эти ошибки напрямую: заказы не делят `items`, каталоги не смешиваются в `load_price`.
8. Не перезапускать и не помечать тесты как нестабильные: все пять причин детерминированы и исправляются в коде.
