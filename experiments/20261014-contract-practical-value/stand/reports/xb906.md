# service.py: на что уходит время и что с этим делать

Все числа получены на одной машине (Windows 11, Python 3.13.2, 24 логических ядра) на данных из datagen.py. Это случайные слова, а не боевые запросы.

## Коротко

Время уходит не туда, куда смотрит bench.py. Есть четыре независимые причины, каждая стоит 0,2-0,6 с на пачке из 1200 запросов. Поодиночке исправление любой даёт только 1,1-1,6x, вместе они дают 23,6x на N=1200: 1,95 с против 0,082 с (медианы по 5 и 7 повторам).

1. `STOP_WORDS` (service.py:8) это список из 400 строк, а не множество. Его возвращает `rng.sample(...)` в datagen.py:25-27. Проверка `token in STOP_WORDS` (service.py:68) сканирует до 400 строк на токен. Стоп-слова составляют 13,2% токенов, остальные 86,8% проходят весь список (cold_paths.out).
2. `load_aliases()` (service.py:61) читает и разбирает aliases.tsv заново на каждом запросе: 202 мкс на запрос.
3. Регулярное выражение на 400 альтернатив собирается заново на каждом запросе (service.py:62): 261 мкс. Затем `alias_re.fullmatch(token)` (service.py:72) стоит 70 мкс на 60 токенов, а `token in aliases` стоит 2,4 мкс.
4. `encode_batch` (service.py:100-104) делает `payload += chunk` для `bytes`. Байты неизменяемы, каждое `+=` копирует весь накопленный буфер, поэтому затраты растут как N^2. На N=1200 это 0,28 с из 1,95, на N=19200 это 75 с из 103 (73%).

Результат обработки не меняется. Побайтовый sha256 вывода совпал на всех N от 150 до 19200 во всех повторах и на 12 вариантах ablation.

Предлагаемый патч лежит в `service_fast.py`. Файл service.py я не менял, он остался эталоном для тестов.

### Достижима ли целевая сложность

Графа здесь нет, поэтому ловушка про плотные графы и O(N log N) к этому входу не относится. Модель по коду и замерам:

- Исходная: process ~ N*(A + T*S) (A строк в aliases, T токенов, S=400 стоп-слов), encode ~ N^2 по числу копируемых байт.
- Целевая: Theta(N*T) на пачку плюс Theta(A) один раз. Ниже опуститься нельзя, каждый токен надо прочитать.
- Достигнута: наклон 1,06 на 11 размерах, зависимость от A убрана (наклон 0,08). Дальше имеет смысл трогать только константу в json.dumps и цикле.

## 3. Почему bench.py показывает странные цифры

Всё проверено замерами.

1. Шесть запусков bench.py подряд без изменений кода. plain: 1,687 / 1,596 / 1,749 / 1,789 / 1,634 / 1,891 с. «dedupe gain»: -37,7% / +0,5% / +3,1% / +4,7% / -8,4% / +10,1%. В сгенерированных данных 1200 разных текстов из 1200 (profile_baseline.out), dedupe ничего не отбрасывает и делает ту же работу плюс `set`. Эти «выигрыши» и «проигрыши» это шум.
2. По одному измерению на режим, без прогрева и повторов, порядок фиксирован (plain, затем dedupe). Таймер захватывает генерацию данных (`make_requests` 0,042 с, 2-3% от 1,4-1,9 с).
3. Большой разброс между сессиями на одной и той же работе. Оригинал на N=1200: 1,40 с (лучшее из 5 в профиле), 1,83 с (медиана первого прогона scaling), 1,95 с (второго), 1,44-2,14 с на пяти повторах в ablation. Разницы меньше ~30% между одиночными запусками на этой машине ничего не значат. Отношения внутри одного вперемешанного прогона надёжнее абсолютных секунд.
4. Размер пачки в bench.py фиксирован (N=1200), а стоимость запроса у оригинала зависит от N: 938 мкс при N=150, 1622 при 1200, 5350 при 19200 (из-за `bytes +=`). Число из bench.py не переносится на другой размер пачки.
5. `dedupe` не ускоряет ту же функцию. Он отбрасывает ответы для запросов с повторяющимся текстом, даже если `id` разные. Тест `test_dedupe_is_not_output_preserving` показывает `[1,2,3]` против `[1,3]`. Строка «same output: True» в bench.py выполняется только потому, что в генераторе нет повторов. На боевом трафике с повторами она станет False.
6. Таймер не виноват: шаг `time.time()` на этой машине 0,24-0,48 мкс (env_check.py).

Для bench.py: `time.perf_counter`, генерацию данных вынести из таймера, 5 и больше повторов с медианой и разбросом, прогрев, чередование режимов, несколько N, отдельная сверка выводов. `dedupe` либо убрать из сравнения скорости, либо проверять на данных с повторами и называть изменением поведения. Готовые образцы: `ablation.py` (N=1200) и `scaling.py`.

## 4. Что предлагаю сделать

По вкладу на N=1200 (ablation):

1. `dict` вместо regex (service.py:62, 72): +0,63 с. `alias_re.fullmatch(token)` истинно ровно тогда, когда token равен одному из ключей, то есть это `token in aliases`. Ключи экранированы `re.escape`, пустым токеном `split()` не бывает. Проверено тестами с ключами-метасимволами (`a.b`, `c|d`, `(x)`, `e*`, `[ab]`, `x{2}`, `^caret`, `dollar$`), пустой целью, дубликатами ключей, юникодом.
2. `STOP_WORDS` в `frozenset` (service.py:8): +0,49 с.
3. Загружать aliases один раз на пачку, а не на запрос (service.py:61): +0,45 с.
4. `b"".join(...)` в `encode_batch` (service.py:100-104): +0,22 с на N=1200, а на больших N основная часть времени (75 из 103 с на N=19200).
5. Исправить bench.py по разделу 3.

Пункты 1-4 собраны в `service_fast.py`. Там `handle_request(request, aliases=None)`, `process_batch` и `encode_batch` с прежними сигнатурами. Неизменённые `CONFIG`, `STOP_WORDS`, `describe_failure`, `load_aliases`, `summarize` импортируются из service.py. Применить можно заменой тел этих трёх функций в service.py.

Не советую:
- переписывать `validate_settings` и `describe_failure` (11,5 мкс один раз и 9,8 мкс на сбой);
- считать `dedupe` оптимизацией, он меняет вывод;

### Два решения для владельца

1. Оригинал перечитывает aliases.tsv на каждый запрос, поэтому правка файла посреди пачки видна со следующего запроса. Мой вариант читает файл один раз на пачку, правка видна со следующей пачки. Если нужна горячая перезагрузка на уровне запроса, кэш можно ключевать по `(st_mtime_ns, st_size)`, это один `os.stat` на запрос. В этой папке ничего не правит файл в процессе, боевой сценарий мне неизвестен [UNKNOWN].
2. `STOP_WORDS` в service_fast это снимок множества при импорте. Оригинал смотрит в список, который теоретически можно изменить в рантайме. В этой папке никто этого не делает.

Одинаково с оригиналом (проверено тестами):
- битый aliases.tsv: каждый запрос становится сбоем с тем же текстом ошибки;
- отсутствующий файл: `FileNotFoundError` из `process_batch`, пустой список запросов файла не трогает;
