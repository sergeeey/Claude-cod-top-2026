# Отчёт: тесты для money.py и найденные дефекты

## Итог

В модуле семь расхождений с его собственными docstring-ами.

- **Заказ ровно на 1000 ₽** не получает скидку 5 %.
- **Возврат от −100 до −999,99** печатается как `- 123,00`, с пробелом после минуса.
- **Половина копейки** округляется к чётному вместо «от нуля». Это задевает и чек, и сумму к оплате.

Покрытие выросло с 0 % до 100 % строк и 100 % ветвлений, но качество подтверждают не эти числа. Из 51 вручную внесённой ошибки тесты поймали все неэквивалентные. На оригинале 60 тестов падают на настоящих багах.

Обычный `pytest` зелёный (152 passed, 60 xfailed), потому что известные баги помечены `xfail(strict=True)`. Зелёный прогон не значит «багов нет».

## 1. Базовая линия до работы

```
python -m coverage run --branch --source=. -m pytest -q    # тестов нет, exit=5
money.py   Stmts 35   Miss 35   Branch 10   BrPart 0   Cover 0%
```

Цели записаны в `evidence/targets.txt` до написания тестов:
- строки ≥ 90 % (число из контракта);
- ветвления ≥ 90 % отдельно (моя цель);
- набор < 10 с (контракт);
- ≥ 90 % убитых неэквивалентных мутантов.

При базе 0 % и 35 операторах цели достижимы, контрактные числа не пересматривал.

Первый прогон до настройки занял 16,15 с (200 примеров hypothesis, с минимизацией контрпримеров). Теперь профиль по умолчанию — 100 примеров без минимизации. Для разбора настоящего падения есть `--hypothesis-profile=money-debug`.

## 4. Проверка на внесённых ошибках

51 мутант эталона, по одной правке на каждый. Паттерн замены проверяется на ровно одно вхождение, мутант проверяется компиляцией. Группы:
- разбор — 12;
- округление — 9;
- формат — 11;
- ставка — 11;
- скидка — 8.

Итог скрипта: убито 49, выжило 2, недействительных 0 (прогон повторён дважды, результаты идентичны).

- **M59** («0.10 записано как 0.1») — эквивалентный мутант, добавлен намеренно как контроль честности подсчёта.
- **M30** («ноль сохраняет минус», отключена защита `if q == 0: q = abs(q)`). В эталоне эквивалентен: исправление BUG-4 считает знак через `q < 0`, и защита становится мёртвым кодом. На структуре оригинала та же правка убивается, падают 4 теста.

Итого: 49 из 50 по скрипту, после разбора M30 — 49 из 49.

Ограничения:
- Мутанты придумал тот же автор, что и тесты.
- Это локальные правки одного места, они не доказывают отсутствие дыр в остальном.
- Агент `reviewer` по условию задания не запускался.

## 5. Почему тесты не подогнаны под вывод

- Ожидания выведены из docstring-ов. Оракул считает на дробях (`Fraction`), а не на Decimal и не кодом модуля. Сам оракул сверен с руками посчитанными значениями.
- 188 тестов-примеров: таблицы из docstring, границы 999,99 / 1000 / 4999,99 / 5000, возвраты, пустые и мусорные строки, большие суммы, сквозной сценарий «строки заказа → скидка → чек».
- 24 свойства hypothesis: сверка с оракулом, идемпотентность, симметрия, монотонность, формат чека по регулярному выражению.
- Свойство «разбор после форматирования возвращает то же число» оставлено, но BUG-4 оно само не видит: `parse_amount` выбрасывает пробелы. BUG-4 ловит только проверка формата регулярным выражением. Это пример ловушки из контракта: строки покрыты на 100 %, а баг всё равно проходит.
- Известные баги помечены `xfail(strict=True, raises=…)`. После исправления тест даст XPASS, который считается ошибкой, и маркер придётся убрать. Опечатка в тесте за xfail не спрячется.

## 6. Что не проверялось

- `parse_amount` принимает то, чего нет в списке «Допускаются»: `NaN`, `Infinity`, `1e5` (→ `Decimal('1E+5')`), `1_000` (→ `1000`). Проверено вручную, в `repro.py` не вошло. Тестов на это нет, решение за владельцем. `NaN` дальше ломает сравнения в `discount_rate`.
- Порог скидки даёт «обрыв»: 999,99 платит 999,99, а 1000,00 после исправления платит 950,00. Это следует из docstring, не баг.
- Входы не-Decimal (float, None, str) и изменённый глобальный контекст Decimal не проверялись.
- Исправленная копия проверена только этим набором (212 из 212) и мутациями, на `NaN` и `Infinity` не проверялась.
