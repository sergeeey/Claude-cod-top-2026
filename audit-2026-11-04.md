## Findings and fixes

### F1 — The null verdict ignores a beneficial measured subset

**MEDIUM; #540; [CODE], [VERIFIED-SYNTHETIC].** In [constraint_rank.py:295](https://github.com/sergeeey/Claude-cod-top-2026/blob/1792744c9f3b49f6aa5398f52dd6c86c9b0fb8dc/skills/extensions/boyko-constraint-engine/scripts/constraint_rank.py#L295), the trade-off branch requires a positive solo gain. At line 315, a nonpositive all-fixed gap then yields `NO_CONSTRAINT_DETECTED` even when another measured subset improves the metric.

Reproduction: full eight-row table for A/B/C; baseline, all singletons, AC, BC and ABC are 0.50; AB is 0.90. Every row has `guard_changed=0`; noise=0.005, repeats=4, MCID=0.03. Actual output:

```text
table_complete: true
total_gap: 0.0
pairwise A+B: interaction 0.4, complementary (need both)
best_clean_subset: [A, B], value 0.9
verdict: NO_CONSTRAINT_DETECTED
```

This is not merely an absent higher-order interaction estimate: the beneficial pair is explicitly measured and already recognized elsewhere in the same result. The skill's verdict table maps the null verdict to doing nothing, so consumers can discard a measured improvement.

**Fix:** Before issuing a null result, examine all measured subsets for gains above the relevant uncertainty/practical threshold. If the all-fixed row cancels a beneficial subset, report a trade-off/non-monotone result and identify that subset; do not equate the all-fixed result with an attainable ceiling in this case. Add this three-candidate control alongside the existing two-candidate cancellation tests. No real-world prevalence claim is made.

### F2 — Underscores do not distinguish verdicts from metadata

**MEDIUM; #541; [CODE], [VERIFIED-SYNTHETIC].** The new `Result` fallback at [build_research_catalog.py:114](https://github.com/sergeeey/Claude-cod-top-2026/blob/1792744c9f3b49f6aa5398f52dd6c86c9b0fb8dc/scripts/build_research_catalog.py#L114) accepts any qualifying bold uppercase token with an underscore. Its comment says the underscore excludes statuses and IDs, but those commonly contain underscores too.

| Input | Base | Target |
|---|---|---|
| `## Result` followed by `**EXP_2026_11_04** was inspected; no verdict was reached.` | `UNKNOWN` | `EXP_2026_11_04` |
| `## Result` followed by `**DRAFT_PENDING_REVIEW**` | `UNKNOWN` | `DRAFT_PENDING_REVIEW` |

The text-to-metadata boundary is affected in both disk and branch records: `parse_verdict` feeds the catalog's `verdict` field. This is evidence contamination, not executable code injection. Positive controls confirm that `## Decision: **GO**` and a long actual verdict now work as intended.

**Fix:** Require unambiguous decision/verdict semantics for generic `Result` sections, or preserve ambiguous candidates separately while leaving `verdict=UNKNOWN`. Add underscore-ID and underscore-status negative controls. Avoid solving this with another punctuation heuristic or an ever-growing list of IDs. Preserve the useful long-token fallback and the existing-output compatibility contract.

The previous audit's correction-ownership/order defects remain outside the modified parser branches; they are not counted as newly introduced defects here. The PR also explicitly discloses the old `_LABEL_VALUE` blank-line performance problem; it is not attributed to this change.

### F3 — Untrusted-code instructions lack an enforceable execution boundary

**MEDIUM guidance gap; #540; [CODE], [VERIFIED-SYNTHETIC].** [system-card.md:38](https://github.com/sergeeey/Claude-cod-top-2026/blob/1792744c9f3b49f6aa5398f52dd6c86c9b0fb8dc/skills/extensions/boyko-constraint-engine/references/system-card.md#L38) places untrusted third-party probe code in a separate folder with `python -I` and argument-based paths. Those precautions do not enforce the adjoining promise that the original system remains untouched.

Trust boundary: third-party probe code runs with the interpreter process's OS authority. Sensitive sinks can include files outside the copy, child processes and network access. A harmless local demonstration ran Python with `-I` and read an explicitly created canary outside the script directory. No secret, private data, network operation or destructive action was involved.

Python documents `-I` as isolation of import paths/environment behavior, not OS resource isolation. [Official Python command-line documentation](https://docs.python.org/3.11/using/cmdline.html#cmdoption-I).

**Fix:** State that a copy/worktree and `-I` protect workflow/import behavior only. Require an existing restricted execution environment with explicit file/network permissions for untrusted probes, or keep the activity to inspection when that boundary is unavailable. An external agent sandbox may provide those controls, but the skill does not state that dependency. This finding concerns an incomplete operational recipe, not an observed sandbox escape.

### F4 — Invalid configuration becomes a plausible numeric result

**LOW; #540; [CODE], [VERIFIED-SYNTHETIC].** [constraint_rank.py:65](https://github.com/sergeeey/Claude-cod-top-2026/blob/1792744c9f3b49f6aa5398f52dd6c86c9b0fb8dc/skills/extensions/boyko-constraint-engine/scripts/constraint_rank.py#L65) uses truthiness for metric direction; cost validation at line 92 checks positivity without finiteness; MCID is never validated before comparisons.

On a one-candidate table increasing from 0.5 to 0.8:

- `higher_is_better="false"` silently means higher-is-better and returns `SINGLE_DOMINANT`.
- `costs={"A": Infinity}` is accepted and produces `cost: Infinity`, `gain_per_cost: 0.0`.
- `mcid=NaN` bypasses threshold comparisons and still yields `SINGLE_DOMINANT`.

Python's default JSON encoder/decoder accepts nonfinite values; therefore the CLI's JSON boundary does not independently reject these cases. [Official Python JSON documentation](https://docs.python.org/3/library/json.html#infinite-and-nan-number-values).

**Fix:** Validate the decoded schema before calculations: real booleans for direction, finite positive costs, and finite nonnegative MCID when provided. Reject nonfinite JSON input/output explicitly. Keep invalid input distinct from missing measurements. These are local bad-input failures, not proof of remote exploitability.
