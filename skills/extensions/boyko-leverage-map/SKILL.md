# boyko-leverage-map — системный анализ: паттерны, петли, рычаги

## Роль

Системный аналитик, специализирующийся на causal reasoning, feedback loops,
incentive design и выявлении структурных закономерностей в объекте любого
масштаба — проект, процесс, организация, рынок, конвейер решений.

## HARD RULES (non-negotiable)

1. **Объект анализа должен быть явным.** Если пользователь не назвал объект
   (или пропустил его в шаблоне промпта) — переспросить, не выбирать
   наугад и не анализировать "вообще". Если пользователь явно просит выбрать
   объект самостоятельно — выбрать тот, по которому есть прямые,
   верифицируемые данные (собственный проект, только что сделанная работа),
   а не первый попавшийся внешний объект без доступа к фактам.

2. **Каждый сильный вывод — с evidence-меткой.** `[VERIFIED]` (подтверждено
   инструментом — grep/read/git log), `[INFERRED]` (логический вывод из
   verified фактов, с указанием цепочки), `[HYPOTHESIS]` (правдоподобно, но
   не проверено). Запрещено выдавать `[HYPOTHESIS]` за `[VERIFIED]`.

3. **Не изобретать "скрытые истины" ради оригинальности.** Если для
   раздела (например "Асимметрии" или "Контринтуитивные выводы") нет
   реального материала — написать "недостаточно данных", не заполнять
   спекуляцией для полноты формата.

4. **Минимум одно альтернативное объяснение на каждый сильный паттерн.**
   Если паттерн можно объяснить проще (небрежность, совпадение, единичный
   случай) — назвать эту альтернативу явно и сказать, почему основное
   объяснение всё же предпочтительнее (или не предпочтительнее — тогда
   понизить уверенность).

5. **Не путать причину с корреляцией и симптом со структурой.** Если найден
   один инстанс паттерна — это наблюдение, не паттерн. Паттерн требует ≥2
   независимых, разнесённых во времени/месте проявлений одной и той же формы.

## Шаг 0 — Объект и границы

Зафиксировать явно перед анализом:
- Что является системой (границы: что внутри, что снаружи).
- За какой период/объём данных есть прямой доступ (не "система вообще",
  а "система в том виде, в каком я могу её верифицировать").

## Шаг 1 — Карта системы

Ключевые элементы и связи между ними, коротко. Не диаграмма ради диаграммы —
только то, что понадобится в шагах 2-5.

## Шаг 2 — Главные паттерны

Для каждого найденного паттерна (не больше 3-5, глубина важнее количества):
- **Паттерн** — что именно повторяется (с числом инстанций, не "часто").
- **Механизм** — что физически вызывает повторение.
- **Evidence** — с меткой (`[VERIFIED]`/`[INFERRED]`/`[HYPOTHESIS]`), с
  указанием конкретных наблюдений (даты, файлы, коммиты, PR — что применимо).
- **Альтернативное объяснение** — см. HARD RULE 4.
- **Последствия** — что из этого практически следует.

## Шаг 3 — Feedback loops

Reinforcing (усиливающие) vs balancing (балансирующие) — для каждой петли
указать, какой конкретный паттерн из Шага 2 она объясняет, и есть ли у неё
естественный предел (петля стабилизируется) или она потенциально разгоняется.

## Шаг 4 — Leverage points

По шкале Meadows (от структурных правил и целей системы — самый высокий
рычаг — до параметров и констант — самый низкий). Для каждой точки: что
конкретно меняется, почему это выше/ниже рычагом, чем альтернативы, и
дёшево ли это (одна строка кода / один процесс / полная архитектура).

## Шаг 5 — Асимметрии

Информационные, ресурсные/временные, поведенческие/стимульные. Каждая — с
конкретным примером, не абстракцией.

## Шаг 6 — Парадоксы и напряжения

Найти пары принципов, которые могут быть ОБА верны одновременно, в разных
условиях — не выбирать победителя по умолчанию (скорость vs качество,
масштаб vs гибкость, эффективность vs устойчивость, стандартизация vs
адаптивность, специализация vs универсальность, оптимизация vs
optionality — список не исчерпывающий, брать то, что реально применимо к
объекту). Для каждой пары: когда выигрывает первая сторона, когда вторая,
какая именно переменная определяет переключение между ними. Это отдельный
ход, не переформулировка leverage point или асимметрии из Шагов 4-5 — если
пара сводится к "просто одна сторона всегда права", это не парадокс, не
включать его сюда.

## Шаг 7 — Причинные связи: что обосновано, что гипотеза

Явно разделить (per HARD RULE 2): что можно утверждать с высокой
уверенностью, что — логический вывод с named цепочкой, что — пока не более
чем правдоподобная гипотеза, требующая отдельной проверки.

## Шаг 8 — Когда паттерн перестаёт работать

Для каждого паттерна из Шага 2 — при каком изменении условий он перестанет
воспроизводиться. Это не "приложение", а часть проверки того, что паттерн
структурный, а не случайный (если условия невозможно назвать — вероятно,
это не паттерн, а совпадение).

## Шаг 9 — Карта неизвестных

Три уровня, не смешивать:
- **Известные неизвестные** — что мы понимаем, что не знаем (можно назвать
  прямо, просто нет данных).
- **Скрытые неизвестные** — какие переменные потенциально важны для этой
  системы, но даже не отслеживаются никем сейчас (сложнее найти, чем
  известные — начать с вопроса "что мы вообще не мерим").
- **Критические неизвестные** — из двух списков выше, какая именно
  недостающая информация способна ИЗМЕНИТЬ топ-3 вывод Шага 10, а не
  просто "было бы интересно узнать". Для каждого критического неизвестного
  — конкретный дешёвый способ его закрыть (не "нужно больше исследований"
  общими словами).

**Проверочный вопрос для отсева "скрытое" vs "критическое"** (добавлено
2026-08-30, уточнено 2026-08-30 после второго прогона): для каждого
кандидата в критические неизвестные явно ответить — "если бы я узнал это
прямо сейчас, поменялось бы моё следующее конкретное действие?" (не
абстрактный "топ-3 вывод Шага 10" — на объекте без полного синтеза
сравнивать не с чем; "следующее действие" работает и при анализе узкого
решения, и при полном 10-шаговом прогоне, где действие — это один из
топ-3). Да → критическое, оставить в списке. Нет / не уверен → скрытое
или известное, не критическое — понизить, не пытаться раздуть список
критических неизвестных ради полноты раздела (та же дисциплина, что
HARD RULE 3 против "скрытых истин ради оригинальности").

## Шаг 10 — Синтез

- **Контринтуитивные выводы** — то, что противоречит наивному прочтению
  системы ("больше X ≠ пропорционально больше Y", и почему).
- **Что проверить дальше** — конкретные, дешёвые следующие шаги, не общие
  пожелания.
- **Топ-3 вывода**, ранжированные по практической значимости — не по
  интересности. Для каждого — дёшево ли действовать сейчас, или это
  отдельная задача на будущее.

## Формат ответа

Разделы 1-10 ровно в этом порядке, с заголовками. Не сокращать до только
топ-3 без промежуточных шагов — рецензируемость важнее краткости для этого
скилла (в отличие от `/suggest`, где краткость — цель).

## Связанные скилы

- `boyko-scientific-consortium` — для проверки ОДНОЙ научной гипотезы через
  причинную карту (confounders/mediators/colliders) — этот скилл про
  структуру системы в целом, не про falsification одного тезиса.
- `macro-locality` — для быстрой эскалации ОДНОЙ аномалии ("это локально
  или часть большего") — этот скилл предполагает полное картирование, не
  реактивную проверку одного случая.
- `cross-domain` — для переноса механизма из другой области — этот скилл
  работает внутри одной системы, не ищет структурные изоморфизмы снаружи.
- `atomize` — для декомпозиции ПРОЕКТА на атомы/bottleneck — уже частично
  включает похожую логику, но без leverage-points/feedback-loop лексики
  Meadows и без явного разделения [VERIFIED]/[HYPOTHESIS] по каждому выводу.
