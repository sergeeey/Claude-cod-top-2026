# /boyko-toolcheck — Живая проверка внешних инструментов

> Статус-источник истины — `skills/registry.yaml`. Версия 1.1 — см. footer.

## Почему не просто "файл существует"

`test -f` или `where <tool>` подтверждают, что бинарник ЕСТЬ на диске — но
не что он реально запускается с текущей версией зависимостей, текущей
авторизацией, текущим конфигом. Ровно так сегодня были найдены живьём два реальных бага: `.codex/config.toml` месяцами ссылался на модель, которая отвергается текущим типом аккаунта, и Codex CLI был устаревшей версии, которая не поддерживала даже рабочий дефолт аккаунта. Оба факта были бы
не видны при проверке "файл существует" — только при реальном запуске.

## Дисциплина: настоящая команда, не догадка

Для каждого инструмента — минимальная, дешёвая, но РЕАЛЬНО выполняемая
команда (не деструктивная, не требующая подтверждения):

| Инструмент | Проверочная команда | Что подтверждает работоспособность |
|---|---|---|
| graphify (meta-graph) | `graphify-query.py stats` (путь к скрипту — из конфигурации пользователя) | Реальные числа (узлы/связи), не ошибка импорта/пути |
| <ваш CLI-инструмент> | `<дешёвая проверочная команда, например tool --version>` | Реальный вывод, не ошибка импорта/пути |
| Codex CLI | `codex --version` (уровень STARTS); `codex login status` (уровень AUTHENTICATED); `codex doctor` — диагностика, не доказательство рабочего процесса | Версия подтверждает только запуск. Авторизацию подтверждает статус входа. Рабочий процесс — только отдельный функциональный контракт |

Список расширяемый — если пользователь называет другой внешний
инструмент, от которого зависит его работа (не Claude Code hook/skill,
а отдельный CLI/сервис), добавь его сюда же по той же логике: дешёвая
команда, реальный вывод, не догадка.

## Уровни готовности (v1.1, по аудиту №10)

PASS означает только то, что реально проверено. Уровни идут по порядку; выше можно
заявлять, только если все ниже пройдены:

| Уровень | Что доказывает | Пример свидетельства |
|---|---|---|
| `DISCOVERED` | бинарник найден | путь из `which`/`where` |
| `STARTS` | CLI запускается и отдаёт осмысленный вывод | `--version`, код 0, не пустой вывод, в JSON нет ключа `error` |
| `AUTHENTICATED` | авторизация подтверждена безопасной командой статуса | `login status` |
| `FUNCTIONAL` | одна реальная функция работает на ожидаемом результате (оракул) | контракт проверки, см. ниже |
| `WORKFLOW_READY` | конкретный рабочий процесс проекта проходит | прогон процесса |

`CLI_START_OK` — не `AUTH_OK` и не `WORKFLOW_OK`. Общий итог: `PASS` только при
`WORKFLOW_READY`; иначе `PARTIAL` с указанием достигнутого уровня; если ни один не
достигнут — `FAIL`. Заявленный уровень выше достигнутого — ошибка отчёта.

## Контракт проверки (на каждый инструмент)

Для каждого инструмента до запуска зафиксировать:

- **безопасная команда** (только чтение или статус; без изменения состояния и без платных вызовов);
- **ожидаемый результат (оракул)**: что должно быть в выводе для PASS;
- **негативные признаки**: `error`, `not logged in`, пустой вывод, код 0 при ошибке в теле;
- **условие остановки**: таймаут, запрос ввода, неожиданный код.

Код 0 без проверки тела вывода PASS не даёт.

## Ограничения исполнения (v1.1)

- Таймаут на команду (по умолчанию 20 секунд). Зависла — `TIMEOUT`, не `FAIL` и не `PASS`.
- Аргументы пользователя в команду не подставлять строкой в shell: только фиксированный
  список команд из контракта.
- Команда просит ввод или открывает браузер (например, логин по OAuth) — остановиться и
  передать шаг человеку. Агент не ждёт в неинтерактивной оболочке.
- Флаг или подкоманду проверять через `<tool> <sub> --help` установленной версии, прежде
  чем использовать (источник: actual CLI companion, прочитан 2026-11-01).
- Платные и изменяющие состояние операции не запускаются в диагностике.

## Редактирование вывода (v1.1)

Перед тем как цитировать вывод или сохранять его, заменить секреты и пользовательские
пути на `[REDACTED]` и `[USER]`: токены, пароли, `Authorization`, ключи вида `sk-…`,
домашние каталоги. Код ошибки, версия и статус остаются. Реализация: `scripts/toolcheck.py`
(`redact`).

## Шаги

1. Для каждого инструмента из таблицы (или названного пользователем) —
   выполни его проверочную команду через Bash. На Windows учитывай MSYS
   path-mangling для аргументов с ведущим `/` или `\` (см. известный
   класс проблем этой же сессии: `/query`, `.codex/config.toml` через
   `git show` — при странной ошибке пробуй через `cmd //c` или batch-файл
   раньше, чем делать вывод "инструмент не работает").
2. Процитируй РЕАЛЬНЫЙ вывод команды — не резюме "работает", а конкретные
   числа/версию/текст ошибки.
3. Если команда упала — не гадай причину. Покажи фактическую ошибку и,
   если причина неочевидна из одного сообщения, скажи "причина неясна из
   этого вывода, нужно смотреть отдельно" вместо того чтобы придумывать
   правдоподобное объяснение.

## Вывод — без обобщений

```
[boyko-toolcheck]
<инструмент 1>: <команда> → <реальный вывод ИЛИ ошибка, с редакцией секретов>
  уровни: DISCOVERED=PASS STARTS=PASS AUTHENTICATED=NOT_RUN FUNCTIONAL=NOT_RUN
  итог: PARTIAL (достигнут STARTS) — claim: CLI_START_OK
```

Итог показывает достигнутый уровень и заявление; `PASS` только при `WORKFLOW_READY`.
Не добавляй «всё в порядке» в конце — таблица говорит сама за себя.
