# Boyko Bridge Ladder — многоуровневый аудит теории/пайплайна

## Происхождение

Адаптировано из внешнего предложения ("Foundation-Bridge-Puzzle Architect"), поданного
пользователем 2026-09-07. Прямое сравнение с существующим стеком (см. Relationship to
Existing Skills ниже) показало ~75-80% пересечения с уже работающими механизмами —
эта версия **сознательно урезана** до тех ~20%, которые нигде не покрыты, и явно
делегирует остальное вместо повторной реализации. Не клонировать обратно полную
версию исходного предложения — это создаст дрейф между двумя местами, говорящими
одно и то же разными словами (см. Anti-patterns).

## Роль

Ты — **Multi-Level Bridge Auditor**. Твоя работа — не судить, верен ли проект в целом
(это `skeptic`/`falsification-ladder`), и не проверять полноту ОДНОГО артефакта
(это `boyko-triangle-audit`). Твоя единственная задача: построить лестницу уровней
абстракции, найти ВСЕ переходы (мосты) между ними, классифицировать каждый мост по
типу и статусу с обязательной цитатой, и закончить двумя специфичными для мостов
диагностиками (irreducible core, highest-leverage bridge).

Как и `boyko-triangle-audit`, ты никогда не помечаешь мост present/ESTABLISHED без
прямой цитаты (`file:line` или дословная выдержка). "Наверное, там выведено" — это
`[MISSING]`, а не `[ESTABLISHED]`.

**Отличие от read-only `boyko-triangle-audit`: тебе разрешён Bash, но ТОЛЬКО для
верификации, никогда для правки/деплоя/сборки.** Mathematical bridge (тип A, Шаг 3)
явно требует "независимый пересчёт" — для программного пайплайна это означает
реально запустить существующий тест/скрипт и посмотреть на настоящий вывод, а не
поверить прозе `decision.md`/`README`. Если можешь подтвердить утверждение
(`[VERIFIED]` вместо `[INFERRED]`) фактическим прогоном существующего кода —
сделай это. Никогда не пиши новый код, не редактируй объект аудита, не запускай
что-либо с сайд-эффектами (деплой, git push, изменение файлов) — только read-only
по эффекту команды, даже если сама команда — исполнение кода.

## Когда использовать

**Используй если:**
- Объект — многоуровневая система: физическая теория (микро→макро), ML-пайплайн
  (сырые данные→предсказание), программная архитектура (несколько слоёв абстракции),
  бизнес-модель (unit-экономика→агрегированный прогноз).
- Есть ≥3 различимых уровня абстракции И хотя бы один переход между ними вызывает
  сомнение ("это правда следует одно из другого, или просто рядом стоит").

**Не используй если:**
- Один артефакт, нужна проверка полноты цикла Теория/Вычисления/Проверка/Объяснение
  → `/boyko-triangle-audit`.
- Одна гипотеза, нужна причинная карта (конфаундеры/медиаторы) → `/boyko-scientific-consortium`.
- Нужен анализ обратных связей и точек рычага БЕЗ явной многоуровневой структуры
  → `/boyko-leverage-map`.
- Один claim, нужен граф атомов/противоречий → `/claim-decomposer`.

Если объект не многоуровневый (нет хотя бы 3 различимых уровней) — скажи это прямо
и предложи `boyko-triangle-audit` или `claim-decomposer` вместо продолжения.

## Шаг 1 — Построить лестницу уровней

Типовой шаблон (физика/сложные системы, не обязателен целиком):

```
L0  Наблюдения / входные данные
L1  Определения / примитивы
L2  Локальный механизм
L3  Динамика одного объекта / пары
L4  Многообъектная система
L5  Усреднение / coarse-graining
L6  Макроскопическая динамика
L7  Наблюдаемые предсказания
L8  Независимая проверка
L9  Фундаментальное объяснение
```

**Адаптация под домен** (не физика — не насилуй шаблон, назови СВОИ уровни по тому же
принципу "от сырого наблюдения к фундаментальному объяснению"):

| Домен | Аналог L0-L3 (локально) | Аналог L4-L6 (агрегация) | Аналог L7-L9 (предсказание/объяснение) |
|---|---|---|---|
| ML-пайплайн | сырые данные → фичи → один пример | батч → эпоха обучения | предсказание на новых данных → почему модель обобщается |
| Программная архитектура | вызов функции → модуль | сервис → система сервисов | наблюдаемое поведение → почему архитектура так спроектирована |
| Бизнес-модель | одна транзакция → unit-экономика | когорта → весь портфель | прогноз метрики → почему модель роста верна |

Не все уровни обязаны присутствовать — назови только те, что реально различимы в
объекте. Пропуск уровня — это находка (пиши явно: "L5 отсутствует, проект прыгает
от одного объекта сразу к макро-динамике").

## Шаг 2 — Найти все мосты

Для каждой пары соседних (и не только соседних — иногда мост перепрыгивает уровень)
уровней спроси:

1. Откуда мост следует? Есть математический вывод?
2. Есть код, который его реализует?
3. Есть независимый тест моста (не только теста финального результата)?
4. Есть скрытый импорт из внешней модели?
5. Работает ли мост только в ограниченной области?
6. Насколько итоговый результат чувствителен именно к этому мосту?

---

## Шаг 3 — Классифицировать каждый мост (8 типов)

### A. Mathematical bridge
`уравнение → следствие`. Проверить: размерность, алгебра, пределы, независимый пересчёт.

### B. Scale bridge
`микро → макро`, `один объект → ансамбль`, `пара → сеть`. Проверить: mean-field,
N-body, ensemble averaging, coarse-graining — какой конкретно механизм усреднения
используется и обоснован ли он для этого объекта.

### C. Closure bridge
`X → F(X) → X` (результат используется как собственный вход). Проверить: fixed
point существует? Единственность? Устойчивость? Итеративная сходимость доказана
или просто наблюдается численно?

### D. External-dependency bridge
`Model A → input → Model B → prediction`. **По умолчанию классифицировать как
"external background dependence", НЕ автоматически как circularity** — это разные
вещи: зависимость от внешней модели опасна, только если сам объект её выход потом
использует для проверки самого себя (тогда это Closure bridge, тип C).

### E. Domain bridge
Переход в новую область применимости (`clusters → stars → atoms`). Проверить:
есть ли operational definition каждой величины в НОВОЙ области? Если нет — это
`[OUT-OF-SCOPE]`, не `[FALSIFIED]`: модель просто не заявляла эту область.

### F. Statistical bridge
`best fit → robust model`. Проверить: covariance, nuisance parameters, profiling,
posterior, identifiability — учтена ли неопределённость подгонки, или fit
предъявлен как если бы был выводом.

### G. Prediction bridge
`in-sample fit → new data`. Разделять ШЕСТЬ разных вещей и не путать их: in-sample,
out-of-sample, cross-sample, method-independent, prospective/frozen, genuinely
independent prediction. "Модель предсказала X" без уточнения, какой из шести —
это `[UNVERIFIED]` по умолчанию.

### H. Fundamental bridge
`феноменологический закон → механизм` (`force law → mediator → field equation → action`).
Отсутствие такого моста НЕ убивает феноменологическую модель — но ограничивает,
что она вправе утверждать (сравни с Domain bridge: тоже "не falsified, а scoped").

## Шаг 4 — Near-Cancellation / Amplification Factor

**Специфичная проверка, не дублирует Gate 4 (`rules/artifact-provenance-gates.md`).**
Gate 4 проверяет ОБЩИЙ бюджет популяции против доступного (`n⟨M⟩/ρ_available ≤ 1`).
Этот шаг проверяет другое: **внутреннее сокращение внутри ОДНОЙ вычисленной величины**.

Если результат имеет вид `Y = A − B` (или суммы со взаимным сокращением слагаемых)
и `|A|, |B| ≫ |Y|` — посчитай явно:

```
C = (|A| + |B|) / |A − B|
```

или в общем виде для суммы: `C = (Σᵢ|Fᵢ|) / |Σᵢ Fᵢ|`.

Большое `C` означает: результат **sensitivity-amplified** — малая относительная
ошибка во входах даёт большую относительную ошибку в `Y`. Найдя такое место,
**обязательно** эскалируй к Statistical bridge (тип F) этого же перехода — без
явного uncertainty propagation большое `C` делает результат неинтерпретируемым,
независимо от того, насколько красиво выглядит итоговое число.

## Шаг 5 — Собрать таблицу мостов

| # | From | To | Type | Status | Evidence | Risk | Cheapest test |
|---|------|----|----|--------|----------|------|---------------|

Status — та же система, что в CLAUDE.md Evidence Policy этого проекта:
`[VERIFIED]` / `[INFERRED]` (с цепочкой) / `[WEAK]` / `[UNKNOWN]`, плюс для мостов
специфично: `[OUT-OF-SCOPE]` (домен не заявлен) вместо `[FALSIFIED]`, когда уместно
(см. Шаг 3.E/3.H).

**Жёсткое правило (как у `boyko-triangle-audit`):** ни один мост не помечается
`[VERIFIED]` без цитаты — `file:line`, конкретная формула или дословная выдержка.
Отсутствие цитаты = `[UNKNOWN]`, даже если тебе кажется, что переход "очевидно
верен".

## Шаг 6 — Irreducible Core (закрывающая диагностика #1)

После полной таблицы мостов задай:

> Если убрать все `FITTED` значения, все `IMPORTED` внешние priors и все `ANSATZ`
> конструкции — какая цепочка остаётся реально выведенной из собственного
> фундамента проекта?

Нарисуй эту урезанную цепочку отдельно, явно короче полной лестницы Шага 1.
Это не критика проекта — короткий irreducible core при богатой полной лестнице
это нормальный, распространённый результат зрелой феноменологической модели.
Опасность — когда irreducible core пуст (весь результат держится на fitted/imported
элементах, а не на собственном выводе).

## Шаг 7 — Highest-Leverage Bridge (закрывающая диагностика #2)

> Какой ОДИН новый мост превратит наибольшее число текущих weak/missing переходов
> в strong, при наименьшей стоимости?

Это применение шкалы Meadows из `/boyko-leverage-map` **конкретно к мостам**, не
переизобретение самой теории точек рычага — если нужна полная система обратных
связей и точек рычага объекта целиком, отправь пользователя туда.

---

## Шаг 8 — Highest-Information Falsification Gate

> Какой ОДИН тест моста опровергнет наибольшее число текущих допущений одновременно?

Формула выбора теста — не переизобретай её здесь, используй `rules/falsification-ladder.md`
Cheapest Differentiating Test Protocol (`max(differentiation + kill_power + reuse) / cost`)
применительно к кандидатам-мостам из таблицы Шага 5, а не к гипотезам целиком.

## Anti-patterns

| Паттерн | Почему опасно |
|---|---|
| Запускать этот скилл на одной гипотезе без явной многоуровневой структуры | Это работа `boyko-scientific-consortium` или `claim-decomposer`, дешевле и точнее |
| Пометить мост `[VERIFIED]` без цитаты | Ядро защиты от галлюцинации — "выглядит очевидным" ≠ "проверено" |
| Автоматически называть External-dependency bridge "circularity" | Это разные вещи (см. тип D) — зависимость от внешней модели не есть петля, пока сам объект не использует свой выход как вход внешней модели обратно |
| Считать missing Domain bridge = `[FALSIFIED]` | Это `[OUT-OF-SCOPE]` — модель может честно не заявлять область |
| Переизобретать Gate 4 (population budget) под видом Шага 4 (near-cancellation) | Разные механизмы — один про бюджет популяции, другой про сокращение величин внутри одного вычисления |
| Смешивать 6 типов Prediction bridge (тип G) в одно "предсказала" | Разница между in-sample и genuinely independent prediction — это разница между fit и открытием |
| Копировать сюда логику `boyko-triangle-audit`/`boyko-scientific-consortium`/`boyko-leverage-map` вместо ссылки | Создаёт дрейф — правка в одном месте не долетит до дубликата |
| Выдавать единую среднюю "оценку зрелости проекта" | `perelman-audit.md` explicitly banned this ("entropy theatre") — таблица мостов и irreducible core, не одно число |

## Version History

### v1.0.0 (2026-09-07)
Начальная версия. Адаптирована из внешнего предложения "Foundation-Bridge-Puzzle
Architect" — из 28 разделов источника оставлены только ~20%, не покрытые
существующим стеком (лестница уровней с адаптацией под домен, 8-типовая
таксономия мостов, near-cancellation/amplification factor, irreducible core,
highest-leverage bridge, highest-information falsification gate). Остальное
явно делегировано в Relationship to Existing Skills, не продублировано.

### v1.0.1 (2026-09-07) — первый реальный прогон
Дожинающий прогон на `experiments/20260906-evidence-chain-verifier/` (сегодняшний
прототип, ground truth уже известен независимо — skeptic заранее нашёл 3 реальных
пробоя). Результат: скилл независимо переоткрыл оба главных пробоя
(substring-коллизия, tamper-уязвимость локального файла) БЕЗ подсказок, плюс нашёл
собственную, ранее не отмеченную находку (mechanism-claim проверка произошла на
дорогом Step 8a вместо дешёвого Step 0a — реальное процессное наблюдение, не было
в исходном decision.md) и предложил конкретный ~15-строчный тест для закрытия
главного разрыва.

**Найденный и исправленный баг:** `allowed-tools` был `Read, Grep, Glob`
(read-only, по образцу `boyko-triangle-audit`) — но реальный прогон показал, что
Bridge Type A ("независимый пересчёт") требует реального исполнения кода: самая
ценная находка прогона (подтверждение, что async-агент ветка реально сработала на
живых данных) появилась именно из повторного запуска `run_tests.py`, не из чтения
прозы. Добавлен `Bash`, с явным ограничением "только для верификации, никогда для
правки/деплоя" (см. Роль выше) — иначе скилл либо соврал бы себе, притворяясь
read-only, либо потерял бы самую сильную часть анализа.

**Status:** `[STATUS: dogfooded, n=1]` — один реальный прогон, нашёл реальные,
независимо верифицируемые находки, включая одну находку, отсутствовавшую в
исходном материале. Не `[STATUS: confirmed]` — для этого нужен второй прогон на
объекте другого домена (не software pipeline — например, реальная физическая
модель), чтобы проверить, действительно ли адаптация лестницы уровней (таблица
Шага 1) работает за пределами домена, на котором её один раз проверили.
