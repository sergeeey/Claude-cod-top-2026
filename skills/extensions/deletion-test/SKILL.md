# Deletion Test — Архитектурный аудит

## Суть

Для каждого модуля задай один вопрос: **"Что изменится в поведении системы, если я удалю это прямо сейчас?"**

- Ничего не изменится → модуль мёртвый груз, кандидат на удаление
- Логика дублируется в N местах → модуль недостаточно централизован
- Система ломается → модуль критический, нужна явная документация зависимостей

**Главный фильтр:** существование файла ≠ необходимость файла.

---

## Что нужно от пользователя

Спроси (или извлеки из контекста):

1. **Точка входа** — главный скрипт, entrypoint, основная команда запуска
2. **Директории в scope** — что аудировать (весь проект или конкретный слой)
3. **Цель** — удалить мусор / найти дублирование / понять coupling

---

## Алгоритм (4 шага)

### Шаг 1: Карта модулей

Составь список всех модулей/файлов в scope:

```bash
find <dir> -name "*.py" -o -name "*.ts" -o -name "*.js" | sort
```

Для каждого модуля — найди его импорты и обратные зависимости:

```bash
grep -rn "import.*<module>\|from.*<module>" <dir>/
```

### Шаг 2: Виртуальное удаление

Для каждого модуля ответь на 3 вопроса:

| Вопрос | Ответ | Значение |
|--------|-------|---------|
| Кто импортирует этот модуль? | N файлов | Fan-in (сколько зависят) |
| Что этот модуль вызывает? | M модулей | Fan-out (сколько от него зависит) |
| Если удалить — что упадёт? | список | Реальный coupling |

**Если fan-in = 0** → никто не импортирует → **кандидат на удаление**.  
**Если логика модуля повторяется в ≥3 местах** → дублирование, нужна централизация.  
**Если fan-in ≥ 10** → god-module, нужно разбить.

### Шаг 3: Классификация

Назначь каждому модулю класс:

| Класс | Критерий | Действие |
|-------|---------|---------|
| 🔴 **DEAD** | fan-in=0, не вызывается из entry path | Удалить |
| 🟡 **DUPLICATE** | логика повторяется в ≥3 местах | Централизовать |
| 🟠 **GOD** | fan-in ≥ 10 или >500 строк с разношёрстной логикой | Разбить |
| 🟢 **HEALTHY** | чёткая ответственность, умеренный coupling | Оставить |
| 🔵 **CRITICAL** | удаление ломает систему, нет дублёра | Документировать зависимости |

### Шаг 4: Отчёт DELETION_TEST_REPORT.md

    # DELETION TEST REPORT — <Проект> / <Дата>

    ## Точка входа

    ## Карта coupling

    | Модуль | Fan-in | Fan-out | Класс | Действие |
    |--------|--------|---------|-------|---------|
    | auth.py | 0 | 2 | 🔴 DEAD | Удалить |
    | db_utils.py | 12 | 5 | 🟠 GOD | Разбить |

    | core_engine.py | 8 | 9 | 🔵 CRITICAL | Документировать |

    ## 🔴 Кандидаты на удаление (DEAD)
    Для каждого — доказательство:
    - `auth.py` — grep показал 0 импортов во всём проекте (см. трассировку)

    ## 🟡 Дублирование (DUPLICATE)
    - Логика валидации email повторяется в: `signup.py:47`, `profile.py:23`, `admin.py:89`
      → Централизовать в `validators/email.py`

    ## 🟠 God-модули (GOD)
    - `db_utils.py` — 12 импортёров, 487 строк, 3 несвязанные ответственности
      → Предлагаемое разбиение: `db/connection.py`, `db/queries.py`, `db/migrations.py`

    ## 🔵 Критические зависимости (CRITICAL)
    - `core_engine.py` — удаление ломает 8 модулей, нет дублёра
      → Добавить README.md + явные интерфейсы

    ## Следующие шаги
    1. [ ] Удалить DEAD модули (безопасно, 0 зависимостей)
    2. [ ] Централизовать DUPLICATE (создать новый модуль, перенаправить импорты)
    3. [ ] Разбить GOD-модули (рефакторинг с тестами)
    4. [ ] Задокументировать CRITICAL (защита от случайного удаления)

## Ключевые инсайты

**Про DEAD модули:**  
Перед удалением — grep ещё раз по строкам, не только по именам файлов. Динамические импорты (`importlib`, `__import__`, строковые имена) не поймает статический grep.

**Про GOD-модули:**  
Fan-in ≥ 10 не всегда плохо — utility-модули (`utils.py`, `helpers.py`) естественно имеют высокий fan-in. Флаг срабатывает когда высокий fan-in *и* несвязанные ответственности одновременно.

**Companion скилы:**

- `intended-vs-implemented` — "что код делает vs что должен делать" (семантика)

**Типичная цепочка:** `/deletion-test` (карта мусора) → удалить DEAD → `/code-materiality` (triage оставшихся рисков) → `/sci-code-audit` (hardening).
