## Findings and concrete fixes

### F1 — A stalled telemetry writer can discard an already-printed denial

**HIGH; #518.** [CODE] [`hooks/permission_policy.py:750`](https://github.com/sergeeey/Claude-cod-top-2026/blob/254d26a895ce27bb72046d9b01fcfe6441c3448d/hooks/permission_policy.py#L750) flushes stdout and calls `log_hook_trigger` synchronously. Both deny branches wait for this call. The writer performs directory creation, rotation and file I/O. Catching exceptions does not bound a blocked I/O operation. [`hooks/settings.json:171`](https://github.com/sergeeey/Claude-cod-top-2026/blob/254d26a895ce27bb72046d9b01fcfe6441c3448d/hooks/settings.json#L171) gives the command hook five seconds and does not set `onFailure`; the Python `hook_main` watchdog defaults to 30 seconds.

[VERIFIED-SYNTHETIC] `probes.py` ran the base and target `main()` functions through the real `hook_main(..., fail_closed=True)` wrapper, replacing only the telemetry writer with a ten-second sleeper. Both received the same synthetic denied command string. **The base exited 0 with one deny; the target exceeded the five-second subprocess deadline despite already flushing that same deny.** No payload command was executed, no real log was touched, and no live Claude session was launched.

[DOCS] Claude Code cancels timed-out command hooks and discards their output. A timed-out PreToolUse command hook falls through to normal permission processing unless configured to block on failure. [Official timeout contract](https://code.claude.com/docs/en/hooks#timeouts).

[INFERRED] Therefore slow logging can remove this hook's deny at the harness boundary. Other static rules or hooks may still block a particular command; this audit does **not** claim a demonstrated end-to-end bypass of every protection. The mismatch between the existing 5/30-second timeouts predates the PR, but #518 adds this new post-decision blocking path.

**Fix:** Bound or detach telemetry work so the policy process exits promptly with one valid decision even when logging cannot complete. Keep any detached writer's stdout/stderr separate. Where the deployed Claude Code version supports it, independently configure the policy hook to block on failure; do not silently assume version support. Add process/harness tests for a hung writer and verify the consumer honors the denial. Swallowing exceptions or adding more flushes is insufficient.

The archived entry uses a recognized status. The dates and status are real committed artifacts; the evaluation date is explicitly supplied.

### F3 — The skill guide confuses pre-approval with restriction

**MEDIUM; #514.** [CODE] [`docs/skills-guide.md:51`](https://github.com/sergeeey/Claude-cod-top-2026/blob/254d26a895ce27bb72046d9b01fcfe6441c3448d/docs/skills-guide.md#L51) labels the section “Tool restriction” and states that skills restrict tools with `allowed-tools`.

[DOCS] The current official reference explicitly says this field pre-approves listed tools and does not remove the other tools; ordinary permission settings govern those other tools. [Claude Code skill permission semantics](https://code.claude.com/docs/en/skills#pre-approve-tools-for-a-skill).

**Impact:** A maintainer can mistake a convenience grant for a security boundary. This is a documentation defect, not proof that an unauthorized tool ran. **Fix:** Rename the section to tool pre-approval, explain the actual scope, and distinguish explicit deny/tool-removal mechanisms. Verify version compatibility before recommending newer frontmatter fields. The correction from agent `tools` to skill `allowed-tools` is useful, but does not establish restriction semantics.

### F4 — The amended declaration regex still counts unfilled fields

**MEDIUM; #514.** [CODE] [`analyze.py:43`](https://github.com/sergeeey/Claude-cod-top-2026/blob/254d26a895ce27bb72046d9b01fcfe6441c3448d/experiments/20261013-ledger-closure-census/analyze.py#L43) uses backtrackable optional asterisks and `\s*` before the value. **Fix:** Parse one physical line at a time; normalize bullet/bold decoration before separately validating a non-empty, non-placeholder value. ## Security scan

- **Trust boundaries:** Hook JSON supplies command/tool inputs and a harness session identifier; the output decision and local telemetry are separate sinks. New code logs constant categories/messages, not the command. Session input is bounded for redaction and then capped. UUID exemption is exact-shape, not a broad character allowlist.
- **Injection:** Reviewed changed Python contains no new shell execution of PR bodies, transcript text or session identifiers. JSON serialization escapes newlines in logged fields; YAML fixtures use `safe_load`. Archived PR prose is untrusted data. Plain display helpers can print that prose, but this audit found no path from it to execution in those helpers.
- **Secrets:** A limited private-key/AWS/GitHub/sk-key signature scan across all 33 changed target files found **zero matches**. No real credentials were printed. This is not an exhaustive secret detector or repository-wide scan. The shared redactor explicitly says it is not exhaustive.
- **Timing:** F1 is the new security-relevant defect. The protected input is a policy-denied request; the failing boundary is synchronous telemetry delaying successful hook completion. It requires a stalled/slow writer; no claim is made that this occurs on every request.
- **Concurrency:** The shared logger's rotation is already best effort and documents race/loss limits. #518 reuses it; no new locking is added. One ordinary append test does not establish exactly-once delivery under concurrent rotation. No concurrency stress test was performed.
- **Measurement:** Deny counts are a lower bound because nested runs, I/O failures and watchdog failures may be absent. Those counts alone do not measure a false-positive rate: outcome labels and a defined sampled population are still needed. No real-world FP improvement was accepted.
